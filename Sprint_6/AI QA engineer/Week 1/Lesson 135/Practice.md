# Практичні завдання до Уроку 135: Створення якісних bug reports

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Трансформація неякісного користувацького відгуку в еталонний Bug Report

**Мета:** Опанувати локалізацію дефекту та складання повноцінного інженерного баг-репорту з сирого відгуку.

**Вхідний контекст та бізнес-сценарій:**
У службу підтримки надійшов емоційний лист: 'Ваш сайт жахливий! Я намагався купити підписку за 20$, а гроші списало двічі і доступ не відкрився!'.

**Покроковий алгоритм виконання:**
1. Виділіть технічні симптоми проблеми: дублювання транзакції (Double Charge), відсутність активації ролі.
2. Сформулюйте гіпотезу передумов та кроків відтворення (Race condition при повторному кліку на кнопку оплати).
3. Складіть професійний заголовок за формулою 'Що? Де? За яких умов?'.
4. Опишіть точні Pre-conditions, Steps to Reproduce, Expected та Actual Result, визначте Severity та Priority.

**Рекомендований системний AI-промпт:**
```text
Ти — Senior QA Engineer. На основі скарги користувача про подвійне списання коштів при оформленні підписки склади бездоганний Bug Report для Jira. Включи правильний Title, Severity S1, Priority P1, точні кроки відтворення, очікуваний та фактичний результат, а також список необхідних технічних додатків (HAR, логи платіжного шлюзу).
```

**Очікуваний результат:**
Повний структурований Bug Report, готовий до передачі бекенд-команді розробки.

**Критерії самоперевірки та оцінювання:**
- [ ] Чіткий інформативний Title без емоцій
- [ ] Логічні та атомарні кроки відтворення
- [ ] Правильне визначення критичності та пріоритету

---

## Завдання 2: Створення автоматизованого AI-промпту для валідації Bug Reports команди

**Мета:** Розробити системний промпт, який перевіряє якість баг-репортів у CI/CD або Slack-боті.

**Вхідний контекст та бізнес-сценарій:**
Команда розробників скаржиться, що джуніор-тестувальники пишуть неповні звіти без передумов і версій оточення.

**Покроковий алгоритм виконання:**
1. Складіть матрицю критеріїв оцінки Bug Report (наявність передумов, точність заголовка, конкретність результатів).
2. Напишіть системний промпт для LLM, який аналізує текст баг-репорту та виставляє оцінку за шкалою 1-10.
3. Налаштуйте бота так, щоб він вказував автору на пропущені обов'язкові блоки (HAR, Console Logs, версія збірки).
4. Протестуйте промпт на двох прикладах: слабкому та еталонному звітах.

**Рекомендований системний AI-промпт:**
```text
Створи системний промпт для AI-асистента, який виконує роль QA Lead та рецензує Bug Reports. Асистент повинен перевіряти дотримання правила 3x у заголовку, повноту кроків, наявність тестових даних та повертати конструктивний список зауважень щодо покращення.
```

**Очікуваний результат:**
Готовий інженерний промпт з детальними правилами перевірки та прикладом аналізу проблемного баг-репорту.

**Критерії самоперевірки та оцінювання:**
- [ ] Суворі об'єктивні критерії оцінки якості репорту
- [ ] Вимога до наявності технічного контексту
- [ ] Практична придатність промпту для інтеграції в боти
