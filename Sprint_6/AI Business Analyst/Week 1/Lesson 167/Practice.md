# Практичні завдання до Уроку 167: User Story та її призначення

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Декомпозиція Epics методом вертикального нарізання (Vertical Slicing)

**Мета:** Опанувати трансформацію монолітного епіку у набір із 4 компактних User Stories за стандартом INVEST.

**Вхідний контекст та бізнес-сценарій:**
У додатку доставки їжі є великий епік: 'Система чайових кур'єру'. Він містить вибір фіксованих сум, введення кастомного відсотка, оплату Apple Pay, оцінку кур'єра та повернення чайових у разі запізнення. Необхідно нарізати його на спринтові історії.

**Покроковий алгоритм виконання:**
1. Виділіть базовий MVP Vertical Slice (перша історія для перевірки гіпотези).
2. Розподіліть розширені функції на 3 наступні незалежні історії.
3. Сформулюйте кожну історію за канонічною трикомпонентною формулою.
4. Перевірте кожну історію за чеклистом INVEST.

**Рекомендований системний AI-промпт:**
```text
Дій як Staff Agile Business Analyst. Проведи декомпозицію великого Epics 'Чайові кур'єру' на 4 компактні User Stories:
Вимоги:
1. Історія 1 (MVP Slice): Фіксовані кнопки чайових (10, 20, 50 грн) на екрані завершення замовлення при оплаті збереженою карткою.
2. Історія 2: Можливість введення довільної суми чайових вручну.
3. Історія 3: Можливість додати чайові заздалегідь під час первинного чекауту.
4. Історія 4: Звіт для кур'єра про отримані чайові за зміну в кур'єрському додатку.
Для кожної історії надай:
- Заголовок та канонічний опис (Як [персона], Я хочу [...], Щоб [...]).
- Обґрунтування відповідності критеріям INVEST.
```

**Очікуваний результат:**
Чотири повноцінні User Stories у форматі Markdown із чітким обґрунтуванням відповідності стандарту INVEST.

**Критерії самоперевірки та оцінювання:**
- [ ] Кожна історія сформульована суворо за канонічною моделлю
- [ ] Кожна історія являє собою повноцінний вертикальний зріз цінності (Vertical Slice)
- [ ] Повна незалежність історій між собою
- [ ] Реалістичний розмір для виконання за 1-2 дні розробки

## Завдання 2: Аудит та рефакторинг технічного беклогу в людиноорієнтовані User Stories

**Мета:** Навчитись виявляти та усувати антипатерни в Agile беклозі (виправлення суто технічних задач у бізнес-історії).

**Вхідний контекст та бізнес-сценарій:**
У беклозі розробники завели задачі: 1) 'Переробити базу під Redis'; 2) 'Підключити Firebase Push SDK'; 3) 'Створити таблицю users_settings'. Product Owner не розуміє, за що платить гроші бізнес. Необхідно переписати ці задачі в ціннісні User Stories.

**Покроковий алгоритм виконання:**
1. Проаналізуйте приховану бізнес-мету кожної з 3 технічних задач.
2. Визначте реальну персону (кінцевий користувач або внутрішній оператор).
3. Переформулюйте задачі за стандартом канонічної формули з акцентом на кінцеву вигоду.
4. Складіть аргументацію для команди, чому такий підхід підвищує мотивацію та якість продукту.

**Рекомендований системний AI-промпт:**
```text
Дій як Agile Coach & Lead Business Analyst. Проведи рефакторинг трьох технічних задач беклогу:
Технічні записи:
1. 'Інтегрувати Redis для кешування профілів користувачів'.
2. 'Підключити Firebase Cloud Messaging SDK у фронтенд'.
3. 'Додати прапорець dark_mode_enabled у таблицю налаштувань бази даних'.
Завдання:
1. Поясни, чому поточні формулювання є типовим антипатерном Agile.
2. Перепиши кожну задачу як повноцінну User Story для кінцевого користувача з обов'язковою бізнес-цінністю (Benefit).
3. Покажи, як зміниться розуміння задачі розробником після рефакторингу.
```

**Очікуваний результат:**
Аналітичний розбір антипатернів та три еталонні User Stories у форматі Markdown.

**Критерії самоперевірки та оцінювання:**
- [ ] Глибоке розкриття шкоди суто технічних описів у бізнес-беклозі
- [ ] Точне перетворення технічних дій на вигоди для реальних людей
- [ ] Правильні формулювання дієслів у кожній частині шаблону
- [ ] Підвищення прозорості беклогу для стейкхолдерів
