# Практичні завдання до Уроку 170: Опис основних, альтернативних і помилкових сценаріїв

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

## Завдання 1: Повна специфікація основного, альтернативного та трьох помилкових потоків для переказу коштів

**Мета:** Опанувати професійний опис розгалужень прецеденту з використанням стандартизованої інженерної нотації нумерації.

**Вхідний контекст та бізнес-сценарій:**
Необхідно описати детальний Use Case 'Переказ коштів між власними рахунками у мобільному банку'. Потрібно охопити успішний шлях, альтернативний шлях із конвертацією валют (гривня -> долар) та 3 сценарії збоїв.

**Покроковий алгоритм виконання:**
1. Опишіть Основний потік (Happy Path) із 6 кроків у гривні.
2. Складіть Альтернативний потік 2a: переказ з гривневого рахунку на доларовий із фіксацією курсу на 30 секунд.
3. Складіть Помилковий потік 3a: недостатньо коштів на рахунку списання.
4. Складіть Помилковий потік 2a.1: сплив 30-секундного таймера курсу валют під час конвертації.
5. Складіть Помилковий потік 5a: блокування транзакції фрод-моніторингом банку.

**Рекомендований системний AI-промпт:**
```text
Дій як Staff Systems Analyst у фінтех-додатку. Опиши Use Case 'Переказ між власними рахунками':
Вимоги:
1. Основний потік (Main Flow): 6 чітких кроків (вибір рахунку списання, вибір рахунку зарахування, введення суми, перевірка, підтвердження FaceID, успішне зарахування).
2. Альтернативний потік 2a (Валютна конвертація): якщо валюти рахунків різняться — показ курсу НБУ + маржа банку, таймер фіксації курсу на 30 секунд, повернення в крок 4.
3. Помилковий потік 3a (Недостатній баланс): зупинка на кроці 3, показ доступного залишку, пропозиція зменшити суму.
4. Помилковий потік 2a.1 (Сплив таймера курсу): сповіщення про зміну курсу, запит підтвердження за новим курсом або відміна.
5. Помилковий потік 5a (Блокування безпекою): перевірка на підозрілу активність, замороження сесії, екран із телефоном підтримки.
Використовуй сувору нумерацію кроків (1, 2, 2a.1 тощо).
```

**Очікуваний результат:**
Повноцінна специфікація розгалуженого Use Case за промисловим стандартом у форматі Markdown.

**Критерії самоперевірки та оцінювання:**
- [ ] Суворе дотримання нотації нумерації кроків відгалужень
- [ ] Чітке розділення поведінки інтерфейсу користувача та реакцій банківського бекенду
- [ ] Повне опрацювання критичних валютних та фродових ризиків
- [ ] Відсутність тупикових ситуацій для клієнта

## Завдання 2: Складання матриці обробки помилок (Error Matrix) для REST API оформлення замовлення

**Мета:** Навчитись систематизувати системні винятки, HTTP статус-коди та тексти користувацьких інтерфейсів.

**Вхідний контекст та бізнес-сценарій:**
Для ендпоінту `POST /api/v1/orders/checkout` необхідно скласти матрицю з 6 типових помилок (помилки валідації 400, неавторизований доступ 401, вичерпання лімітів 422, збій платіжного шлюзу 502, таймаут 504).

**Покроковий алгоритм виконання:**
1. Визначте для кожної помилки HTTP статус-код та внутрішній доменний Error Code.
2. Опишіть технічну причину на рівні бази даних або інтеграції.
3. Складіть точне, безпечне та людиноорієнтоване повідомлення для клієнта.
4. Опишіть рекомендовану дію користувача (Actionable CTA) для кожного випадку.

**Рекомендований системний AI-промпт:**
```text
Дій як Lead Business Analyst & API Architect. Склади таблицю Error Handling Matrix для сервісу оформлення замовлення:
Покрий 6 типових виняткових ситуацій:
1. Кошик порожній (Bad Request 400).
2. Сесія застаріла під час чекауту (Unauthorized 401).
3. Товар із кошика закінчився на складі (Unprocessable Entity 422).
4. Промокод втратив дію або перевищено ліміт активацій (Unprocessable Entity 422).
5. Платіжний шлюз повернув внутрішню помилку еквайрингу (Bad Gateway 502).
6. Бекенд не зміг зафіксувати транзакцію через таймаут бази даних (Gateway Timeout 504).
Колонки таблиці: HTTP Status | Domain Error Code | Technical Cause | UI Error Message | Recommended User Action.
```

**Очікуваний результат:**
Комплексна таблиця Markdown з повною специфікацією обробки помилок API та UI.

**Критерії самоперевірки та оцінювання:**
- [ ] Правильне використання стандартних HTTP статусів згідно з RFC 9110
- [ ] Безпечні людиноорієнтовані повідомлення без витоку внутрішніх деталей систем
- [ ] Наявність конструктивної дії виходу (Actionable CTA) для кожної помилки
- [ ] Повна готовність специфікації для передачі розробникам та QA
