# Практичні завдання до Уроку 157: Витягування фактів та аргументів

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Декомпозиція технічної статті за моделлю аргументації Тулміна

**Мета:** Опанувати аналітичний розбір публікації на Claims, Grounds, Warrants та Rebuttals.

**Вхідний контекст та бізнес-сценарій:**
Відомий CTO опублікував резонансну статтю: 'Чому ми повністю відмовилися від Kubernetes на користь простих віртуальних машин'. Команда вагається, чи варто наслідувати цей приклад. Потрібно препарувати аргументацію автора.

**Покроковий алгоритм виконання:**
1. Виділіть головну тезу (Central Claim) статті.
2. Знайдіть фактичні дані та метрики (Grounds), на які спирається автор (вартість інфраструктури, кількість інженерів).
3. Визначте приховану підставу (Warrant): за яких умов та розміру бізнесу цей висновок працює.
4. Знайдіть логічні застереження (Rebuttals): для яких типів додатків відмова від Kubernetes призведе до катастрофи.

**Рекомендований системний AI-промпт:**
```text
Дій як Principal Systems Analyst. Проведи аналіз статті за моделлю аргументації Стівена Тулміна:
Теза автора: 'Kubernetes — це надмірна складність для 90% компаній, ми перейшли на Hetzner bare-metal і заощадили $100k/місяць'.
Вимоги:
1. Заповни всі 6 блоків моделі Тулміна:
   - Claim (Головне твердження)
   - Grounds / Data (Наведені емпіричні факти)
   - Warrant (Логічний місток)
   - Backing (Фундаментальне обґрунтування)
   - Qualifier (Ступінь упевненості)
   - Rebuttal (Умови, за яких цей аргумент розсипається)
2. Вкажи, чи містить стаття логічну помилку узагальнення (Hasty Generalization).
```

**Очікуваний результат:**
Структурована аналітична модель аргументації у форматі Markdown із критичними висновками.

**Критерії самоперевірки та оцінювання:**
- [ ] Повне заповнення всіх 6 компонентів моделі Тулміна
- [ ] Точне відокремлення фактів економії від суб'єктивних емоцій автора
- [ ] Чітко сформульовані умови Rebuttal (де Kubernetes безальтернативний)
- [ ] Виявлення прихованих упереджень автора

## Завдання 2: Побудова AI-пайплайну екстракції семантичних фактів у формат JSON

**Мета:** Навчитись формулювати системні промпти для витягування структурованих фактів (Суб'єкт-Дія-Об'єкт-Метрика) з неструктурованого тексту.

**Вхідний контекст та бізнес-сценарій:**
Необхідно автоматизувати аналіз 50 публічних звітів про інциденти інформаційної безпеки (Post-Mortem reports). Потрібно витягувати факти: назву компанії, тривалість простою, причину збою та фінансові втрати.

**Покроковий алгоритм виконання:**
1. Складіть JSON-схему для фіксації структурованого факту про інцидент.
2. Напишіть системний промпт для LLM з нульовою толерантністю до галюцинацій (strict extraction).
3. Протестуйте промпт на фрагменті опису глобального збою Cloudflare або AWS.
4. Опишіть валідацію числових полів на відповідність типам даних.

**Рекомендований системний AI-промпт:**
```text
Дій як Knowledge Engineering Specialist. Створи системний промпт для витягування фактів із технічних звітів Post-Mortem:
Вимоги до JSON-схеми вихідних даних:
- incident_date: ISO рядок або null
- target_system: назва системи/сервісу
- duration_minutes: ціле число або null
- root_cause_category: enum [BGP_ROUTING, DNS_FAILURE, CODE_BUG, HARDWARE_CRASH, HUMAN_ERROR]
- root_cause_description: лаконічний факт (до 15 слів)
- estimated_loss_usd: числове значення або null
- source_confidence: high / medium / low
Напиши системний промпт, який суворо забороняє додумування відсутніх чисел і вимагає прямого цитування.
```

**Очікуваний результат:**
Документ із готовим системним промптом, валідною JSON-схемою та зразком витягнутого факту.

**Критерії самоперевірки та оцінювання:**
- [ ] Повна строгість типів у схемі JSON
- [ ] Заборона галюцинацій та підстановки фіктивних значень
- [ ] Категоризація першопричин за стандартизованим enum
- [ ] Готовність промпту до промислової інтеграції в API пайплайн
