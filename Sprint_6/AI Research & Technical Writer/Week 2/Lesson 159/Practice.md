# Практичні завдання до Уроку 159: Побудова структурованих нотаток

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Трансформація неструктурованого конспекту технічного мітингу у формат Architecture Decision Record (ADR)

**Мета:** Опанувати перетворення хаотичних заміток зустрічі у стандартизований інженерний документ прийняття рішень.

**Вхідний контекст та бізнес-сценарій:**
Відбулася 2-годинна гаряча дискусія розробників щодо переходу з REST на gRPC для внутрішніх мікросервісів. Є сирий запис чату з тезами та суперечками. Необхідно створити структурований документ ADR за шаблоном Майкла Найгарда.

**Покроковий алгоритм виконання:**
1. Виділіть статус документа: Пропоновано, Прийнято, Відхилено.
2. Сформулюйте бізнес- та технічний контекст (проблема затримок серіалізації JSON у REST).
3. Опишіть прийняте рішення (впровадження gRPC та Protobuf для внутрішніх сервісів, збереження REST для публічного API).
4. Зафіксуйте наслідки (Consequences): позитивні (скорочення затримок на 60%) та негативні (складність налагодження через Postman).
5. Складіть перелік Action Items із виконавцями.

**Рекомендований системний AI-промпт:**
```text
Дій як Staff Technical Writer & System Architect. Опрацюй сирі нотатки інженерної дискусії:
[Нотатки: обговорювали REST vs gRPC; бекендери скаржаться на оверхед JSON; DevOps каже треба міняти налаштування балансувальника Nginx; домовилися що публічне API лишається REST, а бекенд-сервіси переходять на gRPC; Іван робить PoC до п'ятниці, Олена оновлює Protobuf схеми].
Склади офіційний Architecture Decision Record (ADR-004) за стандартом:
1. Title: ADR-004: Вибір gRPC для міжсервісної комунікації
2. Status: Accepted
3. Context: проблема та технічні обмеження
4. Decision: точне формулювання вибору
5. Consequences: позитивні та компроміси (Positive & Trade-offs)
6. Action Items: конкретні задачі, виконавці, терміни.
```

**Очікуваний результат:**
Повноцінний файл `ADR-004.md` за промисловим стандартом Майкла Найгарда.

**Критерії самоперевірки та оцінювання:**
- [ ] Суворе дотримання структури ADR
- [ ] Чіткий баланс технічних наслідків та компромісів (Trade-offs)
- [ ] Висока інформаційна щільність без розмовного сленгу
- [ ] Вимірювані Action Items із дедлайнами

## Завдання 2: Побудова атомарної мережі карток за методом Zettelkasten

**Мета:** Навчитись декомпозувати складну статтю на три взаємопов'язані атомарні нотатки з Wikilinks.

**Вхідний контекст та бізнес-сценарій:**
Ви прочитали розділ книги про розподілені системи та теорему CAP. Необхідно створити три взаємопов'язані атомарні нотатки у форматі Markdown для персональної бази знань.

**Покроковий алгоритм виконання:**
1. Створіть нотатку 1: 'Теорема CAP стверджує неможливість одночасної узгодженості та доступності при розділенні мережі.md'.
2. Створіть нотатку 2: 'PACELC теорема розширює CAP врахуванням затримок у нормальному стані системи.md'.
3. Створіть нотатку 3: 'Eventual Consistency забезпечує доступність ціною тимчасової розбіжності даних.md'.
4. Пов'яжіть нотатки між собою за допомогою перехресних двосторонніх посилань `[[Назва нотатки]]`.

**Рекомендований системний AI-промпт:**
```text
Дій як Knowledge Architect та майстер Zettelkasten. Створи 3 атомарні нотатки на тему розподілених баз даних:
Вимоги:
1. Кожна нотатка повинна мати заголовок-тезу (завершене твердження).
2. Обсяг кожної нотатки: 120-180 слів (атомарність, лише одна ключова думка).
3. Використовуй синтаксис посилань `[[Назва іншої нотатки]]` для зв'язування всіх трьох файлів у єдину смислову мережу.
4. Додай теги (#distributed-systems, #database-architecture).
5. Наведи короткий приклад конкретної бази даних (Cassandra, DynamoDB, CockroachDB) у відповідній нотатці.
```

**Очікуваний результат:**
Три зв'язані Markdown-нотатки з демонстрацією мережевого мислення та високої атомарності.

**Критерії самоперевірки та оцінювання:**
- [ ] Справжня атомарність кожної окремої картки
- [ ] Осмислене використання двосторонніх посилань [[...]]
- [ ] Лаконічні та точні технічні визначення з прикладами реальних СУБД
- [ ] Відповідність принципам побудови персональної бази знань Zettelkasten
