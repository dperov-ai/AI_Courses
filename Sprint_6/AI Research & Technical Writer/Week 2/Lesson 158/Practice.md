# Практичні завдання до Уроку 158: Класифікація інформації

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Розробка корпоративної політики безпекової класифікації даних (Data Classification Schema)

**Мета:** Навчитись створювати регламент класифікації інформації для IT-компанії за міжнародним стандартом ISO/IEC 27001.

**Вхідний контекст та бізнес-сценарій:**
Fintech-стартап готується до проходження аудиту SOC 2 Type II. Аудитор вимагає надати формальну 4-рівневу політику класифікації даних із чіткими прикладами та правилами обробки для інженерів, фінансистів та ейчарів.

**Покроковий алгоритм виконання:**
1. Визначте 4 рівні: Public, Internal, Confidential, Restricted.
2. Для кожного рівня сформулюйте чіткий критерій: який збиток завдасть компрометація даних.
3. Наведіть конкретні приклади технічних артефактів для кожного рівня (API keys, логи, вихідний код, резюме кандидатів).
4. Сформулюйте правила безпечного поводження: шифрування у спокої (At Rest), під час передачі (In Transit) та терміни зберігання.

**Рекомендований системний AI-промпт:**
```text
Дій як Chief Information Security Officer (CISO) & Technical Writer. Склади корпоративну матрицю класифікації інформації за стандартом ISO 27001 / SOC 2:
Структура документа:
1. Опис 4 рівнів секретності (Public, Internal, Confidential, Restricted).
2. Матриця у форматі Markdown таблиці:
   - Рівень секретності
   - Бізнес-визначення та критерій шкоди від витоку
   - Приклади артефактів розробки (код, кревеншели, дампи баз, дизайн-макети)
   - Вимоги до шифрування (TLS 1.3, AES-256)
   - Політика доступу (RBAC, MFA, доступ за запитом)
3. Правила маркування документів співробітниками (водяні знаки, мітки в заголовках).
```

**Очікуваний результат:**
Офіційна корпоративна політика класифікації даних у форматі Markdown таблиці та регламенту.

**Критерії самоперевірки та оцінювання:**
- [ ] Суворе дотримання вимог ISO 27001
- [ ] Реалістичні інженерні приклади артефактів для кожного рівня
- [ ] Конкретні технічні вимоги до криптографічного захисту
- [ ] Ясні та практичні правила маркування для співробітників

## Завдання 2: Створення промпту для автоматизованої мультилейбл-класифікації тікетів підтримки

**Мета:** Опанувати використання LLM для точного розподілу вхідних звернень за категоріями таксономії з оцінкою впевненості.

**Вхідний контекст та бізнес-сценарій:**
У службу підтримки щодня надходить 2 000 неструктурованих звернень клієнтів. Потрібно створити AI-класифікатор, який визначає функціональний модуль (Auth, Billing, Performance, Security) та рівень терміновості (P1-P4).

**Покроковий алгоритм виконання:**
1. Опишіть таксономію модулів та шкалу пріоритетів.
2. Складіть системний промпт для моделі з вимогою повернути суворий JSON.
3. Передбачте розрахунок Confidence Score та виділення ключових слів-тригерів.
4. Протестуйте промпт на 2 складних суперечливих прикладах звернень.

**Рекомендований системний AI-промпт:**
```text
Дій як Senior Machine Learning & Prompt Engineer. Створи системний промпт для автоматизованої класифікації звернень клієнтів у Jira Service Management:
Таксономія категорій:
- AUTHENTICATION (проблеми з паролями, 2FA, сесіями)
- BILLING_AND_PAYMENTS (списання, повернення коштів, рахунки-фактури)
- PERFORMANCE_BUG (повільна робота, таймаути, зависання)
- SECURITY_INCIDENT (підозрілі транзакції, фішинг, злам)
Пріоритети: CRITICAL (P1), HIGH (P2), MEDIUM (P3), LOW (P4).
Вимоги:
1. Модель повинна повертати виключно валідний JSON.
2. Обов'язкові поля: primary_category, secondary_categories (масив), priority, confidence_score (від 0.00 до 1.00), detected_language, routing_team.
3. Додай інструкцію: якщо в тексті є хоча б натяк на компрометацію паролів або злам — пріоритет автоматично стає CRITICAL.
```

**Очікуваний результат:**
Повноцінний виробничий системний промпт із валідною JSON-схемою та прикладом обробки тексту.

**Критерії самоперевірки та оцінювання:**
- [ ] Сувора типізація вихідного JSON без зайвого тексту моделі
- [ ] Чіткі правила підвищення пріоритету при безпекових інцидентах
- [ ] Наявність поля оцінки впевненості (Confidence Score)
- [ ] Підтримка мультилейбл класифікації
