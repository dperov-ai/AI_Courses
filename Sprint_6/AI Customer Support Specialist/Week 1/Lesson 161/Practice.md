# Практичні завдання до Уроку 161: Пошук у внутрішній документації

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Складання складних пошукових запитів у Confluence CQL для локалізації інциденту

**Мета:** Опанувати професійний пошуковий синтаксис (Булеві оператори, фільтри часу та просторів) для швидкого пошуку рішень.

**Вхідний контекст та бізнес-сценарій:**
У суботу ввечері користувачі масово скаржаться на помилку 'Error 403: Forbidden - IP Geoblocked'. Вам потрібно знайти актуальний регламент розблокування користувачів за останні 30 днів у просторі підтримки, відсіявши застарілу версію v1.

**Покроковий алгоритм виконання:**
1. Складіть базовий запит із точною фразою помилки.
2. Додайте фільтрацію за простором `SUP` та виключіть застаріле слово `legacy`.
3. Додайте умову оновлення документа за останні 30 днів.
4. Опишіть порядок перевірки знайденого регламенту на актуальність.

**Рекомендований системний AI-промпт:**
```text
Дій як Senior Technical Support Specialist. Склади 3 оптимізовані пошукові запити в корпоративній базі Confluence (CQL):
Кейс: Користувачі скаржаться на 'Account Suspended: Fraud Risk Score > 80'.
Вимоги:
1. Запит 1: Точний булевий пошук за фразою помилки з виключенням застарілих правил 2024 року.
2. Запит 2: CQL-запит із фільтром за простором 'FRAUD-OPS', наявністю тегу 'sop-active' та змінами за останні 14 днів.
3. Запит 3: Пошук інциденту в KEDB (Known Errors) за кодом помилки 'ERR-FR-802'.
Надай детальний коментар щодо кожного оператора.
```

**Очікуваний результат:**
Документ із трьома точними пошуковими запитами та інженерними поясненнями логіки фільтрації.

**Критерії самоперевірки та оцінювання:**
- [ ] Правильний синтаксис булевих операторів та лапок
- [ ] Валідний синтаксис Confluence Query Language (CQL)
- [ ] Точне відсікання застарілих даних
- [ ] Орієнтація на швидкість локалізації за умов SLA

## Завдання 2: Створення статті для Known Error Database (KEDB) за методологією KCS

**Мета:** Навчитись фіксувати нові технічні рішення та workarounds у корпоративній базі знань за стандартами ITIL.

**Вхідний контекст та бізнес-сценарій:**
Ви щойно вирішили складний кейс, де у клієнта не завантажувався звіт через конфлікт розширення AdBlock у Chrome. Цього дефекту ще немає в базі знань. Необхідно створити еталонну статтю для колег.

**Покроковий алгоритм виконання:**
1. Опишіть симптоми проблеми та оточення (версія ОС, браузер, розширення).
2. Зафіксуйте кореневу причину (блокування скрипту аналітики розширенням).
3. Складіть покроковий Workaround для клієнта (додавання сайту у винятки розширення).
4. Зазначте метадані статті: теги, статус, посилання на тікет у Jira.

**Рекомендований системний AI-промпт:**
```text
Дій як Knowledge Manager служби технічної підтримки. Склади статтю для внутрішньої бази KEDB (Known Error Database) у форматі Markdown:
Тема: 'Помилка завантаження PDF квитанцій у Chrome через блокувальники реклами'.
Структура статті:
1. Title & Metadata (ID статті, автор, статус 'Active', теги, лінк на баг-трекер Jira).
2. Симптоми та повідомлення про помилку (як це бачить клієнт).
3. Коренева причина (Root Cause — технічне пояснення для операторів).
4. Тимчасове рішення (Workaround — покрокова інструкція, яку можна скопіювати клієнту).
5. Перманентне виправлення (ETA релізу фіксу від розробників).
```

**Очікуваний результат:**
Професійно оформлена стаття KEDB за стандартом ITIL у форматі Markdown.

**Критерії самоперевірки та оцінювання:**
- [ ] Суворе дотримання структури KEDB / KCS
- [ ] Чітке розділення технічного контексту для оператора та зрозумілої інструкції для клієнта
- [ ] Наявність метаданих та статусу документа
- [ ] Висока практична цінність для колег першої лінії
