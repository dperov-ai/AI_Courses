## Завдання 1: Проєктування модульної архітектури Page Object та Component Object

**Мета:** Побудувати чисту архітектуру Page Object з виділенням повторюваного компонента навігаційної панелі на TypeScript.

**Вхідний контекст та бізнес-сценарій:**
У маркетплейсі є сторінка каталогу товарів та сторінка деталей товару. Обидві містять спільний Header з пошуком та кошиком. Необхідно створити архітектуру класів без дублювання коду.

**Покроковий алгоритм виконання:**
1. Створіть клас `HeaderComponent` з локаторами логотипу, пошуку та лічильника кошика.
2. Створіть клас `CatalogPage`, що включає в себе `HeaderComponent` та методи фільтрації товарів.
3. Напишіть тестовий файл, який використовує створені класи для виконання пошуку товару та перевірки результату.

**Рекомендований системний AI-промпт:**
```text
Дій як Principal SDET. Напиши повноцінну архітектуру POM на TypeScript для Playwright:
1. Клас `HeaderComponent`:
   - Локатор поля пошуку `getByPlaceholder('Пошук')`
   - Локатор іконки кошика з лічильником
   - Метод `search(query: string)`
2. Клас `CatalogPage`:
   - Включає екземпляр `HeaderComponent`
   - Метод `open()` -> перехід на /catalog
   - Метод `selectCategory(categoryName: string)`
   - Метод `getProductCount(): Promise<number>`
3. Тестовий файл `catalog.spec.ts`:
   - Ініціалізує CatalogPage
   - Виконує пошук через header
   - Перевіряє, що знайдено хоча б 1 товар.
```

**Очікуваний результат:**
Три файли або цілісний модуль TypeScript із чистим кодом та коментарями архітектурних рішень.

**Критерії самоперевірки та оцінювання:**
- [ ] Чітке розділення HeaderComponent та CatalogPage
- [ ] Правильна типізація Locator та Page
- [ ] Використання композиції (компонент всередині сторінки)
- [ ] Коректний тестовий сценарій без прямих технічних селекторів

## Завдання 2: Рефакторинг неструктурованого тесту в Page Object патерн

**Мета:** Навчитись виділяти бізнес-дії та локатори з заплутаного тесту в компактний клас сторінки оформлення замовлення.

**Вхідний контекст та бізнес-сценарій:**
Тест оформлення замовлення містить 40 рядків імперативних викликів `page.locator(...)`, `page.click(...)`. Його складно читати та підтримувати.

**Покроковий алгоритм виконання:**
1. Виділіть усі елементи форми (ПІБ, телефон, адреса доставки, спосіб оплати) у клас `CheckoutPage`.
2. Створіть інтерфейс `OrderDetails` для типізації вхідних даних замовлення.
3. Реалізуйте високорівневий метод `fillOrderForm(details: OrderDetails)`.
4. Перепишіть тестовий сценарій, зменшивши його до 5 рядків зрозумілого бізнес-коду.

**Рекомендований системний AI-промпт:**
```text
Дій як Lead QA Automation Engineer. Перетвори наступний імперативний код у Page Object:
[Код містить кліки по 5 інпутах, вибір радіокнопки 'Кур'єр', введення адреси та клік 'Оформити'].
Вимоги:
1. Створи файл `CheckoutPage.ts` з інтерфейсом `OrderCustomerData`.
2. Створи метод `submitOrder(data: OrderCustomerData)`.
3. Напиши чистий тест `checkout.spec.ts` з використанням нового класу.
```

**Очікуваний результат:**
Оновлений типізований клас CheckoutPage та лаконічний тестовий сценарій.

**Критерії самоперевірки та оцінювання:**
- [ ] Використання інтерфейсу TypeScript для даних замовлення
- [ ] Інкапсуляція всіх кроків форми в один високорівневий метод
- [ ] Зменшення розміру тесту без втрати покриття
- [ ] Web-first перевірка фінального екрана успіху в тілі тесту
