# Контрольні запитання до Уроку 147: Fixtures та reusable components

Даний блок містить перелік аналітичних та практичних запитань для самоконтролю, перевірки глибини засвоєння матеріалу та підготовки до технічних інтерв’ю.

---

### 1. Чим концепція Test Fixtures у Playwright перевершує класичні хуки `beforeEach` / `afterEach`?

**Відповідь:** Фікстури підтримують Dependency Injection, активуються лише на вимогу тесту (On-Demand), інкапсулюють Setup та Teardown в одному місці та гарантують виконання очищення навіть при падінні тесту.

---

### 2. Що робить функція `use()` всередині оголошення кастомної фікстури?

**Відповідь:** Вона передає ініціалізований ресурс у функцію тіла тесту та призупиняє виконання фікстури. Після завершення тесту виконання продовжується з рядка після `use()` для виконання Teardown.

---

### 3. Які переваги надає використання фікстури `request` порівняно зі взаємодією через UI?

**Відповідь:** Дозволяє виконувати прямі HTTP-запити до API за мілісекунди без запуску вікна браузера, що ідеально підходить для швидкої підготовки тестових даних та авторизації.

---

### 4. У чому різниця між `scope: 'test'` та `scope: 'worker'` у фікстурах?

**Відповідь:** `scope: 'test'` створює новий екземпляр ресурсу для кожного тесту окремо, а `scope: 'worker'` ініціалізує ресурс один раз для всього паралельного процесу (воркера) і перевикористовує його.

---

### 5. Як Playwright визначає, які саме фікстури потрібно запустити для конкретного тесту?

**Відповідь:** Playwright аналізує сигнатуру параметрів тесту (деструктуризацію об'єкта) та запускає лише ті фікстури, які були явно запрошені.

---

### 6. Що станеться з кодом після `await use()`, якщо в тесті впаде асерт?

**Відповідь:** Код після `use()` (блок Teardown) все одно обов'язково виконається, що гарантує захист від витоку ресурсів та збереження чистоти тестової бази.

---

### 7. Як об'єднати використання Page Object Model із фікстурами Playwright?

**Відповідь:** Створити кастомну фікстуру для кожної сторінки, яка створює екземпляр Page Object, викликає метод переходу і передає готовий об'єкт у тест.

---

### 8. Чи можуть фікстури залежати від інших фікстур (Fixture Composition)?

**Відповідь:** Так, фікстура може приймати інші фікстури у своєму списку аргументів (наприклад, фікстура `adminPage` залежить від `page` та `adminCredentials`).

---

### 9. Як передати конфігураційні параметри у фікстуру з `playwright.config.ts`?

**Відповідь:** Оголосити опцію у фікстурі за допомогою `base.extend<{ myOption: string }>({ myOption: ['default', { option: true }] })`.

---

### 10. Що таке авто-фікстури (Automatic Fixtures: `{ auto: true }`)?

**Відповідь:** Це фікстури, які автоматично запускаються для кожного тесту без необхідності явного вказування їх у параметрах тесту (наприклад, для глобального моніторингу консольних помилок).

---

### 11. Як за допомогою фікстури автоматично блокувати виклики сторонньої аналітики у всіх тестах?

**Відповідь:** Створити авто-фікстуру, яка викликає `await page.route('**/*google-analytics.com/**', route => route.abort())` перед виконанням тесту.

---

### 12. Як організувати спільне сховище для фікстур у великій команді?

**Відповідь:** Винести визначення спільних фікстур в окремий модуль (наприклад, `@mycompany/test-fixtures`), який імпортується усіма тестовими специфікаціями.

---

### 13. Як передати стан сесії авторизації через фікстури без використання форми входу на UI?

**Відповідь:** Зберегти токен або файл `storageState` на рівні воркера або глобального сетапу та підключити його до контексту через фікстуру.

---

### 14. Як типізувати об'єкт кастомних фікстур у TypeScript?

**Відповідь:** Визначити TypeScript `type` або `interface`, де ключами є назви фікстур, а значеннями — їхні типи, та передати його в `base.extend<MyType>()`.

---

### 15. Чи можна перевизначати стандартні фікстури (наприклад, `page`) своїми власними?

**Відповідь:** Так, Playwright дозволяє перевизначати навіть базові фікстури (наприклад, автоматично додавати логування або кастомні заголовки до `page`).

---

### 16. Як перевірити наявність помилок у браузерній консолі за допомогою авто-фікстури?

**Відповідь:** Підписатися на `page.on('console', msg => ...)` та `page.on('pageerror', err => ...)` у сетапі фікстури, а в блоці після `use()` перевірити відсутність зібраних помилок.

---

### 17. Як організувати створення унікальних користувачів для паралельних тестів через фікстури?

**Відповідь:** Викликати внутрішнє API генерації користувача з унікальним email (наприклад, `user-${Date.now()}@test.internal`) всередині фікстури перед викликом `use()`.

---

### 18. Чому фікстури кращі за глобальні змінні у тестових файлах?

**Відповідь:** Глобальні змінні створюють небезпеку взаємного впливу тестів при паралельному виконанні, тоді як фікстури забезпечують строгу ізоляцію стану.

---

### 19. Як AI допомагає проєктувати архітектуру фікстур для складних бізнес-додатків?

**Відповідь:** AI аналізує повторювані блоки `beforeEach` у застарілих тестах та автоматично генерує чисті, типізовані фікстури з відповідними Setup/Teardown блоками.

---

### 20. Які помилки найчастіше виникають при неправильному використанні фікстур?

**Відповідь:** Забування виклику `await use()`, розміщення важкої ініціалізації в test scope замість worker scope, або спроба доступу до даних фікстури поза межами тесту.

---
