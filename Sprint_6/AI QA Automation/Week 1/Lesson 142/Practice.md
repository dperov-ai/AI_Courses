# Практичні завдання до Уроку 142: Playwright як інструмент UI Automation

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Створення базового проєкту Playwright та конфігурація мультибраузерного середовища

**Мета:** Розгорнути структуру проєкту Playwright з конфігурацією Chromium, Firefox, WebKit та налаштуванням звітів.

**Вхідний контекст та бізнес-сценарій:**
Ви створюєте новий репозиторій автоматизації тестування для платформи електронної комерції. Потрібно створити виробничу конфігурацію `playwright.config.ts` з підтримкою різних середовищ та збору трейсів при падіннях.

**Покроковий алгоритм виконання:**
1. Створіть файл конфігурації `playwright.config.ts`.
2. Налаштуйте підтримку трьох браузерів (Chromium, Firefox, WebKit) та одного мобільного профілю.
3. Налаштуйте створення HTML-звіту та збереження артефактів (відео, скріншоти, трасування) лише при падінні тестів.
4. Напишіть базовий перевірочний тест доступності головної сторінки.

**Рекомендований системний AI-промпт:**
```text
Дій як Lead QA Automation Engineer. Створи файл `playwright.config.ts` для корпоративного проєкту з такими вимогами:
1. Базовий URL береться зі змінної оточення BASE_URL або за замовчуванням 'https://ecommerce-staging.internal'.
2. Таймаут тесту: 30 секунд, таймаут асерту: 5 секунд.
3. Увімкнений збір trace, screenshot та video ТІЛЬКИ при падінні тесту.
4. Налаштовано 4 проекти: Desktop Chrome, Desktop Firefox, Desktop Safari (WebKit) та Mobile Safari (iPhone 14).
5. Налаштовано HTML та List репортери.
Додай також один приклад тесту на TypeScript, що перевіряє title сторінки.
```

**Очікуваний результат:**
Повністю валідний конфігураційний файл `playwright.config.ts` та приклад тесту з коментарями щодо кожного параметра.

**Критерії самоперевірки та оцінювання:**
- [ ] Коректний синтаксис defineConfig з імпортом devices
- [ ] Правильне налаштування збору артефактів за умовою падіння
- [ ] Наявність усіх чотирьох зазначених проєктів браузерів
- [ ] Чітка типізація TypeScript без синтаксичних помилок

## Завдання 2: Дослідження роботи Trace Viewer та аналіз падіння тесту

**Мета:** Навчитись ініціалізувати збір трасувальних файлів, аналізувати стек падіння та діагностувати помилки через Trace Viewer.

**Вхідний контекст та бізнес-сценарій:**
Тест перевірки кошика періодично падає у нічному прогоні через появу акційного банера, що перекриває кнопку оформлення замовлення. Необхідно зафіксувати це падіння у трейсі та усунути причину.

**Покроковий алгоритм виконання:**
1. Напишіть тест, що симулює перекриття кнопки модальним вікном.
2. Запустіть тест із прапорцем створення трейсу `--trace on`.
3. Опишіть кроки відкриття та аналізу отриманого файлу `trace.zip` через `npx playwright show-trace`.
4. Модифікуйте тест, додавши перевірку або закриття блокуючого модального вікна перед кліком.

**Рекомендований системний AI-промпт:**
```text
Дій як Senior SDET. Поясни покроково, як локалізувати дефект, коли кнопка 'Оформити замовлення' перекрита спливаючим вікном розсилки (Promo Pop-up):
1. Напиши тест на Playwright, де відбувається дія над елементом.
2. Опиши команду терміналу для відкриття Trace Viewer для впалого тесту.
3. Перелічи, які саме вкладки Trace Viewer (Action, Console, Network, Metadata) дозволяють переконатися, що клік не відбувся саме через перекриття елемента (Obscured).
4. Напиши виправлений варіант тесту, який перевіряє наявність модального вікна та закриває його перед продовженням.
```

**Очікуваний результат:**
Детальний інженерний гайд із виправленим тестовим сценарієм та алгоритмом діагностики у Trace Viewer.

**Критерії самоперевірки та оцінювання:**
- [ ] Зрозумілий опис аналізу вкладки DOM Snapshot у Trace Viewer
- [ ] Коректна обробка закриття модального вікна без жорстких пауз
- [ ] Правильний синтаксис команди перегляду трейсу
- [ ] Використання семантичних локаторів Playwright
