# Практичні завдання до Уроку 141: Основи автоматизації Web UI

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Архітектурний аудит та побудова матриці покриття Web UI тестами

**Мета:** Навчитись аналізувати функціональні сценарії вебзастосунку та обирати оптимальний рівень автоматизації згідно з пірамідою тестування.

**Вхідний контекст та бізнес-сценарій:**
Ви SDET у фінтех-продукті «NovaPay». Команда готує новий функціонал: миттєві перекази між картками з 3D-Secure верифікацією та формуванням PDF-квитанції. Керівництво наполягає на покритті 100% дій через Web UI. Вам необхідно запропонувати збалансовану піраміду тестування.

**Покроковий алгоритм виконання:**
1. Проаналізуйте функціональний потік: Авторизація -> Введення реквізитів картки -> Перевірка комісії -> 3D-Secure OTP -> Відображення успіху -> Завантаження квитанції.
2. Розподіліть перевірки між рівнями: Unit, API/Integration та E2E Web UI.
3. Складіть перелік із 3 критичних наскрізних сценаріїв, які обов'язково мають бути покриті саме через Web UI.
4. Опишіть стратегію ізоляції тестових даних та мокування стороннього платіжного шлюзу 3D-Secure для запобігання нестабільності тестів.

**Рекомендований системний AI-промпт:**
```text
Дій як Principal SDET. Розглянь функціональний сценарій грошового переказу у фінтех-додатку.
Склади інженерний план покриття тестами за пірамідою Майка Кона:
1. Визнач, які валідації (формат номера картки, ліміти, розрахунок відсотків) мають бути винесені в Unit та API тести.
2. Сформулюй 3 еталонні E2E UI-сценарії за структурою Given-When-Then.
3. Опиши стратегію мокування (Mocking) для стороннього сервісу 3DSecure банків-емітентів у тестах Playwright.
```

**Очікуваний результат:**
Документ із декомпозицією тестового покриття, матрицею розподілу перевірок та описом 3 E2E сценаріїв із зазначенням точок інтеграції та моків.

**Критерії самоперевірки та оцінювання:**
- [ ] Чіткий розподіл валідацій між рівнями без дублювання на UI
- [ ] 3 критичні E2E сценарії покривають виключно бізнес-поведінку користувача
- [ ] Обґрунтовано використання API-передумов для підготовки балансу замість ручного клікання
- [ ] Описано стратегію запобігання Flakiness при взаємодії з OTP-кодами

## Завдання 2: Створення першого надійного UI-тесту за патерном AAA на Playwright

**Мета:** Закріпити на практиці структуру Arrange-Act-Assert та роботу з семантичними локаторами Playwright.

**Вхідний контекст та бізнес-сценарій:**
Необхідно автоматизувати форму авторизації вебзастосунку з валідацією успішного входу та перевіркою появи повідомлення про некоректний пароль.

**Покроковий алгоритм виконання:**
1. Ініціалізуйте тестовий файл Playwright на TypeScript.
2. Реалізуйте позитивний тест авторизації за структурою AAA з використанням локаторів getByRole та getByLabel.
3. Реалізуйте негативний тест із перевіркою відображення повідомлення про помилку валідації.
4. Використайте Web-first assertions для очікування стану елементів.

**Рекомендований системний AI-промпт:**
```text
Дій як Senior SDET. Напиши два автотести на TypeScript для Playwright (позитивний та негативний вхід у систему):
URL: https://demo-bank.internal/login
Елементи: поле Email, поле Password, кнопка 'Увійти', повідомлення про помилку 'Невірний логін або пароль', аватар користувача з іменем у хедері після успішного входу.
Вимоги:
1. Суворе дотримання коментарів Arrange, Act, Assert.
2. Використання семантичних локаторів getByRole, getByLabel.
3. Використання expect(locator).toBeVisible() або expect(locator).toHaveText().
```

**Очікуваний результат:**
Чистий, типізований TypeScript-файл із двома тестами, готовий до виконання у тестовому ранері Playwright.

**Критерії самоперевірки та оцінювання:**
- [ ] Код скомпільований без помилок типізації TypeScript
- [ ] Повна відсутність жорстких затримок waitForTimeout
- [ ] Використано семантичні локатори відповідно до стандартів W3C WAI-ARIA
- [ ] Наявні чіткі асерти для позитивного та негативного стану
