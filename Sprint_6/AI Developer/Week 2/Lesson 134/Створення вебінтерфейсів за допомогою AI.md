# Урок 134: Створення вебінтерфейсів за допомогою AI

## Вступ: Нова ера Generative UI та AI-Augmented розробки

Поява великих мультимодальних моделей (LLM) трансформувала індустрію створення вебінтерфейсів. Те, що раніше вимагало тижнів кропіткої верстки від дизайнера до верстальника і фронтенд-розробника, сьогодні створюється за хвилини завдяки концепції **Generative UI** та інтелектуальним середовищам розробки (Cursor, Windsurf, v0.dev, Claude 3.5 Sonnet, GitHub Copilot).

Проте штучний інтелект не замінює інженера — він підсилює його. Без глибокого розуміння семантики, CSS-каскаду, патернів реактивності, продуктивності та безпеки неконтрольований AI-генерований код швидко перетворюється на непідтримуване "сміттєзвалище" (Legacy Code), переповнене антипатернами, вразливостями та проблемами з доступністю.

Мета цього уроку — опанувати системну інженерну методологію розробки інтерфейсів за допомогою AI: від промпт-інжинірингу для UI та підходу "Image-to-Code" до налаштування `.cursorrules`, автоматичного аудиту згенерованого коду та інтеграції готових компонентів у реальні виробничі проєкти.

## 3. Методологія Image-to-Code: перетворення макетів у код

Сучасні мультимодальні моделі чудово інтерпретують візуальні зображення (скріншоти з Dribbble, Figma або намальовані від руки скетчі):

```
[Скріншот макета Figma]
           │
           ▼
[AI Vision: аналіз геометрії, кольорів, відступів та шрифтової ієрархії]
           │
           ▼
[Складання плану декомпозиції (Tree of Components)]
           │
           ▼
[Генерація коду розмітки та стилів (Tailwind / Flexbox)]
           │
           ▼
[Експертний інженерний аудит: заміна фіксованих пікселів на rem, додавання a11y]
```

### Пастки Image-to-Code та як їх виправляти:
1. **Хардкод розмірів**: AI часто генерує жорсткі значення `w-[342px]` замість гнучких `w-full max-w-md`. *Рішення*: Явно вказувати у промпті вимогу адаптивності без фіксованої ширини.
2. **Пропуск інтерактивних станів**: На картинці зображено лише статичний вигляд. AI за замовчуванням забуває про `:hover`, `:focus-visible`, `:active` та `:disabled`. *Рішення*: Вимагати генерації повної матриці станів.
3. **Використання растрових картинок замість SVG-іконок**: AI може спробувати вставити випадкові посилання на `unsplash.com`. *Рішення*: Вимагати використання векторних іконок з бібліотеки `lucide-react`.

## 4. Конфігурація середовища розробки: Файл `.cursorrules`

Файл `.cursorrules` у корені репозиторію — це інженерний інструмент, що змушує AI автоматично слідувати стилю вашої команди у кожній відповіді:

```markdown
# .cursorrules для Frontend Проєкту

## Стек технологій
- Next.js 15 (App Router), React 19, TypeScript (строгий режим).
- Стилізація: Tailwind CSS v4, бібліотека іконок Lucide-react.
- Управління формами: React Hook Form + Zod.

## Правила кодування
- Завжди використовувати функціональні компоненти з явною типізацією Props.
- Заборонено використовувати будь-які типи `any` або `@ts-ignore`.
- Компоненти повинні бути строго розділені за Atomic Design.
- Доступність: усі інтерактивні елементи обов'язково мають `aria-label` або видимий текст.
- Стилізація: ніколи не писати інлайн-стилі через атрибут `style=`.
- Адаптивність: підхід Mobile-First (базові класи без префіксів, далі `sm:`, `md:`, `lg:`).
```

## 5. Безпека та контроль якості AI-згенерованого UI

Інженер зобов'язаний проводити ретельне рев'ю згенерованого коду за наступним чеклистом:

| Вектор перевірки | Що шукати в коді AI | Потенційний ризик |
| :--- | :--- | :--- |
| **XSS-вразливості** | Використання `dangerouslySetInnerHTML`, конкатенація HTML | Впровадження зловмисного коду через користувацькі дані |
| **Витоки пам'яті** | Неочищені таймери `setInterval`, слухачі подій без `removeEventListener` у `useEffect`| Зависання вкладки браузера користувача |
| **Доступність (a11y)**| `div` з обробником `onClick` без `role="button"` та `tabIndex` | Неможливість користуватися сайтом людям з вадами зору |
| **Продуктивність** | Важкі обчислення всередині рендера без `useMemo`, відсутність virtual scroll | Падіння FPS та зависання сторінки на великих списках |
| **SEO-проблеми** | Відсутність тегів `<h1>`, пусті атрибути `alt` у картинок | Погіршення позицій сайту в пошукових системах |

## Практичний інженерний розбір: Реальний індустріальний кейс

Розглянемо практичний сценарій розгортання та оптимізації компонента у високонавантаженій системі (наприклад, платіжний віджет інтернет-банкінгу, що обслуговує понад 200 000 користувачів одночасно):

### 1. Архітектурне проєктування
1. **Ізоляція стану**: Відмова від глобального монолітного стану на користь локалізованих реактивних примітивів (Signals або легкі стори Zustand). Це запобігає каскадним ре-рендерам сусідніх дерев компонентів.
2. **Мережева оптимізація**: Реалізація механізму кешування запитів із заголовком `stale-while-revalidate`. Користувач миттєво бачить збережені дані з локального кешу, поки у фоновому потоці асинхронно відбувається оновлення стану через API.
3. **Обробка крайових випадків**: Реалізація відмовостійкості на рівні інтерфейсу (Graceful Degradation): при втраті зв'язку з бекендом формується офлайн-черга запитів у IndexedDB з автоматичною синхронізацією при відновленні мережі (Background Sync API).

### 2. Приклад коду виробничого рівня: Відмовостійкий клієнтський компонент
```typescript
// Production-Ready Component with AbortController, Error Boundary & Accessibility
import React, { useState, useEffect, useRef } from 'react';

interface DataState<T> {
  data: T | null;
  isLoading: boolean;
  error: Error | null;
}

export function ResilientWidget<T>({ endpoint, title }: { endpoint: string; title: string }) {
  const [state, setState] = useState<DataState<T>>({ data: null, isLoading: true, error: null });
  const abortControllerRef = useRef<AbortController | null>(null);

  useEffect(() => {
    abortControllerRef.current = new AbortController();
    
    async function fetchData() {
      try {
        setState(prev => ({ ...prev, isLoading: true, error: null }));
        const response = await fetch(endpoint, {
          signal: abortControllerRef.current?.signal,
          headers: { 'Accept': 'application/json' }
        });
        
        if (!response.ok) {
          throw new Error(`HTTP помилка: статус ${response.status}`);
        }
        
        const payload = await response.json();
        setState({ data: payload, isLoading: false, error: null });
      } catch (err: any) {
        if (err.name !== 'AbortError') {
          setState({ data: null, isLoading: false, error: err });
        }
      }
    }

    fetchData();

    return () => {
      abortControllerRef.current?.abort();
    };
  }, [endpoint]);

  if (state.isLoading) {
    return (
      <div role="status" aria-live="polite" className="animate-pulse p-4 rounded-lg bg-slate-100 dark:bg-slate-800">
        <div className="h-4 bg-slate-300 dark:bg-slate-700 rounded w-3/4 mb-2"></div>
        <div className="h-3 bg-slate-200 dark:bg-slate-600 rounded w-1/2"></div>
        <span className="sr-only">Завантаження даних віджета...</span>
      </div>
    );
  }

  if (state.error) {
    return (
      <div role="alert" className="p-4 border-l-4 border-red-500 bg-red-50 dark:bg-red-950 text-red-700">
        <h3 className="font-semibold">Помилка відображення</h3>
        <p className="text-sm">{state.error.message}</p>
      </div>
    );
  }

  return (
    <section aria-label={title} className="p-4 rounded-xl border border-slate-200 shadow-sm">
      <h2 className="text-lg font-bold mb-3">{title}</h2>
      <pre className="text-xs bg-slate-50 p-2 rounded overflow-x-auto">
        {JSON.stringify(state.data, null, 2)}
      </pre>
    </section>
  );
}
```


## Поглиблений архітектурний практикум: Побудова масштабованих вебінтерфейсів

У сучасній enterprise-розробці створення компонентів та сторінок вимагає суворого дотримання інженерних принципів стійкості, безпеки та продуктивності. Розглянемо детальний архітектурний конвеєр:

```
[Бізнес-вимоги / Дизайн-макет]
             │
             ▼
[Декомпозиція на ізольовані компоненти (Atomic Design)]
             │
             ▼
[Формування контрактів даних (TypeScript Interfaces / Zod Schemas)]
             │
             ▼
[Управління станом: Local State vs Global Store vs Server Cache]
             │
             ▼
[Оптимізація рендерингу (Virtual DOM / Reconciliation / Memoization)]
             │
             ▼
[Аудит доступності (WAI-ARIA, Keyboard Navigation, WCAG 2.1 AA)]
             │
             ▼
[Інтеграційне та E2E тестування (Playwright / Vitest)]
```

### Комплексна інженерна матриця валідації та оптимізації

| Вектор інженерного контролю | Критичні фактори ризику | Стандарти та патерни вирішення | Інструменти автоматизації |
| :--- | :--- | :--- | :--- |
| **Продуктивність (Web Vitals)** | Великий розмір бандла, зайві ре-рендери, високий CLS | Code Splitting (`React.lazy`), Dynamic Imports, Virtualization | Lighthouse, WebPageTest, Bundle Analyzer |
| **Доступність (Accessibility)** | Відсутність клавіатурного фокусу, несемантичні теги | WAI-ARIA, семантичні теги HTML5, видимі `:focus-visible` | Axe DevTools, Screen Readers (NVDA/VoiceOver) |
| **Безпека (Application Sec)** | XSS-ін'єкції, витік чутливих токенів у LocalStorage | Строгий CSP, HttpOnly Cookies, екранування даних | OWASP ZAP, Snyk, SonarQube |
| **Стійкість до помилок** | Падіння всього застосунку через збій у дочірньому блоці | Error Boundaries, Fallback UI, Graceful Degradation | Sentry, Datadog |
| **Типобезпека** | Runtime-помилки типу `undefined is not a function` | Строгий режим TypeScript (`strict: true`), валідація Zod | TypeScript Compiler (tsc), ESLint |

### Типові антипатерни веб-розробки та стратегії їх ліквідації:
1. **Антипатерн «Props Drilling через 10 рівнів»**:
   - *Проблема*: Передача параметрів через десятки проміжних компонентів, які їх не використовують, що руйнує модульність.
   - *Вирішення*: Використання компонентної композиції (`children`), React Context API або легких менеджерів стану (Zustand).
2. **Антипатерн «Некерований мутуючий стан»**:
   - *Проблема*: Пряма зміна об'єктів або масивів стану в обхід імутабельних методів, що ламає механізм виявлення змін рушія рендерингу.
   - *Вирішення*: Використання методів копіювання (`spread operator`, `structuredClone`) або бібліотеки Immer.
3. **Антипатерн «Блокуючі синхронні розрахунки в головному потоці»**:
   - *Проблема*: Виконання важкої фільтрації масивів чи парсингу великих JSON-файлів у Call Stack, що заморожує анімації та взаємодію на 500+ мс.
   - *Вирішення*: Винесення розрахунків у Web Workers або чанкінг через `requestIdleCallback` / `scheduler.yield()`.


## Фундаментальний аналіз архітектурних патернів веб-розробки

Для створення надійних систем інженер повинен володіти передовими концепціями побудови інтерфейсів та оптимізації рендерингу:

### 1. Механізми оптимізації пам'яті та Garbage Collection у браузері
Браузерний рушій V8 використовує генераційний збирач сміття (Generational Garbage Collector):
- **New Space (Scavenge)**: Область пам'яті для короткоживучих об'єктів (локальні змінні функцій, тимчасові проміси). Очищується за частки мілісекунди.
- **Old Space (Mark-Sweep-Compact)**: Довгоживучі об'єкти (глобальні стори, синглтони). Повне очищення (Major GC) вимагає зупинки виконання коду (Stop-the-world).
- **Витоки пам'яті (Memory Leaks)**: Виникають через забуті підписки на події `window.addEventListener`, замикання, що утримують посилання на видалені DOM-вузли (Detached DOM Elements), та неконтрольоване зростання кешів.

### 2. Стратегії ізоляції коду та безпечного виконання
- **Sandboxing в iframe**: Використання атрибутів `sandbox="allow-scripts"` для запуску ненадійного стороннього коду без доступу до cookies батьківського вікна.
- **Subresource Integrity (SRI)**: Хешування зовнішніх CDN-скриптів (`integrity="sha384-..."`), що запобігає атакам підміни коду на зламаних сторонніх серверах.


## Інженерні стандарти виробничого коду (Production Standards)

При підготовці коду компонентів та сторінок до розгортання в продакшн-середовищі інженер зобов'язаний дотримуватися наступних обов'язкових критеріїв:

### 1. Стратегія тестування інтерфейсу (Testing Pyramid)
- **Unit Tests (Модульні тести)**: Тестування ізольованих чистих функцій, кастомних хуків та утиліт валідації (покриття > 85%).
- **Component Tests (Компонентні тести)**: Перевірка візуалізації станів, коректності відпрацювання подій кліку та клавіатури через React Testing Library або Vitest.
- **End-to-End Tests (Наскрізні тести)**: Автоматизовані сценарії на базі Playwright, що емулюють реальні дії користувача від входу до фінальної дії.

### 2. Чеклист готовності до продакшн-релізу (Production Readiness Checklist):
- [ ] Оптимізація зображень (WebP/AVIF, lazy loading, правильні атрибути width/height)
- [ ] Мінімізація впливу сторонніх скриптів на метрики Core Web Vitals (LCP, FID/INP, CLS)
- [ ] Налаштування моніторингу помилок на клієнті через Sentry з відправкою source maps
- [ ] Перевірка безпеки залежностей через `npm audit` та Snyk
- [ ] Валідація контрастності та доступності для Screen Readers

## Архітектурний шаблон enterprise-рівня: Масштабованість, моніторинг та безпека

При проектуванні вебзастосунків для мільйонів користувачів критично закладати принципи надійності ще на етапі створення базових компонентів:

### 1. Трасування продуктивності на стороні клієнта (Real User Monitoring - RUM)
Для відстеження реального досвіду користувачів впроваджується збір Core Web Vitals через `PerformanceObserver` API:
```javascript
new PerformanceObserver((entryList) => {
  for (const entry of entryList.getEntries()) {
    if (!entry.hadRecentInput) {
      console.log('Поточне зміщення CLS:', entry.value);
    }
  }
}).observe({ type: 'layout-shift', buffered: true });
```

### 2. Матриця інженерної зрілості фронтенд-системи:
- **Рівень 1 (Базовий)**: Працюючий код, відсутність глобальних синтаксичних помилок, базова верстка.
- **Рівень 2 (Стандартний)**: Семантична розмітка, поділ на компоненти, базові юніт-тести, строгий TypeScript.
- **Рівень 3 (Виробничий)**: Повна доступність (a11y AA), відсутність витоків пам'яті, оптимізація Core Web Vitals, моніторинг помилок у реальному часі.
- **Рівень 4 (Enterprise)**: Дизайн-система з версіонуванням токенів, автоматизоване тестування візуальних регресій у CI/CD, A/B тестування компонентів, нульовий час простою (Zero-Downtime deployment).
