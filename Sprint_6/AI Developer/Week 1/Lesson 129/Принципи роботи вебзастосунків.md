# Урок 129: Принципи роботи вебзастосунків

## Вступ: Веб як глобальна розподілена обчислювальна система

Сучасний вебзастосунок — це розподілена програмна система, яка функціонує на базі клієнт-серверної архітектури і використовує стек протоколів Інтернету для транспортування даних, узгодження стану та відображення інтерактивного інтерфейсу. Для інженера розуміння принципів роботи вебзастосунків є фундаментальним: від моменту введення URL-адреси в адресний рядок браузера або натискання кнопки у мобільному застосунку до появи першого пікселя на екрані відбуваються сотні скоординованих мережевих, системних та програмних операцій.

У цьому уроці ми детально розберемо повний життєвий цикл веб-запиту, мережеві протоколи від канального до прикладного рівнів (DNS, TCP, TLS 1.3, HTTP/1.1, HTTP/2, HTTP/3 QUIC), архітектуру сучасних браузерних рушіїв (Blink, Gecko, WebKit), механіку критичного шляху рендерингу (Critical Rendering Path) та системні принципи балансування й кешування трафіку на рівні Enterprise.

## 1. Повний життєвий цикл веб-запиту (Request-Response Lifecycle)

Розглянемо вичерпний ланцюжок подій при переході за посиланням `https://app.enterprise-cloud.io/analytics`:

```
+-------------------------------------------------------------------------------+
| 1. Користувацький ввід: парсинг URL, HSTS-перевірка, пошук у кеші браузера   |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 2. Резолвінг імені (DNS Lookup): Local Cache -> OS Hosts -> Resolver -> TLD   |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 3. Транспортне з'єднання (TCP 3-Way Handshake): SYN -> SYN-ACK -> ACK        |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 4. Захищений канал (TLS 1.3 Handshake): Key Exchange, Сертифікат, Cipher Suite|
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 5. Передача HTTP-запиту (HTTP/2 / HTTP/3 Streams): Headers, Cookies, Payload   |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 6. Мережева інфраструктура: Edge Anycast -> CDN / WAF -> L4/L7 Load Balancers |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 7. Бекенд-обробка: Reverse Proxy (Nginx) -> API Gateway -> Сервіс -> БД/Кеш   |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 8. Відповідь сервера: HTTP Status, Response Headers, Тіло відповіді (HTML/JSON)|
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
| 9. Клієнтський рендеринг: DOM + CSSOM -> Render Tree -> Layout -> Paint -> GPU|
+-------------------------------------------------------------------------------+
```

### 1.1. DNS-інфраструктура та алгоритми резолвінгу
Система доменних імен (DNS) — це глобальна розподілена база даних типу ключ-значення з ієрархічною структурою:
1. **Локальні рівні кешування**: Перш ніж запит вийде в публічну мережу, перевіряються:
   - Внутрішній кеш браузера (у Chrome доступний через `chrome://net-internals/#dns`).
   - Кеш операційної системи (`DNS Client Cache` у Windows, `nscd` / `systemd-resolved` у Linux).
   - Статичний файл локальних прив'язок (`/etc/hosts` або `C:\Windows\System32\drivers\etc\hosts`).
2. **Рекурсивний DNS-резолвер (ISP або Public DNS)**: Звернення до призначеного сервера (Cloudflare `1.1.1.1`, Google `8.8.8.8`). Якщо в його кеші запис відсутній, резолвер виконує серію ітеративних запитів.
3. **Ієрархія авторитетних серверів**:
   - **Root Name Servers (Кореневі сервери)**: 13 логічних кореневих серверів (від `a.root-servers.net` до `m.root-servers.net`), розгорнутих через Anycast на сотнях фізичних вузлів. Вони повертають адресу TLD-сервера для доменної зони `.io`.
   - **TLD Name Servers**: Сервери верхнього рівня, які відповідають за зону `.io`, повертають адреси авторитетних серверів домену `enterprise-cloud.io`.
   - **Authoritative Name Servers**: Сервери (наприклад, AWS Route 53 або Cloudflare), які містять первинну зону і повертають конкретний A-запис (IPv4) або AAAA-запис (IPv6).

### 1.2. Встановлення транспортного рівня: TCP та TLS 1.3
Для передачі трафіку за протоколом IPv4/IPv6 клієнт повинен відкрити транспортне з'єднання:
- **TCP Three-Way Handshake**:
  1. `SYN`: Клієнт генерує початковий номер послідовності (Initial Sequence Number, ISN) та надсилає прапорець синхронізації.
  2. `SYN-ACK`: Сервер відповідає власним ISN та підтверджує отримання пакета клієнта (`ACK = ISN_client + 1`).
  3. `ACK`: Клієнт підтверджує отримання номера сервера (`ACK = ISN_server + 1`). З цього моменту з'єднання вважається ESTABLISHED.
- **TLS 1.3 Handshake (Захищений шар)**:
  На відміну від застарілого TLS 1.2, який вимагав 2 повних цикли (2-RTT), TLS 1.3 оптимізовано до 1-RTT (або 0-RTT у разі використання механізму `Early Data` / PSK):
  - Клієнт у пакеті `ClientHello` одразу надсилає підтримувані Cipher Suites та свою частину ключа Діффі-Хеллмана (Key Share).
  - Сервер у відповіді `ServerHello` відправляє свій Key Share, цифровий сертифікат (X.509) та підтвердження обраного шифру. Обидві сторони обчислюють спільний сесійний симетричний ключ безпосередньо.
  - Починається передача зашифрованих прикладних даних.

## 2. Еволюція прикладних протоколів передачі даних

| Характеристика | HTTP/1.1 (RFC 2616, 1999) | HTTP/2 (RFC 7540, 2015) | HTTP/3 (RFC 9114, 2022) |
| :--- | :--- | :--- | :--- |
| **Транспортний протокол** | TCP | TCP | QUIC (поверх UDP) |
| **Формат передачі** | Текстовий | Бінарні фрейми | Бінарні фрейми |
| **Мультиплексування** | Немає (послідовне або Keep-Alive) | Є (багато потоків в одному TCP) | Є (незалежні потоки в QUIC) |
| **Head-of-Line Blocking** | На рівні HTTP-запитів | На рівні TCP-пакетів | Повністю відсутнє |
| **Стиснення заголовків** | Відсутнє | HPACK (статична + динамічна таблиці)| QPACK (адаптоване під out-of-order) |
| **Міграція з'єднання** | Розрив при зміні IP | Розрив при зміні IP | Миттєва без розриву (Connection ID) |
| **Рукостискання (Handshake)** | Окремо TCP (1-RTT) + TLS (1-2 RTT) | Окремо TCP + TLS | Об'єднане QUIC + TLS 1.3 (1-RTT / 0-RTT)|

### Глибокий розбір HTTP/3 та протоколу QUIC
Головним недоліком HTTP/2 була залежність від TCP. Якщо один TCP-сегмент губиться в мережі через перевантаження або втрату сигналу Wi-Fi, стек операційної системи блокує всі подальші пакети (TCP Head-of-Line Blocking), доки втрачений сегмент не буде доставлено повторно. Це зупиняє виконання всіх мультиплексованих потоків на сторінці.

Протокол QUIC, створений на базі UDP, переносить контроль надійності та порядок потоків у простір користувача (User Space). У разі втрати датаграми в потоці #3, потоки #1, #2 та #4 продовжують оброблятися браузером без затримок. Крім того, QUIC використовує 64-бітний ідентифікатор `Connection ID`, завдяки чому мобільний телефон при переході з офісного Wi-Fi на 5G не розриває відкриті сесії та не перезавантажує вебсторінки.

## 3. Критичний шлях рендерингу (Critical Rendering Path)

Після того, як перші пакети HTML-відповіді надходять до браузерного рушія, починається конвеєр перетворення розмітки у фізичне зображення:

```
[Потік байтів HTML] ──> [Символи] ──> [Токени] ──> [Вузли] ──> [DOM Tree]
                                                                     │
[Потік байтів CSS]  ──> [Символи] ──> [Токени] ──> [Вузли] ──> [CSSOM Tree]
                                                                     │
                                                                     ▼
                                                             [Render Tree]
                                                                     │
                                                                     ▼
                                                             [Layout / Reflow]
                                                                     │
                                                                     ▼
                                                             [Paint / Raster]
                                                                     │
                                                                     ▼
                                                             [GPU Compositing]
```

### 3.1. Деталізація кожного етапу CRP:
1. **DOM Construction**: Парсер токенізує HTML-теги (`StartTag`, `EndTag`, `Character`) та формує деревоподібну структуру об'єктів. Процес є потоковим: браузер починає будувати DOM ще до повного завантаження файлу.
2. **CSSOM Construction**: CSS є блокуючим ресурсом для відмальовування (`render-blocking`). На відміну від DOM, CSSOM не може бути побудований потоково, оскільки правила стилів, оголошені в кінці документа, можуть перевизначити (каскадувати) правила на початку.
3. **Render Tree**: Синтез DOM та CSSOM. Сюди потрапляють тільки вузли, які беруть участь у візуальному відображенні. Елементи з `display: none` та службові теги `<head>`, `<meta>`, `<script>` виключаються. Елементи з `visibility: hidden` потрапляють, оскільки резервують геометричне місце.
4. **Layout (Reflow)**: Розрахунок геометрії. Рушій визначає ширину, висоту, координати `X` та `Y` кожного елемента відносно в'юпорту браузера. Важка операція на CPU.
5. **Paint (Repaint)**: Растеризація векторних форм, заповнення пікселів фоном, шрифтами, бордерами, тінями.
6. **Compositing**: Окремі елементи виділяються в окремі шари композитингу (Compositing Layers), передаються на відеокарту (GPU) та зшиваються в єдиний кадр. Властивості `transform` та `opacity` працюють напряму на GPU, оминаючи фази Layout та Paint, забезпечуючи плавність 60/120 fps.

## 4. Архітектурні моделі вебзастосунків

Розробник повинен обирати модель розгортання відповідно до бізнес-вимог:

### 4.1. Single-Page Application (SPA)
- **Сутність**: Сервер віддає мінімальний HTML-каркас (`<div id="root"></div>`) та великий JS-бандл. Маршрутизація виконується у браузері через `History API`.
- **Переваги**: Миттєві переходи без перезавантаження сторінки, багатий UX, ізоляція фронтенду від бекенду.
- **Недоліки**: Довгий час до першого осмисленого відмальовування (First Contentful Paint, FCP), проблеми з SEO для пошукових роботів без виконання JS, велике споживання пам'яті браузера.

### 4.2. Server-Side Rendering (SSR)
- **Сутність**: Сервер (наприклад, Node.js на базі Next.js/Nuxt) генерує повний HTML-код для кожного клієнтського запиту на льоту.
- **Гідратація (Hydration)**: Отримавши готовий HTML, браузер відмальовує його, а потім завантажує JS-бандл, який ініціалізує слухачі подій та прив'язує реактивний стан до існуючих DOM-вузлів.
- **Переваги**: Бездоганне SEO, швидкий FCP.
- **Недоліки**: Навантаження на процесори серверів, час затримки (Time to First Byte, TTFB) при повільних бекенд-запитах, потенційний розрив між відображенням і можливістю клікнути (First Input Delay, FID / Interaction to Next Paint, INP).

### 4.3. Static Site Generation (SSG) та Incremental Static Regeneration (ISR)
- **SSG**: Весь сайт компілюється в статичні HTML/CSS/JS файли під час збірки проєкту (`npm run build`). Ідеально підходить для документації, блогів, лендінгів.
- **ISR**: Поєднання швидкості SSG та динамічності SSR. Сторінка роздається з кешу CDN, але сервер перегенеровує її у фоні після закінчення заданого тайм-ауту (`revalidate: 60`), якщо надійшов новий запит від користувача.

## 5. Корпоративна інфраструктура: Кешування, CDN та балансування

```
               +-------------------------------------------+
               |           Клієнтський браузер             |
               +-------------------------------------------+
                                     │
                     [Cache-Control: max-age=31536000]
                                     ▼
               +-------------------------------------------+
               |       Edge CDN (Cloudflare / Fastly)      |
               +-------------------------------------------+
                                     │ (Cache Miss)
                                     ▼
               +-------------------------------------------+
               |       WAF (Web Application Firewall)      |
               +-------------------------------------------+
                                     │
                                     ▼
               +-------------------------------------------+
               |     L4 / L7 Load Balancer (Nginx/Envoy)   |
               +-------------------------------------------+
                          │                     │
                          ▼                     ▼
               +--------------------+ +--------------------+
               | App Pod 1 (Node.js)| | App Pod 2 (Node.js)|
               +--------------------+ +--------------------+
```

### Стратегії HTTP-кешування
1. **Cache-Control Заголовки**:
   - `public`: Відповідь може кешуватися будь-яким посередником (CDN, проксі).
   - `private`: Кешується виключно в кінцевому браузері користувача (для персональних кабінетів).
   - `no-cache`: Відповідь кешується, але перед кожним показом вимагає валідації на вихідному сервері (через умовні запити `ETag` або `If-Modified-Since`).
   - `no-store`: Категорична заборона запису на диск чи в пам'ять (для банківських операцій).
   - `immutable`: Файл гарантовано ніколи не зміниться (використовується для асетів із хешем у назві: `bundle.a89f3b.js`).

## 6. Безпека веб-застосунків: Базові вектори загроз (OWASP Top 10)

Розробник вебзастосунків повинен проєктувати систему із врахуванням архітектурної безпеки (Security by Design):
1. **SOP (Same-Origin Policy)**: Забороняє скрипту читати дані з іншого походження (`protocol://host:port`), крім випадків дозволу через CORS.
2. **CORS (Cross-Origin Resource Sharing)**: Налаштування заголовків `Access-Control-Allow-Origin` для безпечної інтеграції мікросервісів та сторонніх API.
3. **Захист від XSS**: Екранування користувацького вводу, використання сучасних фреймворків (React/Vue екранують за замовчуванням), строга політика CSP (Content Security Policy).
4. **Захист від CSRF**: Впровадження токенів `Anti-CSRF`, налаштування Cookie з `SameSite=Lax` або `SameSite=Strict` та прапорцем `Secure`.
5. **Clickjacking**: Заборона показу сторінки в iframe через `X-Frame-Options: DENY` або CSP `frame-ancestors 'none'`.

## 7. AI-Assisted Інжиніринг для оптимізації вебзастосунків

Сучасний розробник використовує AI-асистентів (ChatGPT, Claude 3.5 Sonnet, Cursor) як інтелектуальний інструмент профілювання та генерації конфігурацій:
- **Генерація оптимізованих конфігурацій веб-серверів**: Створення безпечних конфігів Nginx/Caddy з підтримкою HTTP/3, TLS 1.3, Brotli-компресії та заголовків безпеки HSTS.
- **Аналіз Waterfall-діаграм**: Інтерпретація HAR-файлів (HTTP Archive) для автоматичного виявлення "пляшкових горлець", блокуючих скриптів та повільних API-відповідей.
- **Оптимізація коду під Core Web Vitals**: Виявлення причин Layout Shift (CLS), довгого LCP та підбір технік лінивого завантаження (`loading="lazy"`, `fetchpriority="high"`).

## Практичний інженерний розбір: Реальний індустріальний кейс

Розглянемо практичний сценарій розгортання та оптимізації компонента у високонавантаженій системі (наприклад, платіжний віджет інтернет-банкінгу, що обслуговує понад 200 000 користувачів одночасно):

### 1. Архітектурне проєктування
1. **Ізоляція стану**: Відмова від глобального монолітного стану на користь локалізованих реактивних примітивів (Signals або легкі стори Zustand). Це запобігає каскадним ре-рендерам сусідніх дерев компонентів.
2. **Мережева оптимізація**: Реалізація механізму кешування запитів із заголовком `stale-while-revalidate`. Користувач миттєво бачить збережені дані з локального кешу, поки у фоновому потоці асинхронно відбувається оновлення стану через API.
3. **Обробка крайових випадків**: Реалізація відмовостійкості на рівні інтерфейсу (Graceful Degradation): при втраті зв'язку з бекендом формується офлайн-черга запитів у IndexedDB з автоматичною синхронізацією при відновленні мережі (Background Sync API).

### 2. Приклад коду виробничого рівня: Відмовостійкий клієнтський компонент
```typescript
// Production-Ready Component with AbortController, Error Boundary & Accessibility
import React, { useState, useEffect, useRef } from 'react';

interface DataState<T> {
  data: T | null;
  isLoading: boolean;
  error: Error | null;
}

export function ResilientWidget<T>({ endpoint, title }: { endpoint: string; title: string }) {
  const [state, setState] = useState<DataState<T>>({ data: null, isLoading: true, error: null });
  const abortControllerRef = useRef<AbortController | null>(null);

  useEffect(() => {
    abortControllerRef.current = new AbortController();
    
    async function fetchData() {
      try {
        setState(prev => ({ ...prev, isLoading: true, error: null }));
        const response = await fetch(endpoint, {
          signal: abortControllerRef.current?.signal,
          headers: { 'Accept': 'application/json' }
        });
        
        if (!response.ok) {
          throw new Error(`HTTP помилка: статус ${response.status}`);
        }
        
        const payload = await response.json();
        setState({ data: payload, isLoading: false, error: null });
      } catch (err: any) {
        if (err.name !== 'AbortError') {
          setState({ data: null, isLoading: false, error: err });
        }
      }
    }

    fetchData();

    return () => {
      abortControllerRef.current?.abort();
    };
  }, [endpoint]);

  if (state.isLoading) {
    return (
      <div role="status" aria-live="polite" className="animate-pulse p-4 rounded-lg bg-slate-100 dark:bg-slate-800">
        <div className="h-4 bg-slate-300 dark:bg-slate-700 rounded w-3/4 mb-2"></div>
        <div className="h-3 bg-slate-200 dark:bg-slate-600 rounded w-1/2"></div>
        <span className="sr-only">Завантаження даних віджета...</span>
      </div>
    );
  }

  if (state.error) {
    return (
      <div role="alert" className="p-4 border-l-4 border-red-500 bg-red-50 dark:bg-red-950 text-red-700">
        <h3 className="font-semibold">Помилка відображення</h3>
        <p className="text-sm">{state.error.message}</p>
      </div>
    );
  }

  return (
    <section aria-label={title} className="p-4 rounded-xl border border-slate-200 shadow-sm">
      <h2 className="text-lg font-bold mb-3">{title}</h2>
      <pre className="text-xs bg-slate-50 p-2 rounded overflow-x-auto">
        {JSON.stringify(state.data, null, 2)}
      </pre>
    </section>
  );
}
```
