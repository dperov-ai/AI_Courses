# Контрольні запитання до Уроку 186: Основи HTTP та REST

Даний блок містить перелік аналітичних та практичних запитань для самоконтролю, перевірки глибини засвоєння матеріалу та підготовки до технічних інтерв’ю.

---

### 1. Чому автоматизація на рівні API займає більшу частку у піраміді тестування, ніж UI автоматизація?

**Відповідь:** API автотести виконуються на порядки швидше (десятки мілісекунд), є значно стабільнішими, не залежать від змін верстки, селекторів браузера та дозволяють повністю покрити всі бізнес-правила та негативні сценарії до готовності інтерфейсу.

---

### 2. Що таке APIRequestContext у фреймворку Playwright і які переваги він надає над звичайним fetch?

**Відповідь:** Це спеціалізований ізольований HTTP-клієнт, що підтримує базові конфігурації (baseURL, спільні заголовки), автоматичне збереження кук і сесій, прозору роботу з JSON, підтримку налаштувань тайм-аутів та ігнорування помилок SSL.

---

### 3. Чому принцип Stateless у REST спрощує паралелізацію автотестів?

**Відповідь:** Оскільки кожен запит містить повний контекст і сервер не зберігає сесію між викликами, тести можна запускати у 20 паралельних потоках без ризику перезапису стану сесії між різними тестами.

---

### 4. Як автотест повинен реагувати на неідемпотентність методу POST?

**Відповідь:** Тест повинен динамічно генерувати унікальні ідентифікатори та дані (UUID, унікальний email) для кожного запуску, щоб не стикатися з помилками конфлікту унікальності (409 Conflict).

---

### 5. Що таке Service Virtualization (Віртуалізація сервісів) і коли вона застосовується в автоматизації?

**Відповідь:** Це техніка симуляції поведінки зовнішніх або нестабільних залежних систем (наприклад, банківських шлюзів) за допомогою мок-серверів (WireMock, Prism), що дозволяє тестувати систему у повній ізоляції.

---

### 6. Як налаштувати Playwright API клієнт для тестування локальних середовищ із самопідписаними SSL-сертифікатами?

**Відповідь:** Встановити параметр 'ignoreHTTPSErrors: true' в конфігурації playwright.config.ts або при створенні нового контексту запиту request.newContext().

---

### 7. Чому використання статичних пауз sleep() в API тестах вважається грубим антипатерном?

**Відповідь:** sleep() безпідставно сповільнює виконання сьюту і водночас не гарантує готовності ресурсу. Замість цього використовується polling (опитування з таймаутом і перевіркою статусу кожні 100-200мс).

---

### 8. Які переваги надає використання єдиного базового URL (baseURL) у конфігурації тест-раннера?

**Відповідь:** Дозволяє перемикати весь набір тестів між різними середовищами (Local, Dev, Staging, Prod) через одну змінну оточення процесу process.env.BASE_URL без зміни коду тестів.

---

### 9. Що таке Connection Pooling та Keep-Alive у контексті швидкісного прогону API автотестів?

**Відповідь:** Це збереження відкритого TCP-з'єднання між серією послідовних HTTP-запитів, що усуває накладні витрати на тристороннє рукостискання (3-way handshake) та прискорює прогін тестів на 40%.

---

### 10. Як організувати очищення даних (Teardown) в автотестах, якщо сам тест упав посередині виконання?

**Відповідь:** Використовувати блоки test.afterEach() або фікстури Playwright (Fixtures) з кодом після виклику 'await use()', які гарантовано виконуються навіть при аварійному падінні основного тіла тесту.

---

### 11. Що таке Contract Testing і як воно пов'язане з основами REST?

**Відповідь:** Це тестування узгодженості схем обміну даними між споживачем (Consumer) та постачальником (Provider) API за допомогою контрактів (наприклад, Pact), що запобігає несподіваним змінам форматів при деплої.

---

### 12. Як обробляти відповіді сервера, які повертають бінарні дані (PDF-звіти, зображення) в автотестах?

**Відповідь:** Використовувати методи читання байтів (response.body() у Playwright або responseType: 'arraybuffer' в Axios) з подальшою перевіркою розміру файлу, заголовка Content-Type та магічних байтів формату.

---

### 13. Що таке fail-fast поведінка в API автотестах?

**Відповідь:** Це стратегія, коли тест негайно переривається при невідповідності статусу відповіді (наприклад, очікували 200, а прийшло 500), не витрачаючи час на безглузді перевірки полів тіла порожньої чи зламаної відповіді.

---

### 14. Як перевірити підтримку стиснення відповідей (Gzip/Brotli) через автоматизований тест?

**Відповідь:** Надіслати заголовок 'Accept-Encoding: gzip, br' та перевірити наявність заголовка відповіді 'Content-Encoding' із відповідним значенням.

---

### 15. Яка різниця між Query параметрами та Body при автоматизації фільтрації?

**Відповідь:** Query параметри додаються до URL (?limit=10) і використовуються для ідемпотентних GET запитів. Body передається окремим потоком даних і використовується для POST/PUT/PATCH запитів.

---

### 16. Що таке Flaky Test у контексті API автоматизації?

**Відповідь:** Тест, який періодично падає без зміни коду, зазвичай через гонки асинхронних операцій, мережеві таймаути або конфлікти спільних тестових даних між потоками.

---

### 17. Як автотест повинен перевіряти заголовки безпеки?

**Відповідь:** Перевіряти наявність у відповіді обов'язкових security-заголовків: Strict-Transport-Security, X-Content-Type-Options: nosniff, Content-Security-Policy.

---

### 18. Що таке冪потентний ключ (Idempotency-Key) у коді автотестів?

**Відповідь:** Унікальний UUID, який генерується тестом і передається у заголовку POST-запиту, що дозволяє перевірити відсутність дублювання операції при повторному відправленні.

---

### 19. Як за допомогою AI оптимізувати структуру сьюту API тестів?

**Відповідь:** AI допомагає згрупувати тести за доменними сутностями, винести дубльовані налаштування у спільні фікстури та створити гнучкі клієнтські класи.

---

### 20. Як вимірювати час виконання запитів у Playwright API тестах?

**Відповідь:** Зафіксувати мітку часу Date.now() до відправки запиту та порівняти з міткою після отримання відповіді, або використовувати вбудовані таймінги трейсів Playwright.

---
