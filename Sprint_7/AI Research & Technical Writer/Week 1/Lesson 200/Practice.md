# Практичні завдання до Уроку 200: Типи технічної та бізнес-документації

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Класифікація та аудит документації за моделлю Diátaxis

**Мета:** Навчитися структурувати документацію продукту за стандартом Diátaxis та виявляти концептуальні дисбаланси.

**Вхідний контекст та бізнес-сценарій:**
Компанія розробляє SaaS-платформу обробки документів за допомогою AI. Наявна база знань хаотична: в одній статті змішані інструкція встановлення бібліотеки, філософія розпізнавання OCR та синтаксис запитів.

**Покроковий алгоритм виконання:**
1. Проаналізувати наданий фрагмент хаотичної документації.
2. Розподілити контент за 4 квадрантами Diátaxis: Tutorial, How-To, Reference, Explanation.
3. Сформувати структуру розділів репозиторію документації.
4. Скласти звіт із рекомендаціями щодо усунення прогалин.

**Рекомендований системний AI-промпт:**
```text
Ти — провідний Technical Writer за стандартом Diátaxis. Проаналізуй наступний текст змішаної документації [вставити текст] та розділи його на 4 чіткі документи: 1) Quickstart Tutorial, 2) How-To Guide з обробки PDF, 3) API Reference для ендпоінта /v1/parse, 4) Explanation архітектури моделей OCR. Дотримуйся строгих стилістичних вимог кожного квадранта.
```

**Очікуваний результат:**
Чотири структуровані документи з чітким розмежуванням цілей та стилістики без змішування теорії з покроковими кроками.

**Критерії самоперевірки та оцінювання:**
- [ ] Tutorial має чіткий початок, простий шлях та очевидний результат для новачка.
- [ ] How-To фокусується виключно на вирішенні виробничого завдання без теоретичних відступів.
- [ ] Reference містить точну таблицю параметрів, типи даних та HTTP-коди.
- [ ] Explanation розкриває архітектурні принципи та причини прийняття проектних рішень.

## Завдання 2: Створення Architecture Decision Record (ADR) за допомогою AI

**Мета:** Опанувати написання та стандартизацію інженерних документів прийняття рішень за шаблоном Michael Nygard.

**Вхідний контекст та бізнес-сценарій:**
Команда інженерів вирішила замінити протокол взаємодії між мікросервісами з REST на gRPC для зменшення затримок мережі. Необхідно зафіксувати це рішення в офіційному ADR.

**Покроковий алгоритм виконання:**
1. Визначити контекст проблеми: високий оверхед серіалізації JSON та затримки понад 150мс.
2. Сформулювати запропоноване рішення: впровадження gRPC та Protocol Buffers.
3. Описати розглянуті альтернативи (GraphQL, WebSockets, оптимізація REST).
4. Зафіксувати наслідки: прискорення обміну на 60%, але необхідність оновлення API Gateway та навчання QA-команди тестуванню gRPC.

**Рекомендований системний AI-промпт:**
```text
Склади професійний Architecture Decision Record (ADR) за шаблоном Nygard для переходу інфраструктури компанії з REST на gRPC. Включи детальний технічний контекст, статус, обґрунтування вибору, таблицю порівняння альтернатив та вичерпний аналіз позитивних і негативних наслідків для розробки, тестування та експлуатації.
```

**Очікуваний результат:**
Повний документ ADR у форматі Markdown, готовий до додавання у папку /docs/adr репозиторію проекту.

**Критерії самоперевірки та оцінювання:**
- [ ] Дотримано канонічної структури ADR (Title, Status, Context, Decision, Consequences).
- [ ] Технічні аргументи містять конкретні метрики та протоколи.
- [ ] Враховано компроміси (Trade-offs) та план пом'якшення ризиків.
