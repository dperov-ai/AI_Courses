# Практичні завдання до Уроку 204: Шаблони документів

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Розробка корпоративного стандарту шаблону PRD (Product Requirement Document)

**Мета:** Створити збалансований виробничий шаблон PRD для AI-driven розробки з чіткими плейсхолдерами та чеклістами.

**Вхідний контекст та бізнес-сценарій:**
Компанія створює інноваційні фічі, але продукт-менеджери описують вимоги у довільній формі, через що розробники постійно випускають не те, що очікував бізнес.

**Покроковий алгоритм виконання:**
1. Визначити обов'язкові розділи PRD: Business Context, Goals & Non-Goals, User Personas, User Stories з Gherkin синтаксисом (Given-When-Then), NFRs, Data Privacy.
2. Написати детальні інструкції та зразки заповнення для кожного блоку.
3. Додати секцію критеріїв успіху (Success Metrics: North Star Metric, Leading Indicators).
4. Створити промпт для валідації заповненого PRD за допомогою AI.

**Рекомендований системний AI-промпт:**
```text
Створи повноцінний професійний шаблон Product Requirement Document (PRD) у форматі Markdown. Шаблон повинен містити інтегровані підказки в квадратних дужках, зразок User Story за стандартом Gherkin, таблицю нефункціональних вимог (NFR) та інтегрований чекліст готовності до розробки (Definition of Ready).
```

**Очікуваний результат:**
Еталонний шаблон PRD, готовий до розміщення у корпоративній базі знань або репозиторії шаблонів компанії.

**Критерії самоперевірки та оцінювання:**
- [ ] Присутні розділи бізнес-цілей та заборонених меж (Non-goals).
- [ ] Включено стандарт опису поведінки Given-When-Then.
- [ ] Наявні точні інженерні плейсхолдери без розпливчастих фраз.

## Завдання 2: Автоматизоване заповнення шаблону Post-Mortem за допомогою AI з сирого логу інциденту

**Мета:** Опанувати швидку екстракцію фактів з аварійних логів та формування офіційного інженерного звіту.

**Вхідний контекст та бізнес-сценарій:**
Під час нічного релізу сталася аварія: збій оновлення бази даних залишив 15 000 користувачів без доступу на 45 хвилин. Наявні сирі повідомлення з чату інциденту в Slack.

**Покроковий алгоритм виконання:**
1. Отримати фрагмент сирих повідомлень чату інциденту з таймстемпами та репліками чергових.
2. Сформулювати інструкцію для AI з витягування фактів за наданим шаблоном Post-Mortem.
3. Згенерувати заповнений документ: точний таймлайн, резюме та аналіз кореневої причини 5 Whys.
4. Сформувати перелік інженерних превентивних завдань (Action items).

**Рекомендований системний AI-промпт:**
```text
Ти — Incident Commander. Використовуючи наданий лог переписки інженерів під час аварії [вставити лог], повністю заповни корпоративний шаблон Blameless Post-Mortem. Дотримуйся об'єктивного тону без звинувачень персоналій, віднови послідовний таймлайн в UTC, сформулюй 5 Whys та запропонуй 3 конкретні технічні Action Items.
```

**Очікуваний результат:**
Повністю заповнений інженерний документ Post-Mortem за найвищими стандартами індустрії (Google SRE / AWS).

**Критерії самоперевірки та оцінювання:**
- [ ] Хронологія відновлена без пропусків та плутанини в часі.
- [ ] Аналіз 5 Whys дійшов до системної інженерної причини (відсутність канареечного релізу / лімітів).
- [ ] Завдання Action Items мають чіткі критерії виконання.
