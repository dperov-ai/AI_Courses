# Урок 204: Шаблони документів

## Вступ: Сила шаблонів та дизайн-систем у технічній документації

У масштабованій інженерній організації створення документів з чистого аркуша є антипатерном, що призводить до хаосу, пропускання важливих розділів та втрати єдиного корпоративного стилю. 

**Шаблони документів (Document Templates)** — це стандартизовані каркаси артефактів, які заздалегідь визначають структуру, обов'язкові поля, правила оформлення та критерії якості для кожного типу документа. Шаблони відіграють таку саму роль у технічному письмі, як компоненти UI-Kit у дизайні інтерфейсів:
- Вони усувають «страх чистого аркуша» у розробників, які пишуть документацію.
- Гарантують обов'язкову присутність критичних секцій (Безпека, Моніторинг, План відкату).
- Дозволяють автоматизувати перевірку документів лінтерами та AI-агентами у CI/CD.

У цьому уроці ми вивчимо анатомію провідних індустріальних шаблонів (PRD, ADR, Post-Mortem, API Reference, Runbook) та техніку створення інтелектуальних шаблонів під керуванням AI.

## 1. Анатомія ключових виробничих шаблонів

### Шаблон 1: Architecture Decision Record (ADR)
```markdown
# ADR-[NUM]: [Коротка дієслівна назва рішення]

- **Статус**: [Draft | Proposed | Accepted | Rejected | Deprecated | Superseded by ADR-XXX]
- **Дата**: YYYY-MM-DD
- **Автори**: [Ім'я, Роль]
- **Технічні стейкхолдери**: [Архітектори, Tech Leads]

## 1. Контекст та постановка проблеми
[Опис бізнес- або технічного драйвера. Які обмеження системи змусили шукати нове рішення?]

## 2. Розглянуті альтернативи
| Критерій оцінки | Варіант 1: [Назва] | Варіант 2: [Назва] | Варіант 3: [Назва] |
| :--- | :--- | :--- | :--- |
| Складність підтримки | Низька | Середня | Висока |
| Затримка (Latency) | ~120ms | ~15ms | ~5ms |
| Вартість ліцензії | Open-source | \$500/міс | Внутрішня розробка |

## 3. Прийняте рішення
[Чітке формулювання вибору з технічним обґрунтуванням, чому саме цей варіант переміг.]

## 4. Наслідки (Consequences)
- **Позитивні**: [Що покращиться?]
- **Негативні / Ризики**: [Які компроміси довелося прийняти?]
- **Вплив на інші підсистеми**: [Що доведеться оновити чи переписати?]
```

## 2. Системи шаблонізації та Docs-as-Code

У сучасних підходах шаблони не просто зберігаються у Word або Confluence, а інтегруються у Git-репозиторії:
1. **GitHub Issue & Pull Request Templates**:
   Файли `.github/ISSUE_TEMPLATE/*.md` та `.github/pull_request_template.md` змушують авторів заповнювати обов'язкові блоки (Опис, Кроки відтворення, Чекліст тестів).
2. **Шаблони статичних генераторів (Docusaurus / MkDocs / Astro Starlight)**:
   Використання компонентів Markdown з фронтметтером (YAML Frontmatter) для автоматичної генерації метаданих, тегів та пошукових індексів.

## 3. AI-керована генерація на основі шаблонів

Використання шаблонів робить взаємодію з AI на порядок надійнішою:
- Замість прохання «Напиши звіт про інцидент», AI передається **суворий шаблон** та сирі логи з наказом: «Заповни цей Markdown шаблон, не змінюючи структуру заголовків та таблиць».
- Це усуває галюцинації моделі та гарантує, що жодне критичне поле не буде пропущено.


## Практичний інженерний розбір: Створення професійної специфікації API за стандартом OpenAPI 3.1

Розглянемо практичний приклад підготовки технічної документації для платіжного шлюзу за методологією Docs-as-Code:

### 1. Специфікація ендпоінта у форматі OpenAPI 3.1 (YAML)
```yaml
openapi: 3.1.0
info:
  title: Enterprise Payments Ingestion API
  version: 1.4.0
  description: Виробничий API сервіс для створення та підтвердження транзакцій еквайрингу.
paths:
  /v1/charges:
    post:
      summary: Створення платіжного платежу (Charge Creation)
      description: Ініціює блокування коштів на рахунку платника. Операція є суворо ідемпотентною.
      operationId: createCharge
      security:
        - BearerAuth: []
      parameters:
        - name: Idempotency-Key
          in: header
          required: true
          description: Унікальний ідентифікатор запиту (UUIDv4) для запобігання подвійному списанню.
          schema:
            type: string
            format: uuid
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [amount, currency, source]
              properties:
                amount:
                  type: integer
                  description: Сума у найменших одиницях валюти (наприклад, копійки для UAH, центи для USD).
                  example: 150000
                currency:
                  type: string
                  description: Тризначний код валюти згідно з ISO 4217.
                  enum: [UAH, USD, EUR]
                  example: "UAH"
                source:
                  type: string
                  description: Токен банківської карти або ідентифікатор збереженого платіжного засобу.
                  example: "tok_visa_debit_4242"
      responses:
        '201':
          description: Платіж успішно створено та авторизовано.
          content:
            application/json:
              schema:
                type: object
                properties:
                  chargeId:
                    type: string
                    example: "ch_8a7d12f9"
                  status:
                    type: string
                    enum: [SUCCEEDED, PENDING, FAILED]
                    example: "SUCCEEDED"
                  capturedAmount:
                    type: integer
                    example: 150000
        '400':
          $ref: '#/components/responses/BadRequestError'
        '401':
          $ref: '#/components/responses/UnauthorizedError'
components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
```


## Архітектура технічної інформації: Систематизація, стандартизація та Docs-as-Code

Професійна технічна документація є інженерним продуктом, який потребує суворої структуризації, єдиного термінологічного апарату та контролю життєвого циклу:

```
[Аудит аудиторії та бізнес-цілей]
               │
               ▼
[Формування інформаційної архітектури (IA) та таксономії]
               │
               ▼
[Вибір моделі контенту за фреймворком Diátaxis]
   ├── Tutorials (Навчання початківців від простого до складного)
   ├── How-To Guides (Покрокові інструкції для вирішення робочих завдань)
   ├── Reference (Технічні довідники API, схем та параметрів конфігурації)
   └── Explanation (Концептуальні пояснення архітектури та передумов)
               │
               ▼
[Складання детального Outline з багаторівневою ієрархією H1-H4]
               │
               ▼
[Стандартизація термінології через глосарії та Style Guides]
               │
               ▼
[Автоматизована збірка та лінтинг (Markdown, Vale, Docs-as-Code CI/CD)]
```

### Комплексна матриця структури та якості документації

| Тип документа | Цільова аудиторія | Ключові структурні блоки | Критерії якості |
| :--- | :--- | :--- | :--- |
| **API Reference** | Розробники, інженери інтеграцій | Опис ендпоінта, Authentication, Query/Path параметри, Request/Response body, Error codes, cURL зразки | 100% відповідність реальній поведінці сервера, OpenAPI 3.1 сумісність |
| **Architecture Decision Record (ADR)** | Архітектори, Tech Leads, інженерна команда | Контекст проблеми, розглянуті альтернативи, прийняте рішення, наслідки та компроміси | Чітка фіксація "Чому саме так?", незмінність історії |
| **Product Requirements Document (PRD)** | Продуктові менеджери, дизайнери, QA | Бізнес-мета, цільові метрики, User Stories, Scope (In-scope / Out-of-scope), нефункціональні вимоги | Однозначність формулювань, відсутність протиріч |
| **Standard Operating Procedure (SOP)** | Техпідтримка, чергові інженери, Operations | Критерії тригера, покроковий чеклист виконання дій, план відкату (Rollback), матриця ескалації | Можливість виконання процедури в умовах нічного інциденту без помилок |

### Стандарти технічного письма та контролю термінології:
1. **Microsoft Writing Style Guide & Google Developer Documentation Style Guide**: Використання активного стану, звернення на «ви», уникнення сленгу, лаконічність формулювань.
2. **Контрольована термінологія**: Один концепт завжди називається одним словом. Неприпустимо в межах одного документа чергувати слова «обліковий запис», «профіль», «акаунт» та «юзер».
3. **Docs-as-Code парадигма**: Збереження документації у Markdown у git-репозиторії, автоматичний лінтинг стилю за допомогою Vale, генерація статичних сайтів через Docusaurus / MkDocs / Mintlify.


## Стандарти структуризації технічної документації та інформаційної архітектури

Створення технічних документів базується на формальних стандартах інженерного письма:
1. **Фреймворк Diátaxis**:
   - Строгий розподіл документації на 4 квадранти: Навчання (Tutorials), Інструкції (How-To Guides), Концепції (Explanation) та Довідники (Reference). Змішування довідкових таблиць з навчальними посібниками вважається грубою архітектурною помилкою.
2. **Стилістичні інженерні гайдлайни**:
   - **Google Developer Documentation Style Guide**: Використання чітких, лаконічних заголовків, списків замість громіздких абзаців, стандартизоване форматування блоків коду.
   - **RFC 2119**: Використання нормативних слів `MUST`, `MUST NOT`, `SHOULD`, `RECOMMENDED`, `MAY` для однозначного тлумачення технічних вимог.

## Індустріальний досвід: Підхід Stripe, Twilio та AWS до технічної документації

Чому документація стає ключовою конкурентною перевагою:
- **Twilio**: Інтерактивні консолі безпосередньо на сторінці документації, де розробник може протестувати виклик API зі своїм ключем без переходу в інші програми.
- **Stripe**: Триколонковий макет (навігація, пояснення, зразок коду на 5 мовах програмування), що мінімізує час від читання до успішного виклику.

## Експертний аналіз: Як розбіжність документації з кодом призвела до зриву партнерської інтеграції на $500K

Кейс технічної комунікації:
1. **Інцидент**: Великий банк інтегрував API логістичної платформи. У PDF-документації було зазначено, що поле дати передається у форматі `DD/MM/YYYY`, тоді як у новому релізі бекенд очікував строго `ISO 8601 (YYYY-MM-DD)`.
2. **Наслідок**: Банк заблокував запуск інтеграції на місяць через регулярні помилки 400 Bad Request.
3. **Рішення**: Повна відмова від ручних PDF-інструкцій та впровадження Docs-as-Code: генерація документації безпосередньо з коду через OpenAPI специфікацію в CI/CD конвеєрі.


## Метрики ефективності технічної документації

Оцінка корисності та зрозумілості матеріалів:
- **Time to First Hello World (TTFHW)**: Час, необхідний сторонньому розробнику від відкриття документації до першого успішного API-запиту (цільове: < 10 хвилин).
- **Zero Search Results Rate**: Відсоток пошукових запитів у документації, які не дали жодного результату (індикатор прогалин у контенті).
- **Documentation Drift**: Відсоток ендпоінтів або параметрів у коді, які відсутні або застаріли в документації (цільове: 0%).

## Поглиблений інженерний гайд: Проектування навігації та пошукової доступності документації

Організація великих інформаційних масивів вимагає дотримання правил інформаційної ергономіки:
1. **Трирівнева глибина навігації (3-Click Rule)**:
   Будь-який технічний документ, опис ендпоінта чи інструкція з налаштування конфігурації повинні бути досяжні не більше ніж за 3 кліки від головної сторінки документаційного порталу.
2. **Семантичне маркування для внутрішнього пошуку (Algolia DocSearch / RAG)**:
   Впровадження структурованих метаданих (frontmatter), ключових слів та синонімів у Markdown-файли, що дозволяє користувачам знаходити потрібний розділ навіть при введенні розмовних чи сленгових термінів.


## Діагностика та виправлення прогалин у технічній документації

Усунення факторів розчарування сторонніх розробників:
- **Застарілі приклади коду (Code Rot)**:
  - Приклади в документації використовують старі методи SDK, які викликають помилки у свіжих версіях.
  - *Вирішення*: Впровадження інструментів автоматизованого тестування прикладів коду в документації (DocFX, markdown-code-runner) у пайплайні CI/CD.


## Управління життєвим циклом документації та версіонування (Content Lifecycle)

Організація підтримки документації у часі:
- **Застарівання та архівування контенту (Deprecation Policy)**:
  Чітке маркування застарілих ендпоінтів та версій API з попередженням за 6-12 місяців до їх остаточного відключення (Sunsetting) за допомогою заголовків `Deprecation` та `Sunset` (RFC 8594).
- **Зворотний зв'язок (Documentation Feedback Loop)**:
  Інтеграція кнопок «Чи була ця стаття корисною? Так/Ні» та збір коментарів для постійного виявлення незрозумілих розділів документації.


## Симуляція архітектури Docs-as-Code та автоматизованого аудиту контенту

Професійне документування програмного забезпечення розглядає текст як код зі строгими критеріями перевірки якості:

### 1. Автоматичний лінтинг стилістики та термінології за допомогою Vale
У репозиторії документації налаштовується інструмент **Vale**, який у CI перевіряє кожне речення за правилами:
- **Заборона пасивного стану**: «Користувач налаштовує параметри», а не «Параметри мають бути налаштовані».
- **Заборона жаргонізмів та неточних термінів**: Замість «задеплоїти» вимагається «розгорнути у виробничому середовищі».
- **Контроль довжини речень**: Речення довше 25 слів підсвічуються як помилка, що потребує декомпозиції для покращення сприйняття.

### 2. Автоматичний контроль відповідності документації коду (Spec Drift Detection)
Під час збірки бекенду інструмент CLI генерує актуальний `openapi.json` та порівнює його з поточною версією в документації за допомогою `openapi-diff`. Якщо бекендери додали новий параметр без оновлення опису, збірка падає, захищаючи клієнтів від застарілих інструкцій.


## Матриця якості та типових помилок технічної документації

| Антипатерн у тексті | Вплив на розробників / користувачів | Приклад помилки | Як переписати за стандартами |
| :--- | :--- | :--- | :--- |
| **Припущення про попередні знання (Curse of Knowledge)** | Новачки не можуть виконати інтеграцію, зростає потік тікетів у підтримку | «Просто підключіть наш SDK та викличте базовий метод» | Надання конкретної команди `npm install sdk-name` та мінімального коду з ініціалізацією |
| **Відсутність опису помилок** | Розробники не знають, як обробляти нестандартні відповіді | Описано лише успішний виклик `200 OK` | Додавання вичерпної таблиці всіх кодів `400, 401, 403, 404, 422, 500` зі зразками JSON-тіл помилок |
| **Застарілі URL або скріншоти інтерфейсу** | Втрата довіри до продукту, хибні кліки | Скріншот панелі управління 2-річної давнини | Використання схем замість фото інтерфейсів, автоматична перевірка посилань лінкером у CI |


## Підсумковий інженерний огляд та практичні рекомендації

Опанування теми **«Шаблони документів»** є ключовим будівельним блоком у професійному становленні спеціаліста за напрямком **AI Research & Technical Writer**. Системне застосування розглянутих методологій дозволяє:
1. **Забезпечити максимальну надійність та стабільність рішень**, спираючись на перевірені індустріальні патерни, міжнародні стандарти та строгі специфікації.
2. **Усунути людський фактор та сліпі зони**, використовуючи матриці контролю якості, автоматизовані тести та перехресну валідацію схем і процесів.
3. **Ефективно інтегрувати сучасні AI-інструменти** у щоденний виробничий конвеєр, виступаючи в ролі кваліфікованого інженера-архітектора, який ставить точні технічні завдання та критично верифікує результат.
