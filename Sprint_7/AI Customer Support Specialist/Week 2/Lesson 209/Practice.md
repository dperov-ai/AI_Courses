# Практичні завдання до Уроку 209: Робота з логами та повідомленнями про помилки

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Аналіз стектрейсу помилки та локалізація збою за допомогою AI

**Мета:** Опанувати швидке читання багаторядкових стектрейсів та формулювання точного діагнозу без залучення програмістів.

**Вхідний контекст та бізнес-сценарій:**
У логах бекенду зафіксовано каскадне падіння запиту клієнта на створення рахунку-фактури зі статусом 500. Наявний повний сирий стектрейс мовою Python/Django.

**Покроковий алгоритм виконання:**
1. Завантажити наданий стектрейс у промпт для аналізу.
2. Визначити точний рядок коду та бібліотеку, яка викликала виняток.
3. З'ясувати причину помилки (наприклад, ділення на нуль через відсутність податкової ставки у профілі клієнта).
4. Сформулювати рекомендацію: як оперативно виправити профіль клієнта та яку задачу поставити розробникам для захисту від повторення.

**Рекомендований системний AI-промпт:**
```text
Проаналізуй наступний стектрейс бекенд-помилки [вставити стектрейс]. Визнач: 1) Точний тип винятку (Exception Class) та його текстовий опис, 2) Який файл та рядок коду стали місцем падіння, 3) Які вхідні дані користувача спровокували цю проблему, 4) Як спеціаліст підтримки може тимчасово допомогти користувачу прямо зараз (Workaround), 5) Який баг-репорт слід оформити для розробників.
```

**Очікуваний результат:**
Вичерпний технічний аналіз стектрейсу зі зрозумілим бізнес-поясненням та конкретними кроками вирішення.

**Критерії самоперевірки та оцінювання:**
- [ ] Правильно визначено кореневий виняток.
- [ ] Надано тимчасове рішення (Workaround) для клієнта.
- [ ] Сформульовано точні технічні вимоги для усунення дефекту розробниками.

## Завдання 2: Пошук та кореляція логів за Trace ID у розподіленій системі

**Мета:** Навчитися відстежувати транзакцію крізь ланцюжок мікросервісів за спільним ідентифікатором.

**Вхідний контекст та бізнес-сценарій:**
Клієнт поскаржився, що при оформленні замовлення побачив помилку 'Сервіс тимчасово недоступний'. Відомий Trace ID із браузера: `tr-8841-ab99`.

**Покроковий алгоритм виконання:**
1. Проаналізувати надані фрагменти логів трьох сервісів: API Gateway, Order Service та Inventory Service.
2. Відновити хронологічний ланцюжок викликів за мітками часу.
3. Знайти, який саме мікросервіс першим зазнав збою та повернув помилку попередньому сервісу.
4. Скласти звіт про розслідування інциденту.

**Рекомендований системний AI-промпт:**
```text
У тебе є сирі логи трьох мікросервісів з спільним trace_id 'tr-8841-ab99' [вставити логи]. Віднови хронологію: о котрій годині надійшов запит в Gateway, кому він був перенаправлений, де виникла помилка і чому. Оформи розслідування у вигляді короткого звіту для L2 підтримки.
```

**Очікуваний результат:**
Чіткий хронологічний звіт проходження запиту між сервісами з виявленням винуватця збою (Inventory Service timeout).

**Критерії самоперевірки та оцінювання:**
- [ ] Послідовність викликів відновлена з точністю до мілісекунд.
- [ ] Точно локалізовано сервіс-винуватець збою.
- [ ] Пояснено механізм поширення помилки вгору по стеку.
