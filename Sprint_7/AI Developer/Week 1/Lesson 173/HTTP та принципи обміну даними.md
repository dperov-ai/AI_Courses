# Урок 173: HTTP та принципи обміну даними

## Вступ: Протокол HTTP як універсальна мова цифрової комунікації

Hypertext Transfer Protocol (HTTP) — це мережевий протокол прикладного рівня, який лежить в основі всієї взаємодії у Всесвітній павутині. Створений на початку 1990-х років для простої передачі текстових документів HTML, сьогодні протокол HTTP (включаючи його сучасні стандарти HTTP/2 та HTTP/3) трансформувався у високоефективну універсальну платформу для передачі будь-яких типів даних: структурованих JSON-документів, медіа-потоків, бінарних файлів та викликів API.

Для AI-розробника та оператора систем штучного інтелекту досконале знання протоколу HTTP є абсолютним мастхевом. Кожен виклик до моделі генеративного інтелекту (наприклад, OpenAI Chat Completions), кожна взаємодія між мікросервісами та кожна дія клієнтського застосунку здійснюється через строгі конструкції HTTP: методи, заголовки, статус-коди та корисне навантаження (payload).

У цьому уроці ми вивчимо структуру та семантику HTTP-запитів і відповідей, механізми узгодження контенту (Content Negotiation), коди станів сервера, особливості роботи заголовків кешування та безпеки, а також еволюцію протоколу від HTTP/1.1 до надшвидкого бінарного HTTP/3 на базі QUIC.

## 1. Структура протоколу HTTP: Запит та Відповідь (Request & Response)

Протокол HTTP функціонує за класичною моделлю «Запит-Відповідь» (Request-Response) поверх надійного транспортного протоколу (TCP або QUIC/UDP). 

```
КЛІЄНТ                                                СЕРВЕР
  │                                                     │
  ├────── HTTP Запит (Метод, URI, Headers, Body) ───────>
  │                                                     │
  │                                           [Обробка бізнес-логіки]
  │                                                     │
  <────── HTTP Відповідь (Status Code, Headers, Body) ──┤
  │                                                     │
```

### 1.1. Анатомія сирого HTTP-запиту (Raw HTTP Request)
HTTP/1.1 запит є текстовим протоколом, що складається з трьох обов'язкових частин:

```http
POST /api/v1/users HTTP/1.1
Host: api.enterprise-cloud.io
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Content-Type: application/json; charset=utf-8
Content-Length: 68
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Accept: application/json

{
  "username": "dperov_ai",
  "email": "dperov@example.com",
  "role": "DEVELOPER"
}
```

1. **Стартовий рядок (Request Line)**:
   - **Метод (HTTP Method)**: дія, яку клієнт просить виконати (`POST`, `GET`, `PUT`, `DELETE`, `PATCH`).
   - **Шлях до ресурсу (Request URI / Path)**: `/api/v1/users` (може містити Query Parameters, наприклад, `?limit=10&page=2`).
   - **Версія протоколу**: `HTTP/1.1` (або узгоджується через ALPN для HTTP/2/3).
2. **Заголовки запиту (Request Headers)**: пари ключ-значення, що передають метадані про клієнта, параметри аутентифікації, очікувані формати даних та правила кешування. Заголовки відокремлюються від тіла пустим рядком `
`.
3. **Тіло запиту (Request Body / Payload)**: безпосередні дані операції. Може бути відсутнім у методах `GET` та `DELETE`.

## 2. Семантика HTTP-методів: Безпечність та Ідемпотентність

Стандарт RFC 9110 визначає суворі математичні правила поведінки серверних обробників для кожного методу:

| Метод | Основне призначення | Безпечний (Safe)? | Ідемпотентний (Idempotent)? | Наявність Body |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | Отримання представлення ресурсу | **ТАК** | **ТАК** | Не рекомендується |
| **HEAD** | Отримання лише заголовків ресурсу (перевірка розміру/дати) | **ТАК** | **ТАК** | Заборонено |
| **POST** | Створення нового підпорядкованого ресурсу або запуск процесу | **НІ** | **НІ** | Зазвичай присутнє |
| **PUT** | Повна заміна ресурсу або створення за відомим URI | **НІ** | **ТАК** | Обов'язкове |
| **PATCH** | Часткова точкова модифікація існуючого ресурсу | **НІ** | **НІ** (у загальному) | Обов'язкове |
| **DELETE** | Видалення вказаного ресурсу | **НІ** | **ТАК** | Рідко |
| **OPTIONS** | Запит підтримуваних серверних методів та параметрів CORS | **ТАК** | **ТАК** | Заборонено |

### Чому концепція ідемпотентності критично важлива?
Операція називається **ідемпотентною**, якщо результат багаторазового виконання ідентичного запиту є точно таким самим, як результат одноразового виконання:
`f(f(x)) = f(x)`.
- Якщо мережевий запит `DELETE /api/v1/files/42` обірвався через збій зв'язку, клієнт може безпечно надіслати його повторно. Навіть якщо перший запит насправді видалив файл, повторний запит поверне статус, але стан системи не скомпрометується.
- Якщо повторно надіслати `POST /api/v1/payments`, без спеціальних механізмів (Idempotency Key) сервер створить другий платіж і спише кошти двічі!

## 3. Класифікація та семантика статус-кодів HTTP

Сервер зобов'язаний інформувати клієнта про результат операції через стандартизовані тризначні коди:

- **1xx (Інформаційні)**: Проміжний стан (`101 Switching Protocols` при переході на WebSocket).
- **2xx (Успішні)**:
  - `200 OK`: Стандартний успішний запит із поверненням даних.
  - `201 Created`: Ресурс успішно створено (обов'язковий заголовок `Location`).
  - `204 No Content`: Запит виконано успішно, але тіло відповіді порожнє (типово для `DELETE`).
- **3xx (Перенаправлення)**:
  - `301 Moved Permanently`: Постійне перенаправлення (кешується браузером).
  - `304 Not Modified`: Ресурс не змінився з часу останнього запиту (використовується локальний кеш).
- **4xx (Помилки клієнта)**:
  - `400 Bad Request`: Синтаксична помилка або невалідний JSON.
  - `401 Unauthorized`: Клієнт не автентифікований (відсутній або невалідний токен).
  - `403 Forbidden`: Клієнт автентифікований, але не має прав доступу до даного ресурсу.
  - `404 Not Found`: Запитуваний ресурс не знайдено на сервері.
  - `422 Unprocessable Entity`: Синтаксис валідний, але порушено бізнес-правила (помилка валідації полів).
  - `429 Too Many Requests`: Перевищено ліміт частоти запитів (Rate Limit).
- **5xx (Помилки сервера)**:
  - `500 Internal Server Error`: Неперехоплений виняток у програмному коді бекенду.
  - `502 Bad Gateway`: Проксі-сервер отримав невалідну відповідь від бекенд-сервісу.
  - `503 Service Unavailable`: Сервер перевантажений або знаходиться на технічному обслуговуванні.
  - `504 Gateway Timeout`: Шлюз не дочекався відповіді від внутрішнього сервісу за відведений час.


## Практичний інженерний розбір: Повний цикл розробки та захисту REST API ендпоінта

Розглянемо практичний сценарій створення виробничого REST API ендпоінта для обробки транзакцій замовлень на базі сучасного стеку (Node.js/Express або Python/FastAPI) з дотриманням принципів Clean Architecture, валідацією DTO, обробкою помилок та авторизацією через JWT:

### 1. Архітектурне проектування контракту ендпоінта
- **Метод та URI**: `POST /api/v1/orders`
- **Заголовки**: `Authorization: Bearer <jwt_token>`, `Idempotency-Key: <uuidv4>`, `Content-Type: application/json`
- **Коди відповідей**:
  - `201 Created`: Замовлення успішно створено, повертається DTO створеного ресурсу та заголовок `Location: /api/v1/orders/{id}`.
  - `400 Bad Request`: Помилка синтаксису JSON або відхилення бізнес-правил.
  - `401 Unauthorized`: Відсутній або невалідний JWT токен.
  - `403 Forbidden`: Користувач не має ролі або прав для створення замовлення від імені організації.
  - `409 Conflict`: Повторний запит із тим самим `Idempotency-Key`, обробка якого ще триває або призвела до конфлікту.
  - `422 Unprocessable Entity`: Помилка валідації схеми вхідних даних (відсутнє обов'язкове поле або невірний формат).

### 2. Виробничий код реалізації (TypeScript / Express з валідацією Zod)
```typescript
import { Request, Response, NextFunction, Router } from 'express';
import { z } from 'zod';

// Схема валідації вхідних даних (DTO)
export const CreateOrderSchema = z.object({
  customerId: z.string().uuid({ message: "customerId повинен бути валідним UUIDv4" }),
  items: z.array(z.object({
    productId: z.string().uuid(),
    quantity: z.number().int().positive({ message: "Кількість повинна бути більшою за 0" }),
    unitPrice: z.number().positive()
  })).min(1, { message: "Замовлення повинно містити хоча б один товар" }),
  shippingAddress: z.object({
    country: z.string().min(2).max(2),
    city: z.string().min(1),
    street: z.string().min(1),
    postalCode: z.string().regex(/^[0-9]{5}$/, { message: "Поштовий індекс має складатись з 5 цифр" })
  })
});

export type CreateOrderDTO = z.infer<typeof CreateOrderSchema>;

export const orderRouter = Router();

orderRouter.post('/api/v1/orders', async (req: Request, res: Response, next: NextFunction) => {
  try {
    // 1. Валідація Idempotency-Key
    const idempotencyKey = req.header('Idempotency-Key');
    if (!idempotencyKey) {
      return res.status(400).json({
        type: "https://api.enterprise.com/errors/missing-header",
        title: "Missing Required Header",
        status: 400,
        detail: "Заголовок 'Idempotency-Key' є обов'язковим для уникнення дублювання платежів."
      });
    }

    // 2. Валідація тіла запиту через Zod
    const validatedData: CreateOrderDTO = CreateOrderSchema.parse(req.body);

    // 3. Виклик бізнес-логіки через сервісний шар
    // const order = await orderService.createOrder(validatedData, req.user.id, idempotencyKey);
    const mockCreatedOrder = {
      id: "ord_9f8c12a4",
      status: "PENDING_PAYMENT",
      totalAmount: validatedData.items.reduce((sum, item) => sum + item.quantity * item.unitPrice, 0),
      createdAt: new Date().toISOString()
    };

    // 4. Повернення успішної відповіді згідно зі стандартом REST
    res.setHeader('Location', `/api/v1/orders/${mockCreatedOrder.id}`);
    return res.status(201).json({
      success: true,
      data: mockCreatedOrder,
      links: {
        self: `/api/v1/orders/${mockCreatedOrder.id}`,
        payment: `/api/v1/orders/${mockCreatedOrder.id}/payments`
      }
    });
  } catch (error) {
    if (error instanceof z.ZodError) {
      return res.status(422).json({
        type: "https://api.enterprise.com/errors/validation-error",
        title: "Validation Error",
        status: 422,
        invalidParams: error.issues.map(err => ({
          name: err.path.join('.'),
          reason: err.message
        }))
      });
    }
    next(error);
  }
});
```


## Поглиблений архітектурний практикум: Побудова стійкої та масштабованої серверної архітектури

У сучасній enterprise-розробці створення серверної логіки та проектування API вимагає суворого дотримання інженерних принципів надійності, безпеки та продуктивності. Розглянемо детальний архітектурний конвеєр обробки запитів:

```
[Клієнтський запит: Web / Mobile / IoT]
                 │
                 ▼
[Edge Layer / CDN: Cloudflare / AWS CloudFront] ──> DDoS Protection, Edge Caching, TLS 1.3 Termination
                 │
                 ▼
[Reverse Proxy / WAF: Nginx / Envoy / Traefik] ──> Rate Limiting (Token Bucket), IP Whitelist, SSL Decryption
                 │
                 ▼
[API Gateway: Kong / AWS API Gateway] ───────────> JWT Validation, Route Dispatching, Metrics (Prometheus)
                 │
                 ▼
[Middleware Pipeline] ───────────────────────────> CORS, Request Logging (Correlation ID), Body Parser, Zod/Joi Validation
                 │
                 ▼
[Controller / Handler Layer] ────────────────────> HTTP Semantics, Status Codes, DTO Transformation
                 │
                 ▼
[Application / Service Layer (Domain Logic)] ────> Бізнес-правила, транзакційні межі, виклики AI-моделей
                 │
                 ▼
[Data Access / Repository Layer] ────────────────> ORM / Query Builder, Read/Write Replicas, Redis Cache
                 │
                 ▼
[Database / External Services] ──────────────────> PostgreSQL, MongoDB, Stripe API, OpenAI API
```

### Комплексна інженерна матриця валідації та оптимізації серверних систем

| Вектор інженерного контролю | Критичні фактори ризику | Стандарти та патерни вирішення | Інструменти автоматизації |
| :--- | :--- | :--- | :--- |
| **Архітектура API** | Невідповідність REST-семантиці, відсутність версіонування | Richardson Maturity Model (Level 3: HATEOAS), версіонування через URI (`/api/v1/`) | Spectral linter, OpenAPI 3.1, Swagger Editor |
| **Безпека (OWASP API Top 10)** | BOLA (Broken Object Level Authorization), ін'єкції SQL/NoSQL | RBAC/ABAC авторизація на рівні сервісу, параметризовані запити ORM | Snyk, OWASP ZAP, Prisma/TypeORM |
| **Продуктивність та масштабованість** | Проблема N+1 у базі даних, блокуючі I/O операції | Асинхронний неблокуючий I/O (Node.js Event Loop / FastAPI), пул з'єднань, Redis кешування | DataLoader, Redis, k6, Autocannon |
| **Стійкість та відмовостійкість** | Каскадне падіння залежних мікросервісів, вичерпання ресурсів | Патерни Circuit Breaker, Retry з Exponential Backoff, Idempotency Keys | Resilience4j, Cockatiel, BullMQ |
| **Надійність обміну даними** | Невідповідність типів між клієнтом і сервером, silent failures | Сувора валідація схем JSON (JSON Schema Draft 2020-12, Zod, Pydantic) | Zod, TypeScript Compiler, Postman Newman |

### Типові інженерні антипатерни backend-розробки та стратегії їх ліквідації:
1. **Антипатерн «Fat Controller (Товстий контролер)»**:
   - *Проблема*: Розміщення складної бізнес-логіки, розрахунків та прямих запитів до бази даних безпосередньо у функціях обробки HTTP-маршрутів.
   - *Вирішення*: Розподіл обов'язків за принципами Clean Architecture: контролер лише витягує дані із запиту та повертає HTTP-відповідь, а вся логіка інкапсулюється у сервісах та доменних сутностях.
2. **Антипатерн «Неідемпотентні повторні операції»**:
   - *Проблема*: Повторне відправлення мережевого запиту (через обрив зв'язку або подвійний клік) призводить до подвійного списання коштів або дублювання записів.
   - *Вирішення*: Впровадження обов'язкового заголовка `Idempotency-Key` (UUIDv4) з кешуванням результату первинної транзакції в Redis на 24 години.
3. **Антипатерн «Синхронне блокування важкими завданнями»**:
   - *Проблема*: Генерація великих PDF-звітів, обробка зображень чи виклик тривалих AI LLM API блокує чергу обробки запитів веб-сервера.
   - *Вирішення*: Патерн асинхронної обробки з чергами (Task Queues: Celery, BullMQ, RabbitMQ) та повернення HTTP `202 Accepted` з посиланням на статус завдання.


## Інженерні стандарти та специфікації серверного коду (Enterprise Server Standards)

При розробці бекенд-інфраструктури та API інженер зобов'язаний спиратися на стандартизовані міжнародні протоколи:
1. **RFC 9110 (HTTP Semantics)**:
   - Семантичне розмежування методів: `GET` та `HEAD` є безпечними (Safe) та не повинні модифікувати стан сервера.
   - Метод `PUT` повністю замінює цільовий ресурс (Full Replacement), тоді як `PATCH` здійснює часткову модифікацію (Partial Modification).
   - Ідемпотентність: повторний виклик `GET`, `PUT`, `DELETE` з однаковими параметрами повинен залишати систему в тому самому стані, що й одиничний виклик.
2. **RFC 7519 (JSON Web Token - JWT)**:
   - Структура токена: `Header.Payload.Signature` у форматі Base64Url.
   - Захист від критичних вразливостей: обов'язкова перевірка алгоритму підпису (`alg !== "none"`) та валідація клеймів `exp` (час життя), `iss` (емітент) та `aud` (аудиторія).
3. **OpenAPI Specification (OAS 3.1)**:
   - Повна синхронізація схеми даних із JSON Schema Draft 2020-12, опис безпекових схем (OAuth2, Bearer, API Keys) та підтримка автоматичної кодогенерації клієнтів.

## Архітектурний шаблон Enterprise-рівня: Від клієнта до сховища даних

## Стандарти безпеки API та захист даних (API Security & Compliance)

При передачі та обробці даних серверний застосунок зобов'язаний дотримуватися принципів Zero Trust та регламентів безпеки:
- **Захист від ін'єкцій (CWE-89 / CWE-79)**: Сувора заборона конкатенації рядків при формуванні SQL чи NoSQL запитів. Використання параметризованих викликів або типізованих ORM (Prisma, TypeORM, SQLAlchemy).
- **Шифрування даних під час передачі (In-Transit Encryption)**: Обов'язкове примусове використання протоколу TLS 1.3 з відключенням застарілих шифрів TLS 1.0/1.1 та налаштуванням заголовка HSTS (`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`).
- **Захист від витоку чутливих даних (Data Masking)**: Автоматичне маскування номерів банківських карток (залишати лише перші 6 та останні 4 цифри), паспортних даних та паролів у системних логах сервера.


## Індустріальний аналіз: Як провідні технологічні гіганти будують свої API

Розглянемо практичні підходи лідерів світової IT-індустрії до проектування API:
- **Stripe**: Визнаний золотим стандартом у дизайні REST API. Ключові принципи: передбачувані URLs, широке використання HTTP-методів, обов'язковий механізм ідемпотентності через заголовки, версіонування через фіксовану дату (наприклад, `Stripe-Version: 2023-10-16`) та деталізовані описи помилок.
- **GitHub**: Використання змішаної моделі (REST API v3 та GraphQL API v4). Зручна пагінація через заголовки `Link`, суворе обмеження частоти запитів (Rate Limiting) з поверненням заголовків `X-RateLimit-Limit`, `X-RateLimit-Remaining` та `X-RateLimit-Reset`.
- **Netflix**: Перехід від монолітних API до мікросервісних шлюзів (Zuul, Spring Cloud Gateway) з динамічною маршрутизацією, фільтрацією запитів та захистом через Circuit Breaker (Hystrix / Resilience4j).

## Підсумковий чеклист готовності серверного API до релізу (Production Readiness Checklist)

Перед розгортанням API на продакшн інженер повинен підтвердити виконання наступних пунктів:
- [ ] Всі ендпоінти використовують коректні HTTP-методи згідно з їх семантикою та ідемпотентністю.
- [ ] Реалізовано централізований Middleware для обробки помилок без витоку деталей стек-трейсу.
- [ ] Впроваджено сувору валідацію вхідних DTO через Zod/Pydantic із поверненням статусу 422.
- [ ] Налаштовано автентифікацію через JWT та авторизацію прав доступу на рівні окремих ресурсів (BOLA check).
- [ ] Впроваджено Rate Limiting та захист від повторних запитів через `Idempotency-Key`.
- [ ] Оновлено та верифіковано OpenAPI 3.1 специфікацію.


## Експертний аналіз реального інциденту: Як помилка в обробці статусів ледь не призвела до втрати $2.4M

У 2022 році великий фінтех-стартап зазнав критичного збою під час розпродажу Black Friday. Розглянемо деталі інциденту:
1. **Симптом**: Клієнти скаржилися на подвійне списання коштів, а баланс складських залишків пішов у мінус.
2. **Коренева причина (Root Cause)**: Клієнтський застосунок при отриманні відповіді від платіжного сервісу надсилав повторний запит, якщо сервер відповідав довше ніж 3 секунди. На бекенді ендпоінт `POST /api/v1/payments` НЕ використовував `Idempotency-Key` та не перевіряв статус вже запущеної транзакції в Redis. В результаті один клік генерував до 4 списань.
3. **Виправлення та архітектурний захист**:
   - Впроваджено обов'язковий фільтр `Idempotency-Key` на рівні API Gateway.
   - Створено таблицю блокувань у Redis із блокуванням повторних викликів на час виконання первинного запиту (Distributed Lock).
   - Оновлено семантику статус-кодів: повернення `409 Conflict` або `202 Accepted` при виявленні паралельної обробки.


## Інженерні метрики ефективності та надійності серверної частини

Для оцінки якості серверної логіки та продуктивності API використовуються об'єктивні числові метрики:
- **Метрики латентності (Latency Percentiles)**:
  - `P50 (Median)`: Час відгуку для 50% користувачів (цільове значення: < 80мс).
  - `P95 / P99`: Час відгуку для 95-99% користувачів з урахуванням складних запитів та навантаження (цільове: < 300мс).
- **Частота помилок (Error Rate)**: Відсоток відповідей зі статусами 5xx відносно загальної кількості запитів (цільове: < 0.05%).
- **Пропускна здатність (RPS / Throughput)**: Кількість успішно оброблених запитів за секунду при нормальному навантаженні.
- **DORA Metrics**: Deployment Frequency (частота релізів) та Lead Time for Changes (час від коміту до продакшну).


## Діалоговий воркфлоу взаємодії інженера з AI-асистентом при проектуванні API

Приклад ефективного багатокрокового діалогу (Prompt Chaining) інженера з моделлю:
1. **Крок 1 (Концептуалізація контракту)**:
   > *Інженер*: «Спроектуй RESTful ендпоінти для системи управління бронюванням номерів у готелі. Врахуй вимоги до пошуку вільних дат, створення броні та її скасування. Надай схему у форматі Markdown таблиці з методами, шляхами та статус-кодами».
   > *AI*: Формує структуру: `GET /rooms`, `POST /bookings`, `DELETE /bookings/{id}` із відповідними статусами (200, 201, 204).
2. **Крок 2 (Генерація безпекових правил)**:
   > *Інженер*: «Тепер напиши Middleware для валідації ролей (RBAC) на базі Express, який перевіряє, чи має користувач право скасовувати бронювання. Додай обробку прострочених JWT токенів».
   > *AI*: Створює типізований Middleware з перевіркою `req.user.role` та коректним поверненням 401/403.

Опанування теми **«HTTP та принципи обміну даними»** є ключовим будівельним блоком у професійному становленні спеціаліста за напрямком **AI Developer**. Системне застосування розглянутих методологій дозволяє:
