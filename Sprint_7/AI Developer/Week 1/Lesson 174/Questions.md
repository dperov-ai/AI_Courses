# Контрольні запитання до Уроку 174: REST API

Даний блок містить перелік аналітичних та практичних запитань для самоконтролю, перевірки глибини засвоєння матеріалу та підготовки до технічних інтерв’ю.

---

### 1. Які 6 ключових архітектурних обмежень визначають стиль REST за Роєм Філдінгом?

**Відповідь:** 1. Клієнт-Серверна архітектура; 2. Відсутність збереження стану (Stateless); 3. Підтримка кешування (Cacheable); 4. Уніфікований інтерфейс (Uniform Interface); 5. Багаторівнева система (Layered System); 6. Код за вимогою (Code on Demand — опціонально).

---

### 2. Чому в іменуванні REST-ендпоінтів суворо заборонено використовувати дієслова (наприклад, /getUsers чи /deleteOrder)?

**Відповідь:** Тому що дієслово вже закодовано в самому HTTP-методі (GET, DELETE). Ендпоінт повинен позначати іменник — сутність або колекцію сутностей у множині (наприклад, GET /users, DELETE /orders/{id}).

---

### 3. Що описує модель зрілості Річардсона (Richardson Maturity Model)?

**Відповідь:** Вона класифікує підходи до проектування веб-сервісів на 4 рівні: Рівень 0 (The Swamp of POX, єдиний ендпоінт), Рівень 1 (Окремі URI ресурсів), Рівень 2 (Стандартні HTTP-методи та статус-коди), Рівень 3 (HATEOAS, гіпермедіа-навігація).

---

### 4. Що таке HATEOAS і яку перевагу воно надає клієнтському застосунку?

**Відповідь:** HATEOAS (Hypermedia As The Engine Of Application State) — це підхід, коли у відповіді сервера передаються гіперпосилання на подальші можливі дії (наприклад, 'links: { pay: "...", cancel: "..." }'). Це дозволяє клієнту адаптуватися до змін бізнес-логіки бекенду без жорсткого хардкоду URL.

---

### 5. Як правильно проектувати ієрархічні зв'язки між сутностями в REST API?

**Відповідь:** Через вкладені шляхи: /users/{userId}/orders для колекції замовлень конкретного користувача або /users/{userId}/orders/{orderId} для конкретного замовлення. При глибині більше двох рівнів рекомендується скорочувати до плоских маршрутів (/orders/{orderId}).

---

### 6. Чому обмеження Stateless є фундаментальним для горизонтального масштабування бекенду?

**Відповідь:** Коли сервер не зберігає стан сесії між запитами, будь-який серверний вузол у кластері може обробити будь-який запит клієнта. Це дозволяє легко додавати або видаляти сервери за балансувальником навантаження без розриву користувацьких сесій.

---

### 7. У чому різниця між пагінацією на основі зміщення (Offset/Limit) та курсорною пагінацією (Cursor-based)?

**Відповідь:** Offset-пагінація проста у реалізації (OFFSET 20 LIMIT 10), але працює повільно на великих обсягах даних і призводить до дублікатів чи пропусків при додаванні нових записів. Cursor-пагінація використовує унікальний покажчик останнього елемента (WHERE id > last_seen_id LIMIT 10), працює за фіксований час O(1) за індексом і стійка до мутацій даних.

---

### 8. Як правильно передавати параметри фільтрації та сортування в REST API?

**Відповідь:** Через Query Parameters (рядок запиту після знака '?'): наприклад, /api/v1/products?category=electronics&minPrice=100&sort=-rating.

---

### 9. Що таке Self-Descriptive Messages (Самоописові повідомлення) в REST?

**Відповідь:** Це вимога, згідно з якою кожне повідомлення містить достатньо інформації про те, як його обробляти (через MIME-типи у заголовках Content-Type, інструкції кешування Cache-Control та параметри довжини Content-Length).

---

### 10. Як у REST API позначається версіонування і які є альтернативні підходи?

**Відповідь:** Найпопулярніший і найнадійніший підхід — через префікс шляху URI (/api/v1/users). Альтернативні підходи: через кастомні заголовки (X-API-Version: 2) або через заголовок Accept (Accept: application/vnd.company.v2+json).

---

### 11. Який HTTP-метод слід використовувати для операції пошуку з великою кількістю складних фільтрів?

**Відповідь:** Зазвичай використовується GET з Query-параметрами. Проте якщо фільтр містить масивні структури або перевищує ліміт довжини URL (близько 2048 символів), використовують POST на спеціальний ендпоінт (наприклад, POST /api/v1/orders/search).

---

### 12. Чому REST API часто називають ресурсо-орієнтованим (Resource-Oriented)?

**Відповідь:** Тому що в центрі архітектури знаходиться робота з іменниками-ресурсами та їх колекціями, на відміну від RPC (Remote Procedure Call), де взаємодія будується навколо виклику віддалених функцій та процедур.

---

### 13. Як обробляти масові операції (Bulk Operations) у RESTful манері?

**Відповідь:** Створюється спеціальний ендпоінт колекції або ресурсу завдання, наприклад, POST /api/v1/invoices/bulk-delete або POST /api/v1/bulk-jobs з передачею списку ID у тілі запиту.

---

### 14. Що повинна повертати успішна відповідь на запит DELETE /api/v1/users/42?

**Відповідь:** Статус 204 No Content з порожнім тілом або статус 200 OK з коротким підтверджуючим об'єктом {'success': true, 'deletedId': 42}.

---

### 15. Яким чином REST API вирішує проблему циклічних посилань у JSON представленнях?

**Відповідь:** Через обмеження глибини вкладеності сутностей у DTO та повернення ID замість повних об'єктів для пов'язаних ресурсів.

---

### 16. Чи є протокол HTTP обов'язковим для реалізації стилю REST?

**Відповідь:** Теоретично ні: REST є архітектурним стилем і може бути реалізований поверх інших протоколів. Проте на практиці 99.9% REST API реалізовані саме поверх протоколу HTTP.

---

### 17. Як правильно оформити ендпоінт для завантаження файлу в REST API?

**Відповідь:** Використовується метод POST /api/v1/files з заголовком 'Content-Type: multipart/form-data' або отримання попередньо підписаного URL (Presigned URL) для прямого завантаження у хмарне сховище (AWS S3).

---

### 18. Що таке API Gateway і яку роль він відіграє в архітектурі REST API?

**Відповідь:** Це точка входу в систему, яка бере на себе маршрутизацію запитів, автентифікацію, обмеження частоти (Rate Limiting), аналітику та агрегацію мікросервісних відповідей для клієнта.

---

### 19. Яким чином оформлюються ресурси типу 'підтвердження замовлення', якщо це дія, а не сутність?

**Відповідь:** Дію моделюють як створення підпорядкованого ресурсу стану, наприклад, POST /api/v1/orders/10/confirmations або PATCH /api/v1/orders/10 з полем {'status': 'CONFIRMED'}.

---

### 20. У чому полягає різниця між REST та GraphQL підходами?

**Відповідь:** У REST клієнт викликає фіксовані ендпоінти зі заздалегідь визначеною структурою відповіді сервера. У GraphQL клієнт звертається до єдиного ендпоінта і сам формує запит, вказуючи точний список полів, які необхідно повернути.

---
