# Практичні завдання до Уроку 172: Призначення серверної частини застосунку

Практичний блок розроблено для закріплення навичок роботи з AI-інструментами, аналізу реальних виробничих кейсів та створення професійних артефактів.

---

## Завдання 1: Архітектурний аудит та декомпозиція обов'язків клієнта та сервера

**Мета:** Навчитися визначати межу довіри (Trust Boundary), класифікувати обов'язки та проектувати безпечну взаємодію між клієнтом і сервером.

**Вхідний контекст та бізнес-сценарій:**
Ви проектуєте сервіс цифрової підписки на курси з AI. Користувач обирає план, вводить промокод на знижку, заповнює реквізити картки та отримує доступ до відеоматеріалів. Необхідно створити матрицю відповідальності та спроектувати захищену архітектуру.

**Покроковий алгоритм виконання:**
1. Складіть таблицю з 6 операцій процесу оплати та визначте, де саме повинна виконуватись кожна дія (Client vs Server).
2. Сформулюйте перелік із 3 потенційних критичних вразливостей, які виникнуть, якщо розрахунок знижки або перевірку оплати довірити фронтенду.
3. Складіть перелік секретів та конфігураційних змінних, які категорично заборонено передавати у клієнтський бандл.

**Рекомендований системний AI-промпт:**
```text
Дій як Senior Backend Architect. Проаналізуй наступний бізнес-процес оформлення підписки на платформу. Склади архітектурну матрицю розподілу обов'язків між Frontend та Backend, вкажи механізми збереження безпеки та опиши покроковий життєвий цикл запиту від кліка до активації доступу в базі даних.
```

**Очікуваний результат:**
Документ з деталізованою матрицею відповідальності, списком векторів загроз та структурою змінних середовища для бекенду.

**Критерії самоперевірки та оцінювання:**
- [ ] Чітке розмежування обов'язків без передачі довіри клієнту
- [ ] Описано захист від підміни ціни та підробки промокоду
- [ ] Вказано перелік обов'язкових змінних середовища (.env) для бекенду

## Завдання 2: Проектування архітектурної схеми серверної частини застосунку

**Мета:** Побудувати надійну трирівневу архітектуру серверного сервісу з використанням інструментів діаграмування.

**Вхідний контекст та бізнес-сценарій:**
Створіть архітектурну модель для бекенду системи обробки заявок клієнтів із використанням reverse proxy, API Gateway, мікросервісів та бази даних.

**Покроковий алгоритм виконання:**
1. Опишіть у текстовому або Mermaid-форматі шлях проходження HTTP-запиту від браузера до бази даних.
2. Виділіть рівні контролерів, бізнес-сервісів та репозиторіїв бази даних.
3. Опишіть механізм відмовостійкості: що відбувається, якщо база даних тимчасово недоступна.

**Рекомендований системний AI-промпт:**
```text
Створи детальну архітектурну діаграму Mermaid для бекенд-системи обробки замовлень. Включи рівні Nginx, API Gateway, Node.js сервісу, Redis кешу та PostgreSQL. Додай пояснення до кожного компонента.
```

**Очікуваний результат:**
Валідна Mermaid діаграма та текстовий супровід з описом функцій кожного архітектурного шару.

**Критерії самоперевірки та оцінювання:**
- [ ] Синтаксично коректна діаграма Mermaid
- [ ] Присутні шари кешування та реляційної бази даних
- [ ] Описано поведінку системи при помилках підключення
