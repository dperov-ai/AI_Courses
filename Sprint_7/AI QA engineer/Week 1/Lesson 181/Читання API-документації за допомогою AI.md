# Урок 181: Читання API-документації за допомогою AI

## Вступ: Документація API як джерело тестових вимог

Для QA-інженера документація API (найчастіше представлена у форматах Swagger UI, ReDoc або сирих файлах OpenAPI 3.0/3.1 у YAML/JSON) є основним джерелом істини та технічних вимог. Проте в умовах швидкої розробки специфікації API часто містять сотні ендпоінтів, десятки вкладених моделей даних, неявні бізнес-обмеження та сліпі зони, які легко пропустити при ручному читанні.

Використання генеративного штучного інтелекту трансформує процес аналізу документації. AI-асистент здатен за лічені секунди розібрати складну специфікацію на 5000 рядків, знайти логічні нестиковки між моделями, виявити відсутність описів помилок та автоматично згенерувати готову матрицю тестування.

У цьому уроці ми навчимося ефективно читати та деконструювати специфікації OpenAPI, використовувати LLM для реверс-аналізу вимог, ставити точні діагностичні промпти та перетворювати специфікацію на детальний план тестування.

## 1. Анатомія специфікації OpenAPI 3.1: Що шукає тестувальник?

Специфікація OpenAPI складається з кількох ключових розділів, кожен з яких містить критичні дані для тестування:

```
[openapi: 3.1.0]  <-- Версія стандарту
       │
[info] ─────────────> Базова назва, версія API, ліцензія
       │
[servers] ──────────> Базові URL оточень (Local, Dev, Staging, Prod)
       │
[paths] ────────────> КАРТА МАРШРУТІВ ТА ОПЕРАЦІЙ:
       ├── parameters (Path, Query, Header, Cookie)
       ├── requestBody (Required, Content-Type, Schema)
       └── responses (200, 201, 400, 401, 403, 404, 422, 500)
       │
[components] ───────> БІБЛІОТЕКА ПОВТОРНО ВИКОРИСТОВУВАНИХ СХЕМ:
       ├── schemas (Моделі даних: User, Order, ErrorResponse)
       ├── securitySchemes (BearerAuth, ApiKeyAuth, OAuth2)
       └── examples (Реалістичні зразки даних)
```

### На що QA звертає першочергову увагу:
1. **Обов'язковість полів (`required: [...]`)**: Чи чітко позначено обов'язкові параметри? Що станеться, якщо їх не передати?
2. **Типи та формати (`type`, `format`)**: Чи вказано формат для рядків (`format: email`, `format: uuid`, `format: date-time`)? Які мінімальні та максимальні межі чисел (`minimum`, `maximum`)?
3. **Обмеження регулярних виразів (`pattern`)**: Чи обмежено формат телефонів чи паролів?
4. **Схеми помилок у секції `responses`**: Чи описані відповіді 401, 403, 422? Якщо в документації описано лише 200 OK — це прямий сигнал про неповноту специфікації.

## 2. AI-методологія аналізу OpenAPI специфікацій

При роботі з великими специфікаціями AI виступає інтелектуальним аудитором документації. Застосовується триступеневий підхід:

1. **Етап 1: Валідація повноти контракту (Contract Completeness Audit)**:
   AI перевіряє, чи для всіх операцій описано схеми помилок, чи немає "висячих" моделей у `components`, які ніде не використовуються.
2. **Етап 2: Синтез граничних значень (Boundary Value Analysis)**:
   AI сканує поля типу `integer`, `string` та генерує список екстремальних тестових значень (мін-1, мін, макс, макс+1, порожній рядок, спецсимволи, null).
3. **Етап 3: Генерація матриці перехресних залежностей (State Dependency Matrix)**:
   AI аналізує зв'язки між ендпоінтами: які запити необхідно виконати попередньо (створити користувача -> отримати токен -> поповнити баланс -> створити замовлення).

│                           │                   │ HTTP-статус  │                                          │

│ 1. Happy Path (Валідний)  │ Вірні email/пароль│ 200 OK       │ JWT токен валідний, expiresIn > 0,       │

### 2. Автоматизований перевірочний скрипт у середовищі Postman / Newman
```javascript
// Postman Test Scripts: валідація статусу, заголовків, безпеки та JSON Schema
pm.test("Status code is 200 OK", function () {
    pm.response.to.have.status(200);
});

pm.test("Response time is acceptable (under 400ms)", function () {
    pm.expect(pm.response.responseTime).to.be.below(400);
});

pm.test("Security Headers are enforced", function () {
    pm.response.to.have.header("Content-Security-Policy");
    pm.response.to.have.header("X-Content-Type-Options", "nosniff");
    pm.expect(pm.response.headers.get("Cache-Control")).to.include("no-store");
});

pm.test("JSON Schema and Payload Integrity", function () {
    const responseJson = pm.response.json();
    
    // Перевірка базових типів
    pm.expect(responseJson).to.be.an('object');
    pm.expect(responseJson.token).to.be.a('string');
    pm.expect(responseJson.user).to.be.an('object');
    pm.expect(responseJson.user.id).to.match(/^[0-9a-fA-F-]{36}$/);
    
    // Сувора перевірка відсутності сенситивних даних
    pm.expect(responseJson.user).to.not.have.property('password');
    pm.expect(responseJson.user).to.not.have.property('passwordHash');
    pm.expect(responseJson.user).to.not.have.property('salt');
});
```


## Комплексна методологія забезпечення якості API: Від специфікації до контрактного тестування

Робота QA інженера над тестуванням серверних інтерфейсів, валідацією контрактів та аналізом помилок вимагає системного підходу, що виходить далеко за рамки простих ручних запитів у Postman:

```
[Аналіз документації API (OpenAPI / Swagger / Stoplight)]
                       │
                       ▼
[Побудова матриці тестового покриття (Happy Path, Boundary, Negative, Security)]
                       │
                       ▼
[Валідація структури даних (JSON Schema Validation & Data Types)]
                       │
                       ▼
[Контрактне тестування (Consumer-Driven Contract Testing: Pact)]
                       │
                       ▼
[Аналіз кодів відповідей, заголовків безпеки та часу відгуку (SLA)]
                       │
                       ▼
[Тестування авторизації та розмежування прав (BOLA / BFLA матриця)]
                       │
                       ▼
[Формування вичерпного баг-репорту з cURL, Payload та Network Trace]
```

### Комплексна інженерна матриця валідації API-інтерфейсів

| Категорія тестування | Фокус перевірки | Очікуваний артефакт | Інструменти тестувальника |
| :--- | :--- | :--- | :--- |
| **Синтаксис та типи (Contract)** | Відповідність типів полів (string, number, boolean), наявність обов'язкових полів | Валідований JSON Schema звіт без розбіжностей | Postman Tests (tv4 / Ajv), Spectral, Prism |
| **Семантика HTTP** | Коректне використання статус-кодів (201 Created vs 200 OK, 400 vs 422, 401 vs 403) | Таблиця відповідності бізнес-помилок та HTTP-статусів | Charles Proxy, Fiddler, Postman |
| **Безпека (Security / Auth)** | Доступ без токена, доступ з простроченим JWT, спроба доступу до чужого ресурсу (IDOR) | Матриця доступу за ролями (RBAC Matrix) | Burp Suite Community, OWASP ZAP, Postman Runner |
| **Обробка граничних значень** | Порожні масиви, null, максимальна довжина рядків, emoji, спеціальні символи | Негативні тест-кейси з перевіркою коректного формату помилки | Postman Newman, Python `requests`, Faker |
| **Продуктивність та SLA** | Час генерації відповіді сервером, розмір відповіді (Payload Size), стиснення gzip/br | Звіт швидкодії ендпоінтів під час одиночних та серійних запитів | Postman Performance, k6, Chrome DevTools Network |

### Типові помилки та підводні камені при тестуванні API:
1. **«Ложнопозитивний статус 200 OK з помилкою всередині»**:
   - *Проблема*: Сервер повертає HTTP 200, але в тілі відповіді знаходиться `{"status": "error", "message": "User not found"}`. Це порушує стандарти REST і ламає автоматичні моніторинги.
   - *Вирішення*: Суворе вимагання використання коректних статусів HTTP 4xx/5xx та перевірка коду статусу першим assertion у тестах.
2. **«Тестування виключно Happy Path»**:
   - *Проблема*: Перевірка лише валідних даних створює хибне враження якості; у реальному середовищі збій виникає при першому некоректному типі даних.
   - *Вирішення*: Правило 80/20: на 1 позитивний сценарій має бути не менше 4-5 негативних (відсутність обов'язкових полів, некоректний формат дати, вихід за межі діапазону).
3. **«Ігнорування заголовків безпеки та кешування»**:
   - *Проблема*: Не перевіряються заголовки `Cache-Control`, `Strict-Transport-Security`, `X-Content-Type-Options`, що призводить до витоку персональних даних через кеш проксі-серверів.
   - *Вирішення*: Включення перевірки обов'язкових заголовків у базовий тест-сьют кожного ендпоінта.


## Регламент стандартизації тестування API та дефектів у Enterprise-командах

Тестування API повинно відповідати міжнародним критеріям якості програмного забезпечення:
1. **ISO/IEC/IEEE 29119 (Software Testing Standards)**:
   - Формалізація тестових сценаріїв: кожен API тест повинен містити чіткі передумови (Pre-conditions), вхідні вектори даних, очікувані HTTP-статуси, заголовки та очікувану структуру payload.
2. **OWASP API Security Top 10 (Редакція 2023 року)**:
   - **API1:2023 BOLA (Broken Object Level Authorization)**: Обов'язкова перевірка доступу до ресурсу за чужим ID (наприклад, спроба звернутися до `/api/v1/orders/102` користувачем з ID 105).
   - **API3:2023 Broken Object Property Level Authorization**: Перевірка Mass Assignment (чи може користувач передати `"role": "ADMIN"` при оновленні свого профілю).
   - **API4:2023 Unrestricted Resource Consumption**: Перевірка лімітів кількості елементів у пагінації (`limit=1000000`) та частоти запитів (Rate Limiting).

## Регламент перевірки безпеки API для QA-інженерів

Контрольні процедури безпеки, які мають бути виконані перед випуском API у реліз:
- **Аудит токенів автентифікації**: Перевірка терміну дії (Expiration Time). Відхилення токенів без терміну придатності або з терміном понад 24 години для користувацьких сесій.
- **Тестування обробки невірних заголовків (Fuzzing Headers)**: Перевірка стійкості до підроблених заголовків `X-Forwarded-For`, `Host`, `Origin` (CORS bypass).
- **Перевірка відсутності Stack Trace у публічних відповідях**: Переконатися, що при статусі 500 сервер повертає знеособлений JSON з `correlationId`, а не внутрішню помилку бази даних або шлях до файлу на сервері.


## Індустріальний досвід: Парадигма Shift-Left тестування в Amazon та Google

Як провідні компанії організовують тестування серверних інтерфейсів:
- **Shift-Left Testing**: Тестування починається ще до появи першого рядка коду — на етапі створення специфікації OpenAPI. QA верифікує схеми, бізнес-правила та логічні протиріччя.

## Експертний аналіз: Як відсутність перевірки BOLA дозволила отримати доступ до даних 150 000 пацієнтів

Повчальний випадок із практики аудиту медичного порталу:
1. **Проблема**: Ендпоінт `GET /api/v1/medical-records/{recordId}` коректно перевіряв, чи надав клієнт валідний JWT токен (був автентифікований). Проте сервіс не перевіряв, чи належить запитуваний `recordId` саме тому користувачу, чий `userId` зашитий у токені.
2. **Наслідок**: Заміна одного числа в URL дозволяла будь-якому зареєстрованому пацієнту завантажувати медичні карти інших людей (Класична вразливість OWASP API1: BOLA / IDOR).
3. **Урок для QA**: Кожен тест-план API повинен містити окрему матрицю крос-авторизації: перевірка доступу користувача 'A' до сутностей користувача 'B'.


## Метрики якості тестування API та стабільності релізів

Показники ефективності контролю якості:
- **Defect Detection Percentage (DDP)**: Відсоток дефектів API, виявлених на етапі тестування, відносно тих, що просочилися на продакшн (цільове: > 95%).
- **API Test Coverage**: Відсоток покритих тестами ендпоінтів та їх можливих статус-кодів згідно з OpenAPI специфікацією (цільове: 100% ендпоінтів, > 85% комбінацій параметрів).
- **Time to Triage**: Час від виявлення дефекту до його локалізації та реєстрації в трекері задач.

## Системний синтез та розвиток експертизи в тестуванні API

Розуміння мережевих рівнів та контрактів API формує фундамент для переходу до ролей SDET та Security QA:
- **Глибоке тестування продуктивності**: Перехід від перевірки функціональності до стрес-тестування (Stress, Spike, Soak Testing) через k6 та Locust.
- **DevSecOps інтеграція**: Вбудовування автоматизованих сканерів безпеки API безпосередньо у конвеєр розробки, перетворюючи тестувальника на захисника архітектури.


## Поглиблений інженерний гайд: Комплексна стратегія фаззинг-тестування API

Фаззинг (Fuzz Testing) — це методологія тестування, при якій на вхід API подаються хаотичні, мутовані, несподівані або напівкоректні дані:
1. **Мутаційний фаззинг JSON**:
   Зміна типів полів (передача масиву замість об'єкта, об'єкта замість булевого типу), впровадження глибокої вкладеності (1000 рівнів `{"a": {"a": ...}}` для перевірки на переповнення стеку парсера Stack Overflow).
2. **Граничні вектори вводу**:
   - Рядки довжиною 1 Мб для перевірки обмежень буфера.
   - Спецсимволи Юнікоду (RTL маркери, нульові байти `\0`, символи заміни, емодзі з комбінованими послідовностями).
   - Числа за межами 64-бітних діапазонів (`1e309`, `-1e309`, `NaN`, `Infinity`).
3. **Критерій успіху фаззинг-тесту**:
   Сервер за жодних умов не повинен падати з кодом 500, зависати понад встановлений тайм-аут чи виділяти необмежену пам'ять. Будь-який невалідний ввід повинен детерміновано відхилятися статусом 400 або 422.


## Діагностика відмов та усунення складних дефектів API (QA Debugging Playbook)

Як QA локалізує нестабільні та приховані збої:
- **Тиха деградація відповідей (Silent Contract Drift)**:
  - Сервер повертає HTTP 200, але замість повного об'єкта повертає порожній словник `{}` або пропускає частину полів через збій у дочірньому мікросервісі. Тести без валідації повної JSON-схеми пропускають такий дефект у реліз.
- **Мережеві збої та втрати пакетів (Packet Loss / Connection Drops)**:
  - Використання інструментів емуляції мережевих проблем (Network Throttling у DevTools, toxiproxy, clumsy) для перевірки того, як клієнт і бекенд обробляють обрив з'єднання під час передачі великого JSON тіла.


## Системна інженерія якості: Контрактне тестування та валідація мікросервісів

Масштабування систем вимагає переходу від класичних ізольованих тестів до наскрізної валідації екосистеми:
- **Consumer-Driven Contracts (Pact Framework)**:
  Клієнтські додатки декларують свої очікування від API у вигляді тестів, які генерують контрактний файл (Pact JSON). Бекенд запускає верифікацію цього контракту при кожному Pull Request, що гарантує 100% сумісність перед релізом без необхідності розгортання складних тестових стендів.
- **Аналіз сумісності версій (Backward & Forward Compatibility)**:
  Перевірка того, що старі мобільні клієнти (які не оновлювалися користувачами 6 місяців) продовжують коректно функціонувати з новою версією бекенду завдяки відсутності видалення старих полів.


## Розширена симуляція наскрізного тестування API (End-to-End API Test Choreography)

Сучасний AI QA Operator повинен вміти конструювати складні багатоетапні ланцюжки перевірок, що моделюють реальні користувацькі шляхи крізь розподілену екосистему:

### 1. Верифікація безпеки авторизаційного потоку OAuth 2.0 PKCE
- Тестування кроку генерації `code_verifier` (криптографічний випадковий рядок) та `code_challenge` (SHA-256 хеш).
- Перевірка відхилення спроб авторизації при передачі скомпрометованого або невідповідного `code_verifier`.
- Валідація життєвого циклу токенів: перевірка неможливості використання `access_token` після настання `exp`, тестування безпечного оновлення через `refresh_token` та перевірка повної ануляції прав при відкликанні (Revocation).

### 2. Тестування асинхронних Webhook-повідомлень та валідація цифрового підпису (HMAC)
- **Імітація вхідного вебхуку від платіжної системи**: перевірка обробки поділа `payment.succeeded`.
- **Контроль криптографічного підпису**: перевірка заголовка `X-Signature-SHA256`. QA-інженер симулює атаку «Man-in-the-Middle», модифікуючи суму в тілі запиту без зміни підпису, і переконується, що сервер відповідає `401 Unauthorized` або `400 Bad Request`.
- **Ідемпотентність вебхуків**: перевірка реакції на триразове надсилання одного й того самого вебхуку (сервер повинен повернути `200 OK`, але статус замовлення оновити лише один раз).


## Матриця дефектів та аналізу причин падіння тестів API

| Дефект тесту | Справжня причина | Методика локалізації | Рекомендовані заходи |
| :--- | :--- | :--- | :--- |
| **400 Bad Request при валідному JSON** | Неспівпадіння типів даних у полях (наприклад, рядок `"123"` замість числа `123`) | Валідація тіла запиту проти офіційної JSON Schema у Swagger UI | Оновлення документації контракту, виправлення тестових фікстур |
| **405 Method Not Allowed** | Використання некоректного HTTP дієслова (наприклад, GET замість POST) | Перевірка таблиці маршрутизації в контролері бекенду | Синхронізація тестів з OpenAPI спекою |
| **409 Conflict при паралельних тестах** | Конфлікт унікальних полів (email, username) через спільний стан | Логування тестових payload, перевірка унікальності генерації `faker.internet.email()` | Застосування унікальних префіксів із таймстемпом або ізоляція тестових баз |
| **429 Too Many Requests** | Перевищення квоти викликів Rate Limiting | Аналіз заголовків `Retry-After`, `X-RateLimit-Remaining` | Збільшення таймаутів, використання виділених ключів без обмежень для середовища QA |


## Підсумковий інженерний огляд та практичні рекомендації

Опанування теми **«Читання API-документації за допомогою AI»** є ключовим будівельним блоком у професійному становленні спеціаліста за напрямком **AI QA engineer**. Системне застосування розглянутих методологій дозволяє:
1. **Забезпечити максимальну надійність та стабільність рішень**, спираючись на перевірені індустріальні патерни, міжнародні стандарти та строгі специфікації.
2. **Усунути людський фактор та сліпі зони**, використовуючи матриці контролю якості, автоматизовані тести та перехресну валідацію схем і процесів.
3. **Ефективно інтегрувати сучасні AI-інструменти** у щоденний виробничий конвеєр, виступаючи в ролі кваліфікованого інженера-архітектора, який ставить точні технічні завдання та критично верифікує результат.
