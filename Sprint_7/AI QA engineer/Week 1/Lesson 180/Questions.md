# Контрольні запитання до Уроку 180: Основи HTTP, REST та API для AI QA Operator

Даний блок містить перелік аналітичних та практичних запитань для самоконтролю, перевірки глибини засвоєння матеріалу та підготовки до технічних інтерв’ю.

---

### 1. Чому тестування API вважається більш ефективним та надійним, ніж тестування виключно через UI?

**Відповідь:** Тестування API відбувається безпосередньо на рівні бізнес-логіки без накладних витрат на рендеринг браузера. Воно значно швидше (мілісекунди замість секунд), стабільніше (не залежить від селекторів та змін інтерфейсу) і дозволяє протестувати граничні та безпекові сценарії, які неможливо відтворити через форму UI.

---

### 2. Що означає, коли API повертає HTTP 200 OK, але в тілі міститься об'єкт {'status': 'error'}?

**Відповідь:** Це грубе порушення стандартів REST API та антипатерн. Клієнти, проксі-сервери та системи моніторингу вважають запит успішним, не помічаючи збою. Помилка повинна повертатися з відповідним кодом сімейства 4xx або 5xx.

---

### 3. У чому полягає різниця між кодами помилок 401 Unauthorized та 403 Forbidden для тестувальника?

**Відповідь:** 401 означає відсутність або недійсність аутентифікаційних даних (токен прострочений, відсутній або підроблений). 403 означає, що користувач успішно ідентифікований, але його роль не має прав на виконання цієї конкретної операції.

---

### 4. Який статус-код сервер повинен повертати при успішному створенні ресурсу через POST-запит?

**Відповідь:** 201 Created, бажано із заголовком 'Location', який містить URL новоствореного об'єкта, або з поверненням самого створеного об'єкта в тілі.

---

### 5. Що перевіряє QA при отриманні коду 204 No Content після виклику методу DELETE?

**Відповідь:** Тестувальник перевіряє, що статус-код дорівнює 204, а тіло відповіді повністю порожнє (Content-Length: 0 або відсутнє тіло).

---

### 6. Чому поява коду 500 Internal Server Error майже завжди вважається багом бекенду?

**Відповідь:** 500 означає, що в серверному коді стався неперехоплений виняток (Unhandled Exception), який призвів до аварійного завершення функції. Будь-які помилкові дії користувача повинні оброблятися бекендом і повертати коди 4xx, а не 500.

---

### 7. Як тестувальник перевіряє ідемпотентність методу DELETE?

**Відповідь:** Надсилає запит на видалення одного й того самого ресурсу двічі. Перший запит повинен видалити ресурс (204/200), а другий — підтвердити відсутність ресурсу (404 Not Found або 204), але стан системи не повинен порушуватись.

---

### 8. Яку небезпеку становить наявність стек-трейсу у тілі відповіді зі статусом 500?

**Відповідь:** Стек-трейс розкриває зловмисникам версії бібліотек, файлові шляхи сервера, внутрішні запити до СУБД та логіку застосунку, що значно спрощує планування цільової кібератаки.

---

### 9. Що таке Query Parameters і як QA використовує їх для негативного тестування?

**Відповідь:** Це параметри рядка запиту (?key=value). QA тестує передачу від'ємних значень, спецсимволів, SQL-ін'єкцій, надвеликих чисел та невідповідних типів даних (наприклад, передачу тексту у параметр page=abc).

---

### 10. Що визначає заголовок Content-Type: application/json у запиті?

**Відповідь:** Він інформує сервер, що байти корисного навантаження в тілі запиту повинні інтерпретуватися як структура JSON.

---

### 11. Які заголовки обов'язково перевіряються при тестуванні захищених ендпоінтів?

**Відповідь:** Заголовок 'Authorization: Bearer <token>', а також захисні заголовки відповіді: 'Content-Security-Policy', 'X-Content-Type-Options: nosniff', 'Strict-Transport-Security'.

---

### 12. Що означає код 422 Unprocessable Entity?

**Відповідь:** Сервер успішно розібрав синтаксис JSON, але дані всередині порушують бізнес-правила або схему валідації (наприклад, сума замовлення менша за нуль).

---

### 13. Як перевірити поведінку API при перевищенні ліміту частоти запитів (Rate Limiting)?

**Відповідь:** Надіслати серію швидких послідовних запитів (наприклад, 100 запитів за секунду через Postman Runner чи k6) та переконатися, що сервер повертає статус 429 Too Many Requests із заголовком Retry-After.

---

### 14. Що таке Payload у контексті HTTP?

**Відповідь:** Це корисне навантаження — дані, що передаються в тілі запиту (Request Body) або повертаються у тілі відповіді (Response Body).

---

### 15. Чому в REST API заборонено використовувати дієслова в шляхах URL (наприклад, /api/getUsers)?

**Відповідь:** Тому що REST орієнтований на ресурси (іменники), а дія над ними визначається стандартизованими HTTP-методами (GET, POST, PUT, DELETE).

---

### 16. Як QA перевіряє обробку помилок при передачі пошкодженого JSON (Malformed JSON)?

**Відповідь:** Надсилає запит із пропущеною лапкою чи зайвою комою і перевіряє, що сервер повертає 400 Bad Request, а не зависає і не падає з кодом 500.

---

### 17. Що таке контракт API (API Contract)?

**Відповідь:** Це формальна угода між клієнтом і сервером (найчастіше OpenAPI/Swagger специфікація), що фіксує точні формати маршрутів, типів параметрів, статусів та схем відповідей.

---

### 18. Що таке безпечні (Safe) методи з точки зору QA?

**Відповідь:** Методи GET та HEAD, які за жодних умов не повинні змінювати дані в базі чи стан системи на сервері.

---

### 19. Як використовувати AI для аналізу поведінки API?

**Відповідь:** AI допомагає за лічені секунди складати матриці негативних сценаріїв на основі Swagger-файлів та інтерпретувати складні відповіді про помилки.

---

### 20. Що таке Response Time (Час відгуку) і як його оцінює QA?

**Відповідь:** Це час від моменту відправки останнього байта запиту до отримання першого/останнього байта відповіді. QA перевіряє відповідність часу відгуку встановленому SLA (наприклад, 95% запитів < 300мс).

---
