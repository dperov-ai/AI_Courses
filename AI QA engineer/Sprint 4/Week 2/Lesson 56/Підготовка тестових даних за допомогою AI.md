# Підготовка тестових даних за допомогою AI: генерація синтетичних датасетів, граничні масиви, маскування та GDPR-compliance

Тестування сучасного програмного забезпечення без якісних тестових даних неможливе.

Якщо тестувальник перевіряє систему лише на трьох записах: *«Іван Іванов», «test@test.com», «+380501112233»*, система неодмінно зламається на продакшні, коли реальний користувач введе прізвище з апострофом (*Д'Артаньян*), ім'я довжиною 120 символів, емодзі в коментарі, китайські ієрогліфи або номер телефону в нестандартному міжнародному форматі.

Водночас копіювання реальної бази даних користувачів з продакшну на тестовий сервер є **грубим злочином у сфері безпеки**, що карається гігантськими штрафами за порушення регламентів **GDPR, HIPAA та банківської таємниці**.

Штучний інтелект стає ідеальним генератором **синтетичних тестових даних (Synthetic Test Data)**: він створює реалістичні, валідні, безпечні та різноманітні датасети будь-якого обсягу у форматах JSON, SQL, CSV та XML за лічені секунди.

У цьому поглибленому посібнику ми розглянемо:

* класифікацію тестових даних: Позитивні, Граничні (Boundary), Аномальні (Fuzzing) та Стресові датасети;
* створення синтетичних персональних даних (Fake PII: імена, адреси, телефони, IBAN, паспорти) без витоку реальних даних;
* генерацію складних реляційних структур зі збереженням зв'язків (Foreign Keys, зв'язки 1-to-Many між користувачами, замовленнями та транзакціями);
* стрес-дані: Unicode, SQL Injection пейлоади, XSS-ін'єкції, спецсимволи та переповнення буфера;
* маскування (Data Masking / Anonymization) та обфускацію реальних виробничих баз даних;
* скрипти генерації тестових фікстур на Python (Faker + LLM).

## 2. Генерація реляційних датасетів зі збереженням цілісності

Часто для тестування потрібна не просто таблиця користувачів, а зв'язана екосистема: Користувачі -> їхні Замовлення -> Товари в замовленні.

```markdown
# ПРОМПТ ДЛЯ ГЕНЕРАЦІЇ ЗВ'ЯЗАНОГО JSON-ДАТАСЕТУ:
Ти — Data Engineer для QA. 
Згенеруй тестовий датасет у форматі JSON для тестування системи логістики.

СТРУКТУРА:
1. Масив з 3 користувачів: `user_id`, `name`, `email`, `registered_at`.
2. Масив з 5 замовлень: `order_id`, `user_id` (посилається на реальний id з масиву 1), `total_amount`, `status` ("pending" | "shipped" | "delivered").
3. Усі дати мають бути логічно узгоджені: дата замовлення ПІЗНІШЕ за дату реєстрації користувача!
4. Включи 1 користувача з українським іменем з апострофом (наприклад, "В'ячеслав"), 1 користувача з дуже довгим email (50+ символів).
```

## 3. Безпека даних: Чому не можна копіювати продакшн (GDPR Compliance)

```
  ПОМИЛКОВИЙ ШЛЯХ (Кримінальний ризик & Штрафи):
  [ Продакшн БД з паспортами клієнтів ] ──► [ Копіювання на Test Server ] ──► [ ВИТІК ДАНИХ! ]

  ПРАВИЛЬНИЙ ШЛЯХ (Синтетичні дані від AI):
  [ Опис схеми БД без реальних даних ] ──► [ AI генерує 1,000 синтетичних людей ] ──► [ 100% БЕЗПЕЧНО ]
```

### Техніка Data Masking (Маскування):
Якщо необхідно використати структуру продакшну:
* Реальні імена замінюються на вигадані через алгоритми генерації.
* Номери карток замінюються на валідні тестові номери (Luhn Algorithm Test Numbers).
* Номери телефонів замінюються на діапазони фіктивних номерів (наприклад, `+380 00 000 00 00`).

## Резюме уроку

1. Якісні тестові дані — запорука виявлення **прихованих та крайових багів** до релізу.
2. Використання реальних даних користувачів на тест-серверах суворо заборонено законами **GDPR/HIPAA** — використовуйте **синтетичні дані від AI**.
3. Завжди тестуйте систему на 5 категоріях: **валіди, межі, стрес-дані, Unicode/RTL та ін'єкції безпеки**.
4. Вимагайте від AI генерації **реляційно зв'язаних даних** із дотриманням хронології та цілісності ключів.
