# Перетворення вимог та User Stories у тестові сценарії: методологія декомпозиції, синтаксис Gherkin (BDD) та матриці покриття

Найгірша ситуація для тестувальника — отримати від продуктової команди User Story формату: *«Як користувач, я хочу зручно оплачувати замовлення в один клік, щоб швидше отримувати товар»* без жодних критеріїв приймання (Acceptance Criteria), описів помилок та технічних деталей.

Якщо тестувальник спробує писати тест-кейси за такою сирою вимогою вручну, він витратить години на випитування подробиць або пропустить половину критичних сценаріїв збою (наприклад: що робити, якщо банк відхилив транзакцію, якщо сесія користувача закінчилася або якщо інтернет обірвався під час списання).

Штучний інтелект стає потужним аналітичним конвертером, який здатний взяти сиру або неповну User Story і розгорнути її у **вичерпну матрицю тестових сценаріїв за стандартом BDD (Gherkin: Given-When-Then), що покриває позитивні, негативні, крайові та безпекові кейси**.

У цьому поглибленому посібнику ми розглянемо:

* структуру професійної User Story та концепцію INVEST;
* Acceptance Criteria за стандартом **Given-When-Then (Gherkin syntax)**;
* покрокову методологію декомпозиції вимоги на 4 квадранти тестування (Happy Path, Negative, Edge Cases, Security/Performance);
* шаблони системних промптів для генерації тестових сценаріїв промислової якості;
* побудову матриці простежуваності вимог (Requirements Traceability Matrix / RTM) за допомогою AI;
* техніку верифікації згенерованих тест-кейсів на повноту та надмірність.

## 1. Анатомія User Story та критеріїв приймання

```
+───────────────────────────────────────────────────────────────────────────+
|                           СТРУКТУРА USER STORY                            |
+───────────────────────────────────────────────────────────────────────────+
| РОЛЬ:      "Як зареєстрований покупець інтернет-магазину..."              |
| ДІЯ:       "...я хочу зберегти дані своєї банківської картки в профілі..."|
| ЦІННІСТЬ:  "...щоб не вводити 16-значний номер при кожній новій покупці". |
+───────────────────────────────────────────────────────────────────────────+
| КРИТЕРІЇ ПРИЙМАННЯ (ACCEPTANCE CRITERIA / GHERKIN BDD):                   |
| Scenario: Успішне збереження валідної картки                              |
|   Given користувач авторизований у системі та відкрив екран "Оплата"      |
|   When він вводить номер картки "4111...", термін дії "12/26", CVV "123"  |
|   And натискає кнопку "Зберегти картку"                                   |
|   Then система токенізує картку через платіжний шлюз                      |
|   And відображає картку у списку у маскованому вигляді "**** **** **** 1111"|
|   And CVV-код НЕ зберігається в базі даних додатку.                       |
+───────────────────────────────────────────────────────────────────────────+
```

## 2. Чотири квадранти декомпозиції вимоги

Коли AI генерує тестові сценарії, його потрібно спрямувати за 4 обов'язковими напрямками:

```
  ┌─────────────────────────────────────────────────────────────┐
  │ 1. ПОЗИТИВНІ СЦЕНАРІЇ (Happy Path)                          │
  │ Стандартний успішний шлях користувача з валідними даними.   │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
  ┌──────────────────────────────┴──────────────────────────────┐
  │ 2. НЕГАТИВНІ СЦЕНАРІЇ (Negative Testing)                    │
  │ Прострочена картка, невірний CVV, недостатньо коштів,       │
  │ блокування банком. Перевірка зрозумілості повідомлень про   │
  │ помилки.                                                    │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
  ┌──────────────────────────────┴──────────────────────────────┐
  │ 3. ГРАНИЧНІ ЗНАЧЕННЯ ТА КРАЙОВІ СТАНИ (Edge Cases)          │
  │ Картка закінчується в поточному місяці, картка з 19-значним │
  │ номером, введення емодзі в поле імені власника.             │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
  ┌──────────────────────────────┴──────────────────────────────┐
  │ 4. БЕЗПЕКА ТА ВІДМОВОСТІЙКІСТЬ (Security & Resilience)      │
  │ Захист від подвійного списання при багаторазовому кліку на  │
  │ кнопку (ідемпотентність), відповідність PCI-DSS.            │
  └─────────────────────────────────────────────────────────────┘
```

## 3. Професійний промпт для генерації BDD-сценаріїв

```markdown
Ти — провідний QA Lead та експерт із Behavior-Driven Development (BDD).
Твоя задача — перетворити надану User Story на вичерпний набір тестових сценаріїв у форматі Gherkin.

ВИМОГИ ДО РЕЗУЛЬТАТУ:
1. Оформи сценарії за блоками:
   - Блок A: Позитивні сценарії (Happy Path) — 2-3 кейси.
   - Блок B: Негативні сценарії (Negative Cases) — 3-4 кейси.
   - Блок C: Крайові випадки (Edge Cases) — 3 кейси.
   - Блок D: Нефункціональні аспекти (Безпека / Ідемпотентність) — 2 кейси.
2. Кожен сценарій пиши суворим синтаксисом: `Scenario:`, `Given`, `When`, `Then`, `And`.
3. Склади зведену матрицю простежуваності (Traceability Matrix) у вигляді таблиці:
   | ID Сценарію | Назва перевірки | Тип тесту | Пріоритет (P1/P2/P3) |

ВХІДНА USER STORY:
"""
[Вставте текст вимоги або опис фічі]
"""
```

## Резюме уроку

1. Перетворення неструктурованих вимог на точні тестові сценарії — **ключова суперсила AI-Augmented QA**.
2. Стандарт **Gherkin (Given-When-Then)** забезпечує єдину мову спілкування між бізнесом, розробниками та тестувальниками.
3. Обов'язково вимагайте від моделі покриття **всіх 4 квадрантів**: позитивні, негативні, крайові та безпекові кейси.
4. Створюйте **матриці простежуваності (RTM)** для гарантії того, що жоден пункт вимог не залишився без тесту.
