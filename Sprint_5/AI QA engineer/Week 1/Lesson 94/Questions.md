# Контрольні запитання до Уроку 94: Декомпозиція Acceptance Criteria

1. **Що таке Acceptance Criteria (Критерії прийнятності) в Agile розробці?**
   - A) Оцінки на випускному екзамені.
   - B) Чіткі умови та правила, виконання яких доводить, що User Story реалізована коректно та готова до релізу. [Правильна]
   - C) Розклад перерв на каву.
   - D) Вартість розробки сайту.
   *Пояснення: AC визначають стандарт якості та повноти реалізації фічі.*

2. **Який ключовий недолік мають розмиті формулювання AC типу 'Користувач може швидко завантажити файл'?**
   - A) Вони займають мало місця в Jira.
   - B) Їх неможливо однозначно протестувати без числових метрик (наприклад, розмір файлу < 10MB, час < 2 сек, підтримувані формати). [Правильна]
   - C) Вони написані українською мовою.
   - D) Немає жодного недоліку.
   *Пояснення: Відсутність вимірюваності робить тестування суб'єктивним.*

3. **Яка структура використовується у форматі Gherkin для опису сценаріїв прийнятності?**
   - A) Start -> Middle -> Finish.
   - B) Given (Початковий стан) -> When (Дія) -> Then (Очікуваний результат). [Правильна]
   - C) Input -> Output -> Error.
   - D) HTML -> CSS -> JavaScript.
   *Пояснення: Given-When-Then — міжнародний стандарт синтаксису BDD.*

4. **Як AI допомагає в декомпозиції одного високорівневого Acceptance Criterion?**
   - A) Видаляє цей критерій з беклогу.
   - B) Генерує повний спектр сценаріїв: позитивний потік, негативні валідації, помилки мережі, таймаути та перевірки прав доступу. [Правильна]
   - C) Автоматично закриває тікет як протестований.
   - D) AI не розуміє вимог.
   *Пояснення: ШІ розгортає одне речення у вичерпну матрицю тестів.*

5. **Що описує блок 'Given' у BDD сценарії?**
   - A) Кінцевий результат перевірки.
   - B) Передумови, контекст та початковий стан системи до здійснення дії (наприклад: користувач авторизований, у кошику 1 товар). [Правильна]
   - C) Назву компанії клієнта.
   - D) Швидкість інтернету.
   *Пояснення: Given задає попередні умови (Preconditions).*

6. **Яка різниця між Rule-Oriented та Scenario-Oriented форматами Acceptance Criteria?**
   - A) Rule-Oriented описує бізнес-правила як список вимог, а Scenario-Oriented описує конкретні користувацькі шляхи поведінки. [Правильна]
   - B) Немає жодної різниці.
   - C) Rule-Oriented використовують тільки юристи.
   - D) Scenario-Oriented пишеться лише для відеоігор.
   *Пояснення: Обидва формати доповнюють один одного залежно від складності логіки.*

7. **Чому декомпозиція AC повинна враховувати Backend/API статус-коди?**
   - A) Щоб перевірити роботу інтернету.
   - B) Щоб QA інженер перевірив не лише UI, а й коректність контрактів відповідей (200 OK, 400 Bad Request, 403 Forbidden). [Правильна]
   - C) Статус-коди не мають значення для тестувальника.
   - D) Це вимога браузера.
   *Пояснення: Наскрізне тестування перевіряє поведінку на всіх шарах архітектури.*

8. **Що робити, якщо Acceptance Criteria містять взаємовиключні вимоги?**
   - A) Протестувати випадковим чином.
   - B) Зупинити розробку, підсвітити колізію вимог Product Owner / BA та узгодити єдине коректне правило до початку кодингу (Shift-Left). [Правильна]
   - C) Написати код без вимог.
   - D) Проігнорувати.
   *Пояснення: Раннє виявлення суперечностей заощаджує до 50% вартості переробок.*

9. **Як AI допомагає генерувати 'Scenario Outline' з таблицею прикладів (Examples)?**
   - A) AI заповнює таблицю випадковими символами.
   - B) Автоматично будує параметризовану таблицю вхідних даних та очікуваних результатів для десятків комбінацій параметрів. [Правильна]
   - C) Видаляє таблиці.
   - D) Збільшує розмір шрифту.
   *Пояснення: Scenario Outline автоматизує тестування таблиць комбінацій.*

10. **Що означає критерій 'Testable' для Acceptance Criteria?**
    - A) Текст має бути написаний латиницею.
    - B) Критерій сформульований настільки чітко, що тестувальник може однозначно визначити статус перевірки: Pass або Fail. [Правильна]
    - C) Тест займає менше 1 секунди.
    - D) До критерію додано малюнок.
    *Пояснення: Однозначність вердикту — основа тестованості.*

11. **Чому важливо включати перевірки безпеки ролей (RBAC) у декомпозицію AC?**
    - A) Щоб заборонити всім працювати.
    - B) Щоб переконатися, що користувач з обмеженими правами (наприклад, гість) не може виконати дію адміністратора через прямий API-запит. [Правильна]
    - C) Для прискорення завантаження.
    - D) Це не стосується QA.
    *Пояснення: Перевірка авторизації на бекенді запобігає витоку привілеїв (IDOR / BOLA).*

12. **Як сформулювати промпт до AI для декомпозиції User Story платіжного модуля?**
    - A) «Протестуй оплату.»
    - B) «Декомнизуй надану User Story та AC на 8 детальних Gherkin-сценаріїв: успішна оплата, недостатній баланс, 3DS таймаут, невалідна картка, дублікат транзакції, повернення.» [Правильна]
    - C) «Напиши щось про гроші.»
    - D) «Запитай у банку.»
    *Пояснення: Деталізація категорій змушує ШІ покрити всі критичні гілки платежу.*

13. **Що таке Empty State сценарій в декомпозиції UI?**
    - A) Вимкнений комп'ютер.
    - B) Перевірка коректного та дружнього відображення екрана, коли даних ще немає (наприклад, порожній кошик, 0 знайдених товарів). [Правильна]
    - C) Помилка сервера.
    - D) Очищення пам'яті.
    *Пояснення: Empty State — обов'язкова частина якісного UX та тест-дизайну.*

14. **Яка роль Acceptance Criteria у визначенні Definition of Done (DoD)?**
    - A) AC визначають критерії готовності конкретної фічі, без виконання яких задача не може вважатися Done. [Правильна]
    - B) Вони замінюють заробітну плату.
    - C) Вони не пов'язані з DoD.
    - D) Це маркетинговий документ.
    *Пояснення: Виконання всіх AC — головна умова закриття завдання.*

15. **Як AI допомагає виявити пропущені нефункціональні вимоги (NFR) в AC?**
    - A) AI заперечує існування NFR.
    - B) Аналізує бізнес-контекст і нагадує про ліміти швидкодії, мобільну адаптивність, вимоги до шифрування та доступності WCAG. [Правильна]
    - C) Вимикає сервери.
    - D) Зменшує розмір коду.
    *Пояснення: ШІ підсвічує «сліпі зони» NFR, які часто забувають аналітики.*

16. **Що таке 'Happy Path' у тестуванні?**
    - A) Прогулянка на свіжому повітрі.
    - B) Сценарій виконання операції за ідеальних умов, коли користувач вводить коректні дані і система не стикається з жодними помилками. [Правильна]
    - C) Сценарій падіння бази даних.
    - D) Тестування гри.
    *Пояснення: Happy Path — базовий позитивний маршрут користувача.*

17. **Чому тестування виключно 'Happy Path' є критичною помилкою QA інженера?**
    - A) Бо користувачі завжди діють ідеально.
    - B) Реальні користувачі та зловмисники постійно вводять некоректні дані, втрачають зв'язок і роблять помилки, які система повинна стабільно обробляти. [Правильна]
    - C) Це не є помилкою.
    - D) Бо Happy Path не існує.
    *Пояснення: Надійність ПЗ визначається саме обробкою негативних та крайових сценаріїв.*

18. **Що є головним підсумком якісної декомпозиції Acceptance Criteria?**
    - A) 100 сторінок нечитабельного тексту.
    - B) Прозорий, структурований набір тест-кейсів, що покриває функціональні, граничні та безпекові аспекти фічі без «білих плям». [Правильна]
    - C) Відмова від тестування.
    - D) Збільшення кількості багів у релізі.
    *Пояснення: Повне тестове покриття з першого дня розробки — мета декомпозиції.*
