# Урок 89: Генерація коду за описом функціональності: від бізнес-логіки до чистої реалізації

## 1. Покрокова декомпозиція та специфікація контрактів

Генерація великих програмних систем «одним магічним промптом» майже завжди зазнає невдачі. Професійний підхід полягає у **покроковій інкрементальній генерації** (Step-by-Step Code Generation):

1. **Етап 1: Контракти та типи даних (Data Models & Interfaces)**. Спочатку генеруються DTO, Pydantic-моделі або TypeScript-інтерфейси.
2. **Етап 2: Сигнатури та бізнес-сервіси (Core Business Logic)**. Реалізація «чистих» функцій без прив'язки до бази чи HTTP.
3. **Етап 3: Інтеграційний шар (Adapters / Routers / DB Layer)**. Підключення до ORM, контролерів та зовнішніх API.
4. **Етап 4: Юніт- та інтеграційні тести (TDD Approach)**. Генерація перевірок крайових умов.

```mermaid
graph LR
    Spec["Бізнес-опис функції"] --> Types["1. Schemas & Types"]
    Types --> Core["2. Core Domain Logic"]
    Core --> Adapters["3. Controller & DB Adapter"]
    Adapters --> Tests["4. Unit & Integration Tests"]
```

## 2. Патерн Test-Driven Prompting (TDP)

Один із найефективніших методів отримання бездоганного коду — **попросити AI спочатку згенерувати тести, а потім реалізувати код**, що проходить ці тести:
1. *Запит 1*: «Напиши набір тестів на Pytest для функції валідації номера банківської картки за алгоритмом Луна (валідна картка, невалідний номер, невірний формат, порожній рядок, спецсимволи).»
2. *Запит 2*: «Тепер напиши чисту реалізацію функції `validate_luhn(card_number: str) -> bool`, яка успішно проходить 100% цих тестів.»

## 3. Генерація з урахуванням архітектурних патернів (Clean Architecture / SOLID)

Під час генерації важливо вимагати дотримання розділення обов'язків:
- **Dependency Inversion (DIP)**: Залежність від абстракцій (інтерфейсів/протоколів), а не від конкретних реалізацій.
- **Single Responsibility (SRP)**: Роутер займається лише HTTP, валідатор — валідацією, репозиторій — базою даних.
