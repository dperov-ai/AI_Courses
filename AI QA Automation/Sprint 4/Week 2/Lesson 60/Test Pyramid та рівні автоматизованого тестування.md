# Test Pyramid та рівні автоматизованого тестування: Unit, Integration, API, E2E та антипатерн «Ice Cream Cone»

Однією з головних причин провалу проектів автоматизації є неправильний баланс між різними типами тестів. Коли команда починає автоматизацію з написання сотень важких UI-тестів через браузер (Selenium/Playwright), вона неминуче отримує повільний, крихкий і дорогий набір тестів, який виконується 6 годин і падає від кожного другого коміту.

Щоб запобігти цьому, засновник сучасної інженерної культури Майк Кон (Mike Cohn) та Мартін Фаулер (Martin Fowler) сформулювали концепцію **Піраміди тестування (Test Pyramid)**.

**Піраміда тестування** — це архітектурна модель розподілу автотестів за рівнями, яка гарантує максимальну швидкість зворотного зв'язку, стабільність та мінімальну вартість підтримки.

У цьому поглибленому посібнику ми розглянемо:

* класичну піраміду тестування: Модульні тести (Unit), Інтеграційні тести (Integration), Тести сервісного рівня (API/Contract), Наскрізні тести (E2E UI);
* характеристики кожного рівня: швидкість, вартість, ізоляція, використання Mock/Stub об'єктів;
* смертельний антипатерн **«Ріжок морозива» (Ice Cream Cone / Inverted Pyramid)** та антипатерн **«Пісочний годинник» (Hourglass)**;
* сучасні адаптації: Тестовий кубок (Testing Trophy) для сучасних фронтенд-додатків;
* як AI допомагає збалансувати піраміду: масова генерація Unit та API-тестів замість перевантаження UI.

---

## 1. Класична піраміда тестування (The Test Pyramid)

```
                            /\
                           /  \     UI E2E TESTS (5-10%)
                          / E2E\    - Повільні (секунди/хвилини), дорогі, крихкі.
                         /──────\   - Тестують критичні користувацькі шляхи.
                        /        \
                       /   API /  \   SERVICE / INTEGRATION / API TESTS (20-30%)
                      / INTEGRATION\  - Швидкі (100-300 ms), надійні, без UI.
                     /──────────────\ - Тестують бізнес-логіку та роботу з БД.
                    /                \
                   /    UNIT TESTS    \  UNIT TESTS (60-70%)
                  /      (Модульні)    \ - Блискавичні (1-5 ms), повністю ізольовані.
                 /──────────────────────\ - Тестують окремі функції, методи та класи.
```

## 3. Антипатерн «Ріжок морозива» (Inverted Pyramid)

Коли команда не пише Unit та API-тести, а всю перевірку покладає на браузерні кліки:

```
  АНТИПАТЕРН "ICE CREAM CONE" (КАТАСТРОФА):
  
     \   UI E2E TESTS (80%)  /   ◄── 1,000 UI тестів ганяються 4 години,
      \─────────────────────/        постійно падають через таймаути мережі.
       \  INTEGRATION (15%)/
        \─────────────────/
         \  UNIT (5%)    /       ◄── Юніт-тестів майже немає, розробники
          \─────────────/            не перевіряють свій код локально.
```

### Наслідки антипатерну:
* Розробники чекають результатів білда півдня замість 5 хвилин.
* Помилка в одній кнопці ламає 200 наскрізних тестів одночасно.
* Збільшується вартість хмарних серверів (CI Runner Cloud Bills).

---

## 4. Як AI допомагає відновити правильну форму піраміди

1. **Миттєве написання Unit-тестів:** AI генерує 100% покриття для будь-якої функції на Python/JavaScript з моками та граничними значеннями за 10 секунд.
2. **Перенесення перевірок з UI на API:** Замість того, щоб реєструвати користувача через заповнення 10 полів у браузері, AI створює допоміжний API-виклик `POST /api/v1/users`, скорочуючи час виконання кроку з 15 секунд до 50 мілісекунд.
3. **Автоматична генерація контрактних тестів:** Створення перевірок відповідності API специфікації OpenAPI/Swagger.

---

## Резюме уроку

1. **Піраміда тестування** — фундамент стабільної та швидкої інженерної інфраструктури.
2. **База піраміди (Unit + API)** повинна містити 80-90% усіх тестів: вони блискавичні, надійні та дешеві.
3. **Верхівка піраміди (UI E2E)** має містити лише 5-10% тестів для перевірки критичних бізнес-шляхів.
4. Уникайте антипатерну **«Ріжок морозива»**, переносячи перевірки бізнес-правил на нижчі рівні за допомогою AI.
