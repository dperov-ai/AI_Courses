# Коли достатньо промпта, а коли потрібен workflow або AI-агент: повний посібник з архітектурного вибору

У сучасному світі AI-технологій спостерігається небезпечний тренд: маркетологи закликають впроваджувати «автономних AI-агентів» для кожної елементарної бізнес-задачі.

Проте в реальній інженерній практиці більшість проектів зазнають фіаско саме через **надмірну складність архітектури (Over-engineering)**. Спроба побудувати складну автономну агентну систему для задачі, яка вирішується або звичайним промптом у чаті, або лінійним 3-кроковим сценарієм у Make/n8n, веде до появи повільного, надзвичайно дорогого та нестабільного монстра, який постійно ламається та галюцинує.

Професіоналізм AI-архітектора полягає у виборі **мінімально необхідного рівня складності**, який гарантує стабільний бізнес-результат за мінімальних витрат.

У цьому поглибленому посібнику ми розглянемо:

* три рівні зрілості AI-інструментів: Single Prompt -> Structured Workflow -> Autonomous Agent;
* що таке автономний AI-агент, цикл ReAct та робота з зовнішніми інструментами (Tools / Function Calling);
* поглиблену матрицю прийняття архітектурних рішень;
* антипатерн Over-engineering: як не витратити $50,000 на те, що робиться за 15 хвилин;
* реальні бізнес-сценарії з чітким обґрунтуванням вибору кожного рівня.

## 2. Глибинна різниця: Workflow vs AI-Agent

Ключова відмінність полягає в тому, **хто володіє логікою прийняття рішень про наступний крок**:

```
+───────────────────────────────────────────────────────────────────────────+
|               ДЕ СТВОРЮЄТЬСЯ МАРШРУТ ВИКОНАННЯ ЗАДАЧІ?                    |
+───────────────────────────────────────────────────────────────────────────+
| У WORKFLOW (Конвеєрі):                                                    |
| Маршрут на 100% зафіксований людиною-інженером:                           |
| [Крок 1] ──► [Крок 2] ──► IF x > 10 THEN [Крок 3] ELSE [Крок 4]           |
| Модель не може сама придумати Крок 5. Вона лише обробляє дані на своєму   |
| вузлі. Це гарантує повну передбачуваність і високу швидкість.             |
|                                                                           |
| В AI-AGENTІ (Агенті):                                                     |
| Інженер задає лише МЕТУ та НАДАЄ НАБІР ІНСТРУМЕНТІВ (Tools):              |
| [Мета: Знайти постачальника зерна] + [Інструменти: Пошук, Калькулятор, Email]|
| Модель САМА запускає цикл ReAct:                                          |
| "1. Подумаю: спочатку пошукаю в Google -> Викликаю Tool_Search".          |
| "2. Побачила результат -> Подумаю: треба порахувати ціну -> Викликаю Calc".|
| "3. Подумаю: ціна підходить -> Викликаю Tool_Send_Email".                 |
+───────────────────────────────────────────────────────────────────────────+
```

## 4. Антипатерн Over-Engineering: реальний бізнес-кейс

### Ситуація:
Компанія захотіла автоматизувати збір лідів із контактної форми на сайті та відправку комерційних пропозицій.

* **Помилкове рішення (Over-engineering):**  
  Розробники витратили 2 місяці та $15,000 на створення складного мультиагентного фреймворку (AutoGen/CrewAI), де «Агент-Менеджер» спілкувався з «Агентом-Аналітиком» та «Агентом-Копірайтером».  
  *Результат:* Агенти постійно зациклювалися, витрачали $10 на кожну заявку, часто надсилали клієнтам дивні листи або зависали посеред розмови.

* **Правильне рішення (Structured Workflow):**  
  Створення 4-вузлового сценарію в n8n:  
  `[Webhook форми] -> [LLM парсить ім'я та бюджет] -> [Генерація PDF за шаблоном] -> [Gmail відправляє лист]`.  
  *Результат:* Зібрано за 2 години, собівартість $0.002 за заявку, надійність 100%, нуль збоїв.

## Резюме уроку

1. Завжди починайте з найпростішого рівня: **Промпт -> якщо повторюється щодня, будуйте Workflow -> якщо алгоритм динамічний, створюйте Агента**.
2. **Structured Workflow (Make / n8n)** — головний фундамент бізнес-автоматизацій: швидкий, дешевий та надійний на 99.9%.
3. **AI-Агенти** потрібні виключно для завдань із високою невизначеністю, де системі потрібна повна свобода вибору інструментів та покрокового дослідження.
4. Уникайте пастки **Over-engineering**, яка марнує бюджети на надмірно складні рішення.
