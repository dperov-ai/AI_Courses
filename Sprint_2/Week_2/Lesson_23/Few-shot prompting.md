# Few-shot prompting: сила прикладів у роботі з AI

Коли ми просимо велику мовну модель (LLM) виконати задачу, у нас є два принципово різні шляхи:
1. **Описати словами, як це має бути** (довгі правила, пояснення, обмеження).
2. **Показати конкретні зразки** за принципом «Ось вхідні дані -> Ось бажаний результат».

Другий підхід у науці про штучний інтелект називається **Few-shot prompting** (промптинг за кількома прикладами). Це одна з найпотужніших технік prompt engineering, яка дозволяє досягти бездоганного результату навіть у тих випадках, коли описати задачу словами надзвичайно складно.

У цьому уроці ми розберемо:

* що таке Zero-shot, One-shot та Few-shot prompting;
* як мовні моделі навчаються «на льоту» завдяки In-Context Learning;
* чому один точний приклад замінює три сторінки інструкцій;
* як правильно конструювати блоки прикладів (Input -> Output);
* скільки прикладів дійсно потрібно і де починається перевитрата токенів;
* типові помилки (зміщення класів, перенавчання в контексті);
* готові практичні кейси для бізнесу, аналітики та роботи з текстом.

---

## Парадигми промптингу: Zero-shot, One-shot та Few-shot

Усі запити до мовних моделей за кількістю наданих зразків поділяються на три основні рівні:

```
+-------------------------------------------------------------------+
|                        ПАРАДИГМИ ПРОМПТИНГУ                       |
+-------------------------------------------------------------------+
| 1. ZERO-SHOT  ───► Лише інструкція (без жодного прикладу)         |
| 2. ONE-SHOT   ───► Інструкція + 1 якісний приклад                 |
| 3. FEW-SHOT   ───► Інструкція + 2-5 (або більше) типових прикладів|
+-------------------------------------------------------------------+
```

### 1. Zero-shot Prompting (Промптинг без прикладів)
Ви просто формулюєте задачу і розраховуєте на базові знання моделі, отримані під час її попереднього навчання (pre-training).

> **Промпт:**  
> Визнач тональність відгуку (позитивна, нейтральна, негативна):  
> «Товар доставили вчасно, але пакування було пом’ятим».

* **Коли використовувати:** Для стандартних, простих і широко розповсюджених завдань (переклад, базовий копирайтинг, загальні питання).

---

### 2. One-shot Prompting (Промптинг з одним прикладом)
Ви надаєте інструкцію і додаєте рівно один зразок того, як вхідні дані трансформуються у вихідні.

> **Промпт:**  
> Перетвори неформальне повідомлення на лаконічний корпоративний статус за зразком.
> 
> **Приклад:**  
> *Вхід:* «Я там трохи покопався в базі, наче все ок, але треба ще протестити завтра зранку».  
> *Результат:* «Проведено первинний аудит БД. Критичних помилок не виявлено. Фінальне тестування заплановано на ранок наступного дня».
> 
> **Вхідні дані для опрацювання:**  
> «Дизайнер скинув макети, але вони криві, чекаю правок десь до обіду».  
> *Результат:*

* **Коли використовувати:** Коли потрібно швидко задати стиль, тональність або специфічний формат одного типу.

---

### 3. Few-shot Prompting (Промптинг з кількома прикладами)
Ви показуєте моделі серію з 2–6 (іноді більше) різноманітних прикладів, які охоплюють різні сценарії, крайові випадки (edge cases) та варіації відповідей.

```
[ ІНСТРУКЦІЯ: Класифікуй звернення клієнтів за категорією та пріоритетом ]

[ Приклад 1: Технічний збій -> P1 (Критичний) ]
[ Приклад 2: Питання щодо тарифу -> P3 (Низький) ]
[ Приклад 3: Запит на повернення коштів -> P2 (Середній) ]
[ Приклад 4: Спам / Нерозбірливе -> P4 (Ігнорувати) ]

[ НОВЕ ЗВЕРНЕННЯ: Клієнт пише: «Не можу увійти в кабінет, вибиває помилку 500» ]
[ ВІДПОВІДЬ МОДЕЛІ: ]
```

## Чому приклади працюють: механіка In-Context Learning

Великі мовні моделі володіють унікальною властивістю — **In-Context Learning (навчання всередині контексту)**.

Коли ви передаєте приклади в промпт:
1. Ваги нейромережі не змінюються (це не fine-tuning).
2. Механізм уваги (Self-Attention) виявляє **математичні та структурні закономірності** між вашим входом (Input) і виходом (Output).
3. Модель вловлює не лише прямий зміст, а й:
   * довжину відповіді;
   * пунктуацію, регістр та синтаксис;
   * рівень формальності;
   * структуру вкладеності (наприклад, JSON, списки, спеціальні символи).

> **Важливо**
> 
> Моделі набагато легше повторити продемонстрований патерн, ніж розшифрувати абстрактне словесне правило на 500 слів. Якщо у вас виникають труднощі з поясненням «на пальцях» — просто дайте 3 якісні приклади.

## Анатомія ідеального Few-shot блоку

Щоб Few-shot промпт працював без збоїв, він повинен мати чітку, стандартизовану розмітку.

```
+-------------------------------------------------------------------+
|                   СТРУКТУРА FEW-SHOT ПРОМПТУ                      |
+-------------------------------------------------------------------+
| 1. СИСТЕМНА ІНСТРУКЦІЯ (Що робити і які правила діють)            |
| 2. РОЗДІЛЮВАЧ БЛОКУ ПРИКЛАДІВ (### Приклади)                      |
| 3. ПРИКЛАД 1 (Вхід -> Вихід)                                      |
| 4. ПРИКЛАД 2 (Вхід -> Вихід)                                      |
| 5. ПРИКЛАД 3 (Вхід -> Вихід)                                      |
| 6. РОЗДІЛЮВАЧ ЦІЛЬОВОЇ ЗАДАЧІ (### Реальні дані)                  |
| 7. НОВИЙ ВХІД + ОЧІКУВАННЯ ВИХОДУ                                  |
+-------------------------------------------------------------------+
```

### Приклад бездоганного шаблону розмітки:

```markdown
Ти — асистент для вилучення сутностей із неструктурованих текстів.
Твоя задача — витягти з відгуку: [Продукт], [Оцінку від 1 до 5], [Головний недолік].
Формат виводу — виключно валідний JSON.

### Приклади:

Вхід: "Купив навушники Sony WH-1000XM5. Звук космос, але через дві години тиснуть на вуха. 4 бали."
Вихід:
{
  "product": "Sony WH-1000XM5",
  "score": 4,
  "issue": "тиснуть на вуха при тривалому носінні"
}

Вхід: "Кавомашина DeLonghi Magnifica працює вже місяць. Кава смачна, але занадто гучно меле зерна, дитина прокидається. Ставлю 3."
Вихід:
{
  "product": "DeLonghi Magnifica",
  "score": 3,
  "issue": "гучний шум під час помелу зерен"
}

Вхід: "Чохол для iPhone 15 Pro сів ідеально. Жодних нарікань, топ за свої гроші."
Вихід:
{
  "product": "Чохол для iPhone 15 Pro",
  "score": 5,
  "issue": null
}

### Опрацюй наступний текст:

Вхід: "Клавіатура Keychron K2 чудова, але клавіша пробілу трохи люфтить і дзвенить. Загалом на 4 з 5."
Вихід:
```

## Скільки прикладів додавати? Закон спадної віддачі

Часте питання початківців: *«Чи правда, що чим більше прикладів, тим краще?»*

Відповідь: **Ні.**

```
Якість
відповіді
  ▲
  │              . - - - - - - (Плато / насичення)
  │            /
  │          /
  │        /
  │       /
  │      /  (Зона найвищої ефективності: 3-5 прикладів)
  │     /
  │    /
  │   /
  └──┴─────┴─────┴─────┴─────┴────────► Кількість прикладів
     0     1     3     5     10    20
```

1. **Від 0 до 1 прикладу:** гігантський стрибок у точності форматування та стилю (модель перестає гадати).
2. **Від 1 до 3–5 прикладів:** суттєве підвищення точності логіки, стабілізація класифікації, закриття крайових випадків.
3. **Понад 5–7 прикладів:** приріст якості мінімальний або відсутній, але:
   * стрімко зростає витрата токенів (і вартість за запит);
   * збільшується затримка генерації (latency);
   * модель може почати «зациклюватися» на словах із прикладів (overfitting).

> **Оптимальне правило:**  
> Використовуйте **від 2 до 5 різноманітних прикладів**. Цього достатньо для 95% бізнес-задач.

## Принцип різноманітності та балансування вибірки

Якість Few-shot промпту визначається не кількістю прикладів, а їхньою **репрезентативністю**.

### Помилка 1: Незбалансовані класи (Class Imbalance)
Якщо ви робите промпт для модерації коментарів і надасте 4 приклади токсичних коментарів і 0 прикладів нормальних — модель почне вважати токсичним майже будь-який вхідний текст.

* **Правило:** Якщо класифікуєте на 3 класи (Позитив / Нейтрал / Негатив) — надайте щонайменше по 1 якісному прикладу на кожен клас.

### Помилка 2: Одноманітність прикладів
Якщо всі ваші приклади довжиною в 3 слова — модель розгубиться, коли клієнт надішле повідомлення на 5 абзаців.

* **Правило:** Показуйте варіативність:
  * один короткий приклад;
  * один довгий розгорнутий приклад;
  * один приклад із двозначним контекстом або сленгом;
  * один приклад, де обов'язкове поле відсутнє (значення `null` або «не вказано»).

## Реальні бізнес-кейси застосування Few-shot

### Кейс 1. Перетворення технічних баг-репортів на людські реліз-нотатки
Звичайний Zero-shot запит видасть або сухий технічний лог, або надто пишний рекламний текст. Завдяки 2 прикладам ми задаємо точний внутрішній Tone of Voice компанії:

```markdown
Перетвори внутрішній технічний опис багу на публічний пункт для списку оновлень (Release Notes).
Тон: дружній, зрозумілий звичайному користувачу, з легким гумором, 1 речення.

Приклад 1:
Вхід: "Fixed memory leak in ImageCachingService caused by unreleased bitmap references."
Вихід: "Додаток більше не втомлюється від великої кількості фото — оптимізували пам'ять, щоб усе літало."

Приклад 2:
Вхід: "Resolved race condition during checkout button rapid clicking."
Вихід: "Виправили баг із подвійним натисканням на оплату: тепер жодних випадкових подвійних замовлень."

Реальна задача:
Вхід: "Fixed WebSocket reconnection timeout on iOS when app resumes from background state."
Вихід:
```

---

### Кейс 2. Стандартизація адреси та контактних даних з сирого тексту
Коли користувачі вводять контактні дані як завгодно (із помилками, різними скороченнями, без індексів), Few-shot дозволяє надійно нормалізувати інформацію:

```markdown
Нормалізуй контактні дані у єдиний формат:
[Країна] | [Місто] | [Вулиця, будинок, кв.] | [Телефон у форматі +380...]

Приклади:

Вхід: "м. Київ, вул. Хрещатик 22 кв 14, 050 123 45 67, Петро"
Вихід: Україна | Київ | вул. Хрещатик, буд. 22, кв. 14 | +380501234567

Вхід: "Львів, Франка Івана 10 / 2, тел +38(067)999-88-77"
Вихід: Україна | Львів | вул. Івана Франка, буд. 10, кв. 2 | +380679998877

Вхід: "Одеса Дерибасівська 5 0931112233"
Вихід: Україна | Одеса | вул. Дерибасівська, буд. 5 | +380931112233

Опрацюй запис:
Вхід: "Харків пр. Науки 40, кв. 112, 095 444 55 66"
Вихід:
```

## Типові підводні камені Few-shot prompting

```
+-------------------------------------------------------------------+
|                        ТИПОВІ ПІДВОДНІ КАМЕНІ                     |
+-------------------------------------------------------------------+
| 1. Конфлікт між інструкцією та прикладами                          |
| 2. Занадто вузькі приклади -> Модель копіює їхній зміст           |
| 3. Помилки та неточності всередині самих прикладів                |
| 4. Забування розділювачів (модель сприймає приклад як нове завдання)|
+-------------------------------------------------------------------+
```

### 1. Помилка у розмітці прикладу навчає модель помилятися
Якщо ви в одному з прикладів пропустили кому в JSON або допустили граматичну помилку, модель сприйме це як **обов'язкове правило стилю** і почне навмисно дублювати цю помилку у всіх наступних генераціях.

### 2. Ефект «дзеркального копіювання» (Surface Mimicry)
Якщо в усіх прикладах для email-розсилки ви використали ім'я *«Олексій»*, модель може почати звертатися «Олексій» навіть до клієнтів з іншими іменами. Завжди варіюйте змінні дані в прикладах.

## Чек-лист для створення Few-shot промпту

- [ ] **Чи є чітка інструкція перед блоком прикладів?** (Не покладайтеся лише на приклади, вступна задача все одно потрібна).
- [ ] **Чи однакова розмітка у всіх прикладів?** (Єдині маркери: `Вхід:`, `Вихід:`, `###`).
- [ ] **Чи збалансовані класи/типи відповідей?** (Є позитивні, негативні, короткі, довгі варіанти).
- [ ] **Чи перевірено приклади на відсутність помилок і друкарських одруків?**
- [ ] **Чи додано крайовий випадок (Edge Case)?** (Що робити, якщо дані неповні або неоднозначні).
- [ ] **Чи кількість прикладів перебуває в межах 2–5 штук?**

## Резюме уроку

1. **Few-shot prompting** — це техніка передачі моделі інструкції разом із кількома зразками (Input -> Output).
2. Приклади активують механізм **In-Context Learning**, дозволяючи моделі зчитати точний формат, структуру, тон та специфічну бізнес-логіку без fine-tuning.
3. Оптимальна кількість прикладів для більшості завдань — **від 2 до 5**. Більша кількість рідко покращує результат, але збільшує затримку та вартість токенів.
4. Приклади мають бути **збалансованими** за категоріями та покривати нестандартні ситуації (крайові випадки).
5. Будь-яка неточність у прикладі сприймається моделлю як норма і тиражується у фінальних відповідях.
