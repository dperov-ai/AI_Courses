# Структуровані відповіді: від тексту до машиночитаних форматів

Коли ми використовуємо AI для повсякденного спілкування, звичайного зв'язного тексту (прози) зазвичай достатньо. Але як тільки AI стає частиною бізнес-процесу, передає дані в інші програми (CRM, Notion, Excel, Telegram-боти, Make, n8n) або повинен дати швидку аналітику — неструктурований текст стає головною проблемою.

Модель може написати:

> Звісно, я з радістю допоможу вам із цим завданням! Ось інформація, яку мені вдалося зібрати: ім'я клієнта — Олексій, його пошта — alex@example.com, а статус замовлення — оплачено. Звертайтеся, якщо будуть ще питання!

Для людини це зрозуміло, але автоматизувати обробку такої відповіді дуже складно: парсер зламається через вступні фрази та змінну структуру.

У цьому уроці ми розберемо:

* чому структурування виводу є фундаментом автоматизації та продуктивності;
* популярні формати представлення даних: Markdown, Таблиці, Key-Value, JSON, XML;
* як гарантувати 100% відповідність виводу заданій схемі;
* JSON Schema та нативні Structured Outputs у сучасних API;
* як позбутися «балакучості» моделі та отримувати тільки чисті дані;
* реальні бізнес-пайплайни використання структурованих відповідей.

## Людина vs Система: два типи споживачів контенту

Перед створенням промпту завжди потрібно відповісти на питання: **Хто буде читати або обробляти результат?**

```
+-------------------------------------------------------------------+
|                        ТИПИ СПОЖИВАЧІВ ДАНИХ                      |
+-------------------------------------------------------------------+
| 1. ДЛЯ ЛЮДИНИ (Human-Readable):                                   |
|    - Markdown (заголовки, жирний шрифт, списки, цитати)           |
|    - Порівняльні таблиці                                          |
|    - Чек-листи з чекбоксами [x]                                   |
|                                                                   |
| 2. ДЛЯ СИСТЕМ ТА КОДУ (Machine-Readable):                         |
|    - JSON / JSON Schema                                           |
|    - CSV / TSV (для імпорту в таблиці)                            |
|    - XML / Теги (<user>, <action>, <status>)                      |
+-------------------------------------------------------------------+
```

## Формати структурування для людей

### 1. Markdown-структуризація
Замість одноманітної «стіни тексту» вимагайте від моделі використання чітких візуальних елементів:

> Оформи відповідь у форматі Markdown із чіткою структурою:
> * Заголовок H2 для кожного ключового блоку.
> * Не більше 3 речень у кожному абзаці.
> * Використовуй марковані списки для перерахування фактів.
> * Головні висновки та ризики виділяй блоками цитат `> **Увага:**`.

---

### 2. Табличний формат (Markdown Tables)
Таблиці — найкращий спосіб візуалізації для порівняння параметрів, вибору рішень чи планування.

**Приклад промпту:**
> Порівняй три інструменти автоматизації (Make, n8n, Zapier) за такими параметрами:
> 1. Складність налаштування (для новачка)
> 2. Можливість Self-hosted розгортання
> 3. Цінова модель
> 4. Головна перевага
> 5. Головний недолік
> 
> Оформи результат виключно у вигляді єдиної зведеної Markdown-таблиці.

## Формати структурування для систем (JSON, XML, Key-Value)

Коли результат генерації AI потрібно передати в базу даних або відправити вебхуком (Webhook), стандартом є **JSON (JavaScript Object Notation)**.

### Проблема «брудного» JSON і як її вирішити

Звичайні промпти часто повертають «брудний» вивід:

```
Ось ваш JSON-об'єкт:
```json
{
  "name": "Олексій",
  "age": 30
}
```
Сподіваюся, це було корисно!
```

Якщо передати таку відповідь у програмний парсер `JSON.parse()`, він впаде з критичною помилкою через текст на початку та в кінці.

### Як досягти ідеально чистого JSON через промпт:

```markdown
Ти — сервіс парсингу лідів.
Твоя задача — вилучити з тексту повідомлення дані клієнта та повернути їх у форматі JSON.

Використовуй точну схему:
{
  "client_name": string or null,
  "phone": string (у форматі +380...) or null,
  "email": string or null,
  "budget_usd": number or null,
  "service_requested": string,
  "urgency": "low" | "medium" | "high"
}

КРИТИЧНІ ОБМЕЖЕННЯ:
1. Твоя відповідь повинна містити ТІЛЬКИ валідний JSON.
2. Не додавай жодних вступних фраз, пояснень чи фінальних слів.
3. Не огортай JSON у блок коду ```json ... ``` (видавай сирий текст починаючи з { і закінчуючи }).
4. Якщо значення не вказано в тексті — повертай null, не вигадуй дані.
```

## Нативні Structured Outputs у сучасних API

У 2024–2026 роках провідні AI-провайдери (OpenAI, Anthropic, Google) впровадили механізм **гарантованого дотримання схем (Guaranteed JSON Schema / Structured Outputs)** на рівні генерації токенів (Constrained Decoding).

```
                      +-----------------------------+
                      |         JSON SCHEMA         |
                      |  (Типи, обов'язкові поля)   |
                      +-----------------------------+
                                     │
                                     ▼
[ PROMPT ] ──► [ LLM + Constrained Decoding ] ──► [ 100% ВАЛІДНИЙ JSON ]
                                                 (Синтаксичні помилки 
                                                  фізично неможливі)
```

При використанні цієї функції через API або розробницькі платформи ви передаєте JSON-схему або Pydantic-модель, і модель на рівні граматики забороняє генерацію будь-яких токенів, які порушують формат.

## Тегова розмітка (XML Tags): ідеальний баланс

Коли вам потрібно поєднати вільне міркування (Chain-of-Thought) і чисті структуровані дані, найкраще працюють **XML-подібні теги**.

Цей підхід офіційно рекомендується компанією Anthropic (розробниками Claude) як найнадійніший спосіб структурування складних відповідей.

### Приклад комбінованого промпту з тегами:

```markdown
Проаналізуй звернення користувача до банку.

У відповіді використай такі обов'язкові теги:
<thought>
Тут покроково проаналізуй ситуацію: чи є ознаки шахрайства, який рівень емоційного напруження клієнта, які інструкції безпеки порушено.
</thought>

<summary>
Коротке резюме ситуації для оператора (1-2 речення).
</summary>

<action_items>
- Пункт 1
- Пункт 2
</action_items>

<crm_payload>
{
  "fraud_risk": true/false,
  "block_card_immediately": true/false,
  "category": "security_incident"
}
</crm_payload>
```

**Перевага:** Людина може легко прочитати блок `<summary>` та `<thought>`, а автоматизований скрипт регулярним виразом або парсером забирає вміст тегу `<crm_payload>`.

## Практичний кейс: обробка замовлення з месенджера

Повідомлення клієнта:
> «Добрий день! Хочу замовити у вас 3 піци Карбонара і 2 Пепероні на вулицю Сагайдачного 15, кв 4. Бажано до 19:30. Оплата готівкою кур'єру. Мій номер 067 111 22 33, Максим».

**Промпт для екстракції:**
```markdown
Ти — бекенд-парсер замовлень для ресторану.
Перетвори текстове повідомлення на структурований JSON замовлення.

Схема:
{
  "customer": {
    "name": string,
    "phone": string
  },
  "delivery": {
    "address": string,
    "target_time": string or null
  },
  "payment_method": "cash" | "card_online" | "card_terminal",
  "items": [
    {
      "name": string,
      "quantity": integer
    }
  ]
}

Повертай виключно валідний JSON.
```

**Результат генерації:**
```json
{
  "customer": {
    "name": "Максим",
    "phone": "+380671112233"
  },
  "delivery": {
    "address": "вул. Сагайдачного, буд. 15, кв. 4",
    "target_time": "19:30"
  },
  "payment_method": "cash",
  "items": [
    {
      "name": "Піца Карбонара",
      "quantity": 3
    },
    {
      "name": "Піца Пепероні",
      "quantity": 2
    }
  ]
}
```

## Чек-лист перевірки промпту на структурованість

- [ ] **Чи чітко вказано формат?** (JSON, Markdown Table, XML-теги, CSV).
- [ ] **Чи надано схему полів або приклад бажаної структури?**
- [ ] **Чи визначено допустимі значення (Enums)?** (Наприклад, `"status": "open" | "closed" | "pending"`).
- [ ] **Чи вказано, що робити з відсутніми даними?** (`null`, `""`, чи `не вказано`).
- [ ] **Чи встановлено заборону на зайві вступні та заключні фрази?**

## Резюме уроку

1. **Структуровані відповіді** перетворюють непередбачуваний текст мовної моделі на стандартизовані дані, придатні для бізнес-систем та автоматизацій.
2. Для сприйняття людиною найкраще підходять **Markdown-форматування та порівняльні таблиці**.
3. Для програмних систем стандартом є **чистий JSON** із суворо заданою схемою та типами даних.
4. Щоб уникнути зайвого тексту навколо коду, використовуйте чіткі негативні обмеження або нативні механізми **Structured Outputs**.
5. Використання **XML-подібних тегів** (`<thought>`, `<output>`) дозволяє об'єднати глибокі міркування CoT із чистими машинними даними в одній відповіді.
