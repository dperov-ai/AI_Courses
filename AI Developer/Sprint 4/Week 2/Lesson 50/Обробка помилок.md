# Обробка помилок: винятки (Exceptions), стек-трейс, захисне програмування, кастомні помилки та моніторинг

У реальному світі програми ніколи не працюють в ідеальних тепличних умовах.

Мережевий кабель може бути висмикнутий під час транзакції, диск сервера може переповнитися, база даних може не відповісти через тайм-аут, файл конфігурації може бути пошкодженим, а користувач обов'язково введе літери у поле «номер телефону». Якщо програма не готова до збоїв, вона впаде з аварійним завершенням процесу (Crash / Unhandled Exception), викликавши відмову сервісу та фінансові втрати.

Професіоналізм розробника вимірюється не тим, як його код працює в ідеальному сценарії («Happy Path»), а тим, **як елегантно та надійно система обробляє нештатні ситуації (Edge Cases & Failures)**.

У цьому поглибленому посібнику ми розглянемо:

* природу помилок: Синтаксичні помилки (Syntax Errors), Логічні баги (Logic Errors) та Винятки часу виконання (Runtime Exceptions);
* анатомію блоку `try - except / catch - finally / else`;
* аналіз Stack Trace: як читати стек викликів, знаходити першопричину (Root Cause) та файл збою;
* створення власної ієрархії кастомних бізнес-винятків (Custom Exceptions);
* антипатерни обробки помилок: ковтання винятків (`except: pass`), перехоплення занадто широкого `BaseException`;
* патерни відмовостійкості: Retry з Exponential Backoff, Circuit Breaker та журналювання помилок (Sentry, ELK, Datadog).

## 1. Анатомія конструкції Try-Except-Else-Finally

```
  ┌─────────────────────────────────────────────────────────────┐
  │ 1. TRY: Блок небезпечного коду (читання файлу, запит до API)│
  └──────────────────────────────┬──────────────────────────────┘
                                 │
           ┌─────────────────────┴─────────────────────┐
           ▼ (Якщо сталася помилка)                    ▼ (Якщо ВСЕ ПРОЙШЛО УСПІШНО)
  ┌─────────────────────────────────┐        ┌─────────────────────────────────┐
  │ 2. EXCEPT (Catch):              │        │ 3. ELSE:                        │
  │ Перехоплення КОНКРЕТНОГО типу   │        │ Код, який виконується ТІЛЬКИ    │
  │ винятку (наприклад, FileNotFnd) │        │ якщо в блоці try не було помилок│
  └────────────────┬────────────────┘        └────────────────┬────────────────┘
                   │                                          │
                   └─────────────────────┬────────────────────┘
                                         ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ 4. FINALLY: Код, який виконується ГАРАНТОВАНО ЗАВЖДИ        │
  │    (закриття з'єднань із БД, звільнення файлових дескрипторів)│
  └─────────────────────────────────────────────────────────────┘
```

## 2. Як читати Stack Trace (Стек викликів)

Коли виникає непокритий виняток, інтерпретатор друкує Stack Trace знизу вгору:

```
Traceback (most recent call last):
  File "main.py", line 42, in <module>
    order_service.checkout(user_id=15, cart=cart)
  File "services/order.py", line 88, in checkout
    self.payment_gateway.charge(amount=total)
  File "gateways/stripe.py", line 19, in charge
    response = requests.post(self.api_url, json={"amount": amount}, timeout=5)
  File "requests/api.py", line 119, in post
    return session.post(url, data=data, json=json, **kwargs)
requests.exceptions.ConnectTimeout: HTTPSConnectionPool(host='api.stripe.com', port=443): Read timed out.
```

### Алгоритм читання стека:
1. **Дивіться на останній рядок:** Він містить точну назву помилки (`ConnectTimeout`) та опис проблеми.
2. **Підніміться на один рівень вище:** Знайдіть **останній рядок вашого власного коду** (`gateways/stripe.py`, рядок 19).
3. **Проаналізуйте контекст:** Чому саме виклик `requests.post` перевищив таймаут у 5 секунд?

## 3. Топ-3 смертельні антипатерни обробки помилок

```python
# АНТИПАТЕРН 1: КОВТАННЯ ПОМИЛКИ (Silent Failure / Exception Swallowing)
try:
    save_to_database(user)
except Exception:
    pass # ЖАХ! Якщо база впаде, ніхто не дізнається, чому дані зникли!

# АНТИПАТЕРН 2: ПЕРЕХОПЛЕННЯ ЗАБАГАТО (Catch-All BaseException)
try:
    run_background_worker()
except BaseException: # Перехоплює навіть KeyboardInterrupt (Ctrl+C) і SystemExit!
    print("Помилка")

# ПРАВИЛЬНИЙ ПАТЕРН: Логування та прокидання специфічних винятків
import logging

try:
    save_to_database(user)
except DatabaseConnectionError as err:
    logging.error(f"Помилка з'єднання з БД для користувача {user.id}: {err}", exc_info=True)
    notify_devops_team()
    raise ServiceUnavailableException("Сервіс тимчасово недоступний, спробуйте пізніше") from err
```

## 4. Створення власної ієрархії кастомних винятків

```python
# Базовий бізнес-виняток додатку
class DomainException(Exception):
    """Базовий клас для всіх помилок предметної області."""
    pass

class InsufficientFundsError(DomainException):
    def __init__(self, current_balance: float, requested_amount: float):
        self.current_balance = current_balance
        self.requested_amount = requested_amount
        super().__init__(
            f"Недостатньо коштів: баланс ${current_balance}, запитано ${requested_amount}"
        )

class AccountBlockedError(DomainException):
    pass
```

## Резюме уроку

1. Обробка помилок — це створення **відмовостійкої поведінки програми** при непередбачуваних зовнішніх факторах.
2. Блок `finally` гарантує звільнення ресурсів (закриття файлів та мережевих з'єднань).
3. Ніколи не використовуйте `except: pass` — кожна помилка повинна бути **залогована зі стек-трейсом (`exc_info=True`)** або коректно оброблена.
4. Створюйте власні класи винятків для чіткого розмежування системних збоїв та порушень бізнес-правил.
