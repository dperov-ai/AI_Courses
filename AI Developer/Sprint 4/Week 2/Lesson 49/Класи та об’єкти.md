# Класи та об’єкти: Об'єктно-орієнтоване програмування (ООП), 4 стовпи проектування, SOLID та патерни

Коли розмір програмної системи перевищує кілька тисяч рядків коду, процедурний стиль перестає справлятися зі складністю. Дані та функції, розкидані окремо, починають хаотично впливати один на одного.

Для вирішення цієї проблеми виникла парадигма **Об'єктно-Орієнтованого Програмування (ООП)**. ООП об'єднує дані (стан / поля) та функції для роботи з ними (поведінку / методи) в єдині цілісні сутності — **Об'єкти**, які створюються за кресленнями — **Класами**.

У цьому поглибленому посібнику ми розглянемо:

* різницю між класом (Class Blueprint) та екземпляром об'єкта (Instance);
* чотири стовпи ООП: Інкапсуляція, Успадкування, Поліморфізм та Абстракція;
* конструктори (`__init__`), деструктори та ключове слово `self` / `this`;
* модифікатори доступу: `public`, `protected`, `private` та властивості `@property` (Getters/Setters);
* принципи чистої архітектури **SOLID** (Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion);
* Композицію vs Успадкування: чому «Composition over Inheritance» є золотим правилом сучасної розробки.

## 1. Клас vs Об'єкт: від креслення до реальності

```
  КЛАС (Креслення / Blueprint):           ОБ'ЄКТИ (Екземпляри в пам'яті / Instances):
  ┌──────────────────────────────┐        ┌──────────────────────────────┐
  │ Class: BankAccount           │───────►│ Instance 1: acc_alice        │

  └──────────────────────────────┘        ┌──────────────────────────────┐
                                 └───────►│ Instance 2: acc_bob          │
                                          │ owner = "Боб", balance = 1200│
                                          └──────────────────────────────┘
```

## 2. Чотири стовпи ООП на практиці

```
+───────────────────────────────────────────────────────────────────────────+
|                             ЧОТИРИ СТОВПИ ООП                             |
+───────────────────────────────────────────────────────────────────────────+
| 1. ІНКАПСУЛЯЦІЯ (Encapsulation):                                          |
|    - Приховування внутрішнього стану об'єкта від прямої зміни ззовні.     |
|    - Заборонено: `acc.balance = -1000` (пряма мутація).                   |
|    - Дозволено: `acc.withdraw(500)` (метод перевіряє валідність операції).|
|                                                                           |
| 2. АБСТРАКЦІЯ (Abstraction):                                              |
|    - Виділення тільки суттєвих характеристик об'єкта для зовнішнього світу.|
|    - Водієві достатньо педалі газу, йому не потрібно вручну керувати      |
|      впорскуванням палива в циліндри двигуна.                             |
|                                                                           |
| 3. УСПАДКУВАННЯ (Inheritance):                                            |
|    - Створення похідних класів на базі батьківського для повторного       |
|      використання коду (`SavingsAccount` успадковує `BankAccount`).       |
|                                                                           |
| 4. ПОЛІМОРФІЗМ (Polymorphism):                                            |
|    - Здатність різних класів реалізовувати однаковий інтерфейс по-своєму. |
|    - Метод `pay()` працює однаково для `CreditCard`, `PayPal` чи `Crypto`.|
+───────────────────────────────────────────────────────────────────────────+
```

## 3. Приклад реалізації на Python з типами даних

```python
from abc import ABC, abstractmethod

# 1. АБСТРАКЦІЯ: Інтерфейс платіжного шлюзу
class PaymentGateway(ABC):
    @abstractmethod
    def process_payment(self, amount: float) -> bool:
        pass

# 2. ПОЛІМОРФІЗМ: Різні реалізації одного інтерфейсу
class StripeGateway(PaymentGateway):
    def process_payment(self, amount: float) -> bool:
        print(f"Обробка платежу ${amount} через Stripe API...")
        return True

class CryptoGateway(PaymentGateway):
    def process_payment(self, amount: float) -> bool:
        print(f"Відправка транзакції ${amount} у блокчейн...")
        return True

# 3. ІНКАПСУЛЯЦІЯ ТА КОМПОЗИЦІЯ: Сервіс замовлень
class OrderService:
    def __init__(self, payment_gateway: PaymentGateway):
        self._gateway = payment_gateway # Композиція замість успадкування!

    def checkout(self, user: str, total: float):
        print(f"Оформлення замовлення для {user}")
        if self._gateway.process_payment(total):
            print("Замовлення успішно оплачено!")
```

## 4. Принципи SOLID: короткий довідник

* **S (Single Responsibility):** Один клас — одна відповідальність.
* **O (Open/Closed):** Класи відкриті для розширення, але закриті для модифікації.
* **L (Liskov Substitution):** Дочірній клас має повноцінно замінювати батьківський без зламу програми.
* **I (Interface Segregation):** Краще багато вузьких інтерфейсів, ніж один монолітний.
* **D (Dependency Inversion):** Модулі вищого рівня не повинні залежати від модулів нижчого рівня; обидва повинні залежати від абстракцій (інтерфейсів).
